Construindo uma rede

O Capítulo 1 mostrou como dois hosts conseguem trocar bits de forma confiável através de um único enlace. Mas a Internet conecta bilhões de dispositivos que nunca estão diretamente ligados entre si. Este capítulo explica como pacotes atravessam roteadores, como tabelas de encaminhamento são construídas e como os roteadores descobrem sozinhos os melhores caminhos da rede.

Motivação

Por que precisamos de uma camada de rede?

A camada de enlace resolve um problema específico: fazer dois vizinhos diretos — ligados pelo mesmo cabo, pela mesma fibra ou pelo mesmo canal de rádio — conversarem sem erros. Mas isso não é suficiente para conectar um notebook em Porto Alegre a um servidor no Japão: entre os dois existem dezenas de enlaces distintos, cada um com sua própria tecnologia. É É exatamente esse o papel da camada de rede: permitir que hosts que não compartilham um enlace direto troquem informação por meio de dispositivos intermediários chamados roteadores.

A unidade de informação da camada de rede é o pacote. Um roteador recebe pacotes por uma de suas interfaces, decide para qual outra interface encaminhá-los e os reenvia — repetindo esse processo até o pacote alcançar o destino final. Essa decisão de "para onde mandar em seguida" é o coração de todo o capítulo.

Diferente da camada de enlace, que normalmente lida com apenas dois vizinhos, a camada de rede precisa responder a três perguntas ao mesmo tempo: como identificar de forma única cada host e roteador (endereçamento), como decidir o próximo salto de cada pacote (encaminhamento) e como manter essas decisões corretas mesmo quando links falham ou a rede cresce (roteamento). As próximas seções tratam cada uma dessas perguntas.

Fundamentos

Pacotes e endereçamento

Um pacote é composto por um cabeçalho e uma carga útil (payload). O cabeçalho carrega as informações de controle que os roteadores precisam para tomar decisões — em especial o endereço do host de origem e o endereço do host de destino. A carga útil é o dado que a aplicação realmente quer transmitir.

Para que o encaminhamento funcione, cada dispositivo da rede — host ou roteador — precisa de um endereço de rede único, geralmente representado como uma sequência de bits de tamanho fixo. É esse endereço, e não um nome amigável como "servidor-web", que os roteadores usam para decidir o próximo salto.

Arquitetura

Datagrama vs. circuito virtual

Existem duas grandes formas de organizar o plano de encaminhamento de uma rede de pacotes. Elas se diferenciam por uma pergunta simples: o roteador precisa "lembrar" de uma conexão antes de encaminhar os pacotes que fazem parte dela?

O modo datagrama se inspira no correio tradicional: cada envelope carrega o endereço completo do destinatário, e cada agência decide independentemente para onde encaminhá-lo. O circuito virtual se inspira na telefonia clássica: antes da ligação começar, a rede monta um canal fim a fim, e depois disso os "envelopes" (quadros de voz) só precisam de um número de canal, muito mais curto que um endereço completo. A tecnologia MPLS (Multiprotocol Label Switching), usada por muitos provedores para dar previsibilidade ao tráfego dentro do seu backbone, é um exemplo moderno de comutação por rótulos.

Plano de dados

Tabelas de encaminhamento, buracos negros e loops

Uma tabela de encaminhamento associa cada destino (ou bloco de destinos) à interface de saída que deve ser usada. Se o cálculo dessa tabela estiver incorreto, dois problemas clássicos podem ocorrer:

  • Buraco negro: um roteador recebe pacotes para um destino que não consta em sua tabela e simplesmente os descarta.
  • Loop de encaminhamento: um conjunto de roteadores aponta uns para os outros em círculo, e o pacote nunca chega ao destino — apenas consome banda até ser descartado por outro mecanismo (como um limite de saltos).

Em redes muito grandes, manter uma entrada para cada host individual tornaria as tabelas gigantescas. A solução amplamente usada é o endereçamento hierárquico: os bits mais significativos do endereço identificam um bloco maior da rede (por exemplo, o provedor), e os bits menos significativos identificam o host dentro desse bloco — de forma muito parecida com um CEP, que vai do país até o número da casa. Com endereços hierárquicos, o roteador não busca uma correspondência exata: ele procura o prefixo mais longo que combina com o endereço de destino, técnica conhecida como longest prefix match. O diagrama abaixo usa, apenas para caber na figura, um endereço fictício de 16 bits — bem menor que os 32 bits de um endereço IPv4 real —, então os prefixos /n mostrados servem só para este exemplo e não devem ser lidos como blocos típicos da Internet real.

Plano de controle

Roteamento por vetor de distância

Calcular tabelas de encaminhamento manualmente só funciona em redes minúsculas. Redes reais usam algoritmos distribuídos — os roteadores trocam mensagens entre si e calculam suas próprias tabelas automaticamente. A família mais simples é o vetor de distância, baseado na ideia do algoritmo de Bellman-Ford: cada roteador só precisa saber, para cada destino, qual é o custo total do melhor caminho conhecido e por qual vizinho esse caminho passa.

Periodicamente, cada roteador envia a seus vizinhos diretos um resumo da sua própria tabela — o chamado vetor de distância. Ao receber o vetor de um vizinho, o roteador soma o custo do enlace até esse vizinho e compara com o que já conhecia; se o novo caminho for mais curto, a tabela é atualizada. Repetindo esse processo, a rede inteira converge para as rotas mais curtas sem que nenhum roteador precise conhecer a topologia completa.

O vetor de distância tem uma fragilidade conhecida como contagem ao infinito: se um enlace falha, dois roteadores vizinhos podem, por um tempo, ficar anunciando um ao outro um caminho que na verdade já não existe mais, incrementando o custo aos poucos até um valor absurdamente alto. Duas técnicas atenuam o problema:

  • Split horizon: um roteador nunca anuncia de volta, para o vizinho X, uma rota que ele aprendeu através do próprio vizinho X.
  • Split horizon com poison reverse: além de não reanunciar, o roteador anuncia explicitamente essa rota com custo infinito para o vizinho de quem a aprendeu, deixando a informação ainda mais clara.

O protocolo RIP (Routing Information Protocol) é o exemplo histórico mais conhecido de roteamento por vetor de distância, ainda usado hoje em redes pequenas ou como material didático por sua simplicidade.

Plano de controle

Roteamento por estado de enlace

A segunda grande família de algoritmos de roteamento segue uma filosofia oposta: em vez de cada roteador conhecer apenas o "resumo" que seus vizinhos enviam, todo roteador aprende a topologia completa da rede e calcula localmente o melhor caminho até cada destino, tipicamente com o algoritmo de Dijkstra.

O processo tem três etapas. Primeiro, cada roteador descobre seus vizinhos diretos trocando mensagens de descoberta (hello). Em seguida, ele empacota a lista de seus vizinhos e o custo de cada enlace num pacote de estado de enlace (Link State Packet, LSP) e o distribui para toda a rede por meio de inundação (flooding): cada roteador que recebe um LSP novo o retransmite para todas as suas interfaces, exceto aquela por onde ele chegou. Por fim, com uma cópia do LSP de cada roteador da rede em mãos, cada nó monta o grafo completo da topologia e roda Dijkstra a partir de si mesmo.

Como cada roteador enxerga a topologia inteira, o roteamento por estado de enlace converge mais rápido após uma falha e não sofre do problema de contagem ao infinito. Em compensação, exige mais memória (para guardar o mapa completo) e mais processamento (para rodar Dijkstra). OSPF (Open Shortest Path First) e IS-IS são os protocolos de estado de enlace mais usados hoje dentro de redes corporativas e de provedores.

🌐 BGP entre provedores

Dentro de uma única rede (um "sistema autônomo"), protocolos como OSPF cuidam do roteamento interno. Entre provedores diferentes, quem manda é o BGP, um protocolo de vetor de caminho que anuncia a rota completa de sistemas autônomos, não apenas um custo — assim cada provedor decide sozinho em quem confiar. Para consultar informações públicas de roteamento, veja o BGP Toolkit ou o RIPEstat; as rotas e atributos observados dependem do ponto de coleta e do momento.

🏷️ MPLS em backbones

Provedores usam rótulos MPLS justamente para ganhar o encaminhamento em O(1) do circuito virtual, enquanto ainda deixam o protocolo de roteamento (por exemplo OSPF) decidir qual caminho os rótulos devem seguir.

📶 CIDR e blocos de endereço

Em uma conexão residencial, é comum receber um único endereço IPv4 público — que pode estar compartilhado por CGNAT — e, quando há IPv6, um prefixo como /56 ou /64, conforme o provedor. Um /24 contém 256 endereços IPv4 e costuma ser um bloco de rede, não a alocação típica para uma residência.

🧭 traceroute

A ferramenta traceroute (ou tracert) estima, salto a salto, o caminho de encaminhamento observado a partir da origem. Ela não é um protocolo de roteamento nem identifica, sozinha, qual algoritmo calculou cada rota. Dentro de um sistema autônomo, protocolos como OSPF podem contribuir para as rotas; entre sistemas autônomos, o BGP troca informações de alcançabilidade e políticas influenciam a escolha. Resultados podem variar por caminho de volta, balanceamento e filtros de ICMP.

    Mão na massa

    Exemplos de código

    Os três trechos abaixo, em Python, implementam os mecanismos centrais deste capítulo: busca por prefixo mais longo em uma tabela de encaminhamento, roteamento por vetor de distância (Bellman-Ford distribuído) e roteamento por estado de enlace (Dijkstra sobre o grafo completo).

    1. Busca por prefixo mais longo (longest prefix match)
    def longest_prefix_match(endereco: str, tabela: dict[str, str]) -> str | None:
    """
    endereco: string de bits, ex. "01011010"
    tabela: mapa {prefixo: interface}, ex. {"010": "Norte", "0": "Oeste"}
    Retorna a interface associada ao prefixo mais longo que combina com o endereco.
    """
    melhor_prefixo = None
    for prefixo, interface in tabela.items():
        if endereco.startswith(prefixo):
            if melhor_prefixo is None or len(prefixo) > len(melhor_prefixo):
                melhor_prefixo = prefixo
    return tabela[melhor_prefixo] if melhor_prefixo is not None else None

tabela = {"0": "Oeste", "010": "Norte", "0101101": "Sul"}
print(longest_prefix_match("01011010", tabela))  # "Sul" (prefixo mais especifico vence)
print(longest_prefix_match("01100000", tabela))  # "Oeste" (so o prefixo generico combina)
    2. Vetor de distância (Bellman-Ford distribuído)
    INFINITO = float("inf")

def inicializa_tabelas(topologia: dict[str, dict[str, int]]) -> dict[str, dict[str, tuple[int, str]]]:
    """Cada roteador comeca so conhecendo a si mesmo, com custo 0."""
    tabelas = {}
    for roteador in topologia:
        tabelas[roteador] = {roteador: (0, roteador)}
    return tabelas

def rodada_vetor_distancia(topologia, tabelas):
    """Uma rodada de troca de vetores entre vizinhos diretos."""
    mudou = False
    novas_tabelas = {r: dict(tabelas[r]) for r in tabelas}

    for roteador, vizinhos in topologia.items():
        for vizinho, custo_enlace in vizinhos.items():
            for destino, (custo_vizinho, _) in tabelas[vizinho].items():
                novo_custo = custo_vizinho + custo_enlace
                custo_atual, _ = novas_tabelas[roteador].get(destino, (INFINITO, None))
                if novo_custo < custo_atual:
                    novas_tabelas[roteador][destino] = (novo_custo, vizinho)
                    mudou = True

    return novas_tabelas, mudou

topologia = {
    "A": {"B": 1, "C": 4},
    "B": {"A": 1, "D": 2},
    "C": {"A": 4, "D": 1},
    "D": {"B": 2, "C": 1},
}

tabelas = inicializa_tabelas(topologia)
for rodada in range(1, 10):
    tabelas, mudou = rodada_vetor_distancia(topologia, tabelas)
    if not mudou:
        print(f"Convergiu na rodada {rodada}")
        break

print(tabelas["A"])  # {'A': (0,'A'), 'B': (1,'B'), 'C': (4,'C'), 'D': (3,'B')}
    3. Estado de enlace (Dijkstra sobre a topologia completa)
    import heapq

def dijkstra(grafo: dict[str, dict[str, int]], origem: str) -> dict[str, tuple[int, list[str]]]:
    """
    grafo: {no: {vizinho: custo}}
    Retorna, para cada destino, (custo total, caminho completo).
    Equivale ao que um roteador faz apos aprender toda a topologia via LSPs.
    """
    distancias = {no: INFINITO for no in grafo}
    caminhos = {no: [] for no in grafo}
    distancias[origem] = 0
    caminhos[origem] = [origem]

    fila = [(0, origem)]
    visitados = set()

    while fila:
        custo_atual, no_atual = heapq.heappop(fila)
        if no_atual in visitados:
            continue
        visitados.add(no_atual)

        for vizinho, custo_enlace in grafo[no_atual].items():
            novo_custo = custo_atual + custo_enlace
            if novo_custo < distancias[vizinho]:
                distancias[vizinho] = novo_custo
                caminhos[vizinho] = caminhos[no_atual] + [vizinho]
                heapq.heappush(fila, (novo_custo, vizinho))

    return {no: (distancias[no], caminhos[no]) for no in grafo}

INFINITO = float("inf")
grafo = {
    "E": {"B": 1, "C": 1, "D": 1},
    "B": {"E": 1, "A": 1, "C": 1},
    "C": {"E": 1, "B": 1},
    "D": {"E": 1, "A": 1},
    "A": {"B": 1, "D": 1},
}

for destino, (custo, caminho) in dijkstra(grafo, "E").items():
    print(f"E -> {destino}: custo {custo}, caminho {' -> '.join(caminho)}")

Protocolos seguros: ssh, TLS e DNSSEC

No Capítulo 8 você viu as ferramentas: cifras, hashes, assinaturas e Diffie-Hellman. Aqui elas viram protocolos de verdade. O ssh substitui o telnet, o TLS protege a web e o e-mail, e o DNSSEC assina as respostas do DNS. Em todos, os detalhes fazem a diferença: a ordem de uma lista, um número de sequência, um resumo assinado.

Apresentação

Da criptografia aos protocolos

Um protocolo seguro precisa negociar algoritmos sem que um atacante escolha os mais fracos, autenticar o outro lado, combinar chaves e proteger cada mensagem contra leitura, alteração e repetição. O livro mostra como três protocolos resolvem isso: o ssh, para acesso remoto; o TLS, para qualquer aplicação sobre TCP; e o DNSSEC, para as respostas do DNS.

Objetivos de aprendizagem

  • Explicar por que o telnet foi substituído pelo ssh e como o ssh negocia algoritmos sem permitir ataques de rebaixamento.
  • Descrever como o cliente ssh confia na chave do servidor, como as chaves de sessão são derivadas e o que é um HMAC.
  • Acompanhar o handshake do TLS 1.2, comparar as trocas RSA e DHE_RSA e explicar o sigilo futuro.
  • Explicar como o protocolo de registro detecta registros alterados, repetidos ou apagados, e o que o TLS 1.3 mudou (1-RTT, 0-RTT).
  • Calcular a dificuldade do envenenamento de cache do DNS e seguir a cadeia de confiança do DNSSEC, inclusive nas respostas negativas (NSEC).

Antes de começar

Revise o Capítulo 8 (Eve, Mallory, chave pública, hashes e Diffie-Hellman) e a mensagem DNS do Capítulo 9. O capítulo cobre as seções 3.7 a 3.9 do livro (pág. 169–185 do PDF). Os resumos e assinaturas das simulações são simplificados: mostram o mecanismo, mas não têm segurança.

Cada pergunta vale 10 pontos se acertada na primeira tentativa (5 depois). Os desafios das simulações valem de 10 a 15 pontos. Ao concluir tudo de um conceito, você ganha a medalha dele.

Conceito 1

Login remoto: telnet

1. Contextualização

Nos anos 1960 e 1970, um computador central era usado por vários terminais ligados por linhas seriais ou modems. Acessar computadores remotos foi uma das primeiras motivações para criar redes (pág. 169 do PDF).

2. Explicação

O protocolo mais simples para isso é o telnet (RFC 854). Ele roda sobre TCP, na porta 23, numa conexão bidirecional: vão os caracteres digitados pelo usuário e voltam as saídas dos programas no servidor, com algumas exceções, como caracteres de controle do terminal. O conjunto de caracteres padrão é o ASCII; a RFC 5198 permite Unicode.

O problema é que tudo vai em claro: nome de usuário, senha e comandos. Qualquer um que escute a rede, como a Eve do Capítulo 8, captura as senhas, e há programas que automatizam isso. Por isso o telnet quase não é mais usado: foi substituído pelo ssh (pág. 169 do PDF).

4. Prática

Qual é o principal problema do telnet?

5. Fixação

  • telnet: TCP, porta 23, caracteres em claro nos dois sentidos.
  • Quem escuta a rede captura senhas e comandos.
Conceito 2

ssh: negociando os algoritmos

1. Contextualização

Algoritmos criptográficos envelhecem: um que hoje é seguro pode ser quebrado daqui a alguns anos. Um protocolo seguro precisa permitir trocar de algoritmo, e isso abre uma porta para o atacante.

2. Explicação

O secure shell (ssh) foi criado por T. Ylönen em meados dos anos 1990 contra a escuta do telnet. A versão original era livre; depois o autor criou uma empresa, e outros programadores continuaram uma versão de código aberto, o OpenSSH. Hoje o ssh também transfere arquivos e cria túneis (pág. 169 do PDF).

O ssh roda direto sobre TCP. A primeira mensagem de cada lado é uma linha ASCII com a versão do protocolo e do programa, útil para depurar. Depois vem a SSH_MSG_KEX_INIT, que negocia quatro tipos de algoritmo (pág. 170 do PDF):

  • troca de chaves, cifra, MAC (código de autenticação de mensagem) e compressão.

Para cada tipo, o cliente manda uma lista ordenada dos que aceita, o preferido primeiro, e o servidor compara com a sua; a IANA mantém a lista de nomes. A negociação permite evoluir: um cliente atualizado anuncia um algoritmo novo como preferido, mesmo que o servidor ainda não o conheça. Para a compressão, os dois podem anunciar none.

Complemento
A regra exata está na RFC 4253, seção 7.1: vale o primeiro algoritmo da lista do cliente que também está na lista do servidor. A ordem do servidor não importa. Se não houver algoritmo em comum, a conexão falha.

O perigo é o ataque de rebaixamento (downgrade). Um cliente aceita uma cifra preferida, com chaves de 128 bits, e uma antiga, de 48 bits, mantida por compatibilidade. Se Mallory apagar a preferida da lista do cliente, o servidor escolhe a antiga, mais fácil de quebrar. O ssh se defende assim: o servidor assina um hash de todas as mensagens da troca, inclusive as listas. Se Mallory mexeu numa delas, o hash que o cliente calcula, com o que ele enviou, não bate com o que o servidor assinou, com o que ele recebeu (pág. 171 do PDF).

4. Prática

O cliente envia [chacha20, aes128-ctr, aes256-gcm]; o servidor aceita [aes256-gcm, aes128-ctr]. Qual cifra é escolhida?

5. Fixação

  • Linhas de versão, depois KEX_INIT com listas ordenadas para quatro tipos de algoritmo.
  • Agilidade de algoritmos é necessária, mas abre espaço para o rebaixamento.
  • Defesa: assinar um hash de todas as mensagens da negociação.
Conceito 3

ssh: a chave do servidor, as chaves de sessão e as mensagens

1. Contextualização

No Capítulo 8, você viu que um Diffie-Hellman sem autenticação cai diante de Mallory. Como o cliente ssh sabe que está falando com o servidor certo, se o ssh nem usa certificados?

2. Explicação

Com Diffie-Hellman, a troca de chaves do ssh funciona assim (pág. 170 do PDF):

  • o cliente sorteia a e envia A = ga mod p;
  • o servidor sorteia b, envia B = gb mod p, calcula K = Ab mod p e assina com a sua chave privada hash(VC || VS || KEX_INITC || KEX_INITS || chave pública do servidor || A || B || K), em que V são as linhas de versão e KEX_INIT as mensagens de negociação de cada lado;
  • o cliente calcula K = Ba mod p e confere a assinatura.

Nota
No livro, os cálculos de K estão trocados: o servidor calcularia K = Ba e o cliente K = Ab (pág. 170 do PDF). Cada lado só conhece o próprio segredo, então o servidor usa o seu b sobre o A do cliente, e o cliente usa o seu a sobre o B do servidor, como acima. O livro também troca a descrição de VClient e VServer: VC é a linha de versão do cliente (RFC 4253, seção 8).

O servidor não manda certificado. O ssh supõe que o cliente guarda as chaves públicas dos poucos servidores que usa. Na primeira conexão, o cliente mostra a impressão digital (fingerprint) da chave, que o administrador pode publicar, e o usuário decide se aceita. Se depois a chave recebida não coincidir com a guardada, o aviso é forte: pode ser Mallory no meio, um servidor invadido ou apenas um servidor reinstalado com chave nova (pág. 170–171 do PDF). Um registro DNS também pode publicar a impressão digital (RFC 4255).

Nota do livro
Chaves de uso único (pág. 171 do PDF). O ssh não usa K diretamente. Com a função de hash negociada, ele deriva seis chaves: uma para cifrar e uma para autenticar em cada sentido, e uma para inicializar a cifra (IV) em cada sentido. Nunca se usa a mesma chave para dois fins: se cliente e servidor cifrassem com a mesma chave, um atacante poderia devolver ao cliente dados que ele próprio cifrou.

Depois disso, as mensagens seguem o Binary Packet Protocol (RFC 4253, pág. 171–172 do PDF): tamanho (sem contar o MAC e o próprio campo), tamanho do enchimento, dados (comprimidos, se for o caso), pelo menos 4 bytes de enchimento aleatório para completar o bloco da cifra e o MAC. O MAC é calculado sobre um contador de mensagens, que não é transmitido mas é contado nas duas pontas, e a mensagem em claro: mac = MAC(chave, número_de_sequência || mensagem).

Nota do livro
HMAC (RFC 2104, pág. 172 do PDF). Um MAC ingênuo, H(K, dados), não é seguro. Os protocolos da Internet usam o HMAC, que funciona com qualquer hash H: H[K ⊕ opad, H(K ⊕ ipad, dados)], em que ipad é o byte 0x36 repetido, opad é o byte 0x5C repetido e ⊕ é o ou exclusivo. É mais resistente do que H(K, dados) a alguns ataques, como você viu no Capítulo 8.

Nota
O livro diz que o SHA-1 usa blocos de 20 bytes e que ipad e opad têm 20 bytes (pág. 172 do PDF). O SHA-1 produz um resumo de 20 bytes, mas processa blocos de 64 bytes, e é esse o tamanho de ipad, de opad e da chave completada com zeros (RFC 2104, seção 2). O mesmo vale para o SHA-256. O exemplo de código 1 confere isso com o módulo hmac do Python.

Para autenticar o usuário, o ssh aceita nome e senha, que agora vão dentro do canal cifrado, e dois mecanismos de chave pública: o usuário guarda a sua chave pública no servidor e assina uma mensagem com a privada; ou, entre hosts que confiam uns nos outros, como os de um laboratório, o computador onde Alice já entrou assina uma mensagem confirmando isso, e o outro aceita sem pedir a senha de novo (pág. 172 do PDF).

4. Prática

Primeira conexão a um servidor ssh: aparece a impressão digital da chave. O que fazer?

5. Fixação

  • Diffie-Hellman assinado pelo servidor; o cliente guarda a chave do servidor (sem certificado).
  • Chave diferente da guardada = aviso forte: Mallory, invasão ou reinstalação.
  • Seis chaves derivadas; cada mensagem tem enchimento e MAC com número de sequência; HMAC.
Conceito 4

TLS: onde ele entra e como começa

1. Contextualização

O ssh resolve o login remoto. Mas a web, o e-mail e muitas outras aplicações também precisam de segurança. Em vez de cada uma inventar a sua, existe uma camada comum.

2. Explicação

O Transport Layer Security começou com o nome Secure Socket Layer (SSL), que muita gente ainda usa. Ele serve a qualquer aplicação que use o transporte confiável e roda sobretudo sobre TCP (há variantes para SCTP e para UDP, o DTLS). O TLS cifra e autentica as SDUs da aplicação; o TCP entrega esse fluxo cifrado com confiabilidade. Usam TLS o HTTP (o HTTPS), o SMTP, o POP, o IMAP e protocolos proprietários (pág. 172 do PDF).

Há duas formas de começar uma sessão TLS (pág. 173 do PDF):

  1. Uma porta dedicada para a versão "sobre TLS" do protocolo. Funciona, mas gasta duas portas por aplicação:
    AplicaçãoPorta TCPPorta TLS
    POP3110995
    IMAP143993
    NNTP119563
    HTTP80443
    FTP21990
  2. Uma mensagem especial na porta normal. No SMTP, o servidor anuncia 250-STARTTLS em resposta ao EHLO; o cliente envia STARTTLS, o servidor responde 220 Ready to start TLS, e a sessão TLS começa ali mesmo (RFC 3207).

A sessão tem duas fases: o handshake, que negocia os parâmetros e as chaves, e a transferência de dados, em que tudo vai cifrado e autenticado. O livro, e este capítulo, tratam do caso da web: o TLS começa logo depois da conexão TCP.

4. Prática

Qual é a desvantagem de usar uma porta dedicada para a versão com TLS?

Em que porta um cliente de e-mail acessa o IMAP direto sobre TLS?

5. Fixação

  • TLS (ex-SSL): cifra e autentica as SDUs da aplicação, sobre TCP.
  • Porta dedicada (443, 993, 995…) ou STARTTLS na porta normal.
  • Handshake, depois dados cifrados.
Conceito 5

O handshake do TLS 1.2

1. Contextualização

Antes do primeiro byte da página, o navegador e o servidor precisam concordar nos algoritmos, o navegador precisa ter certeza de que fala com o site certo, e os dois precisam combinar chaves que Eve e Mallory não conheçam.

2. Explicação

Esses são os três objetivos do handshake (pág. 173 do PDF). Em resumo: o cliente propõe um nonce aleatório; o servidor responde com o seu nonce e um certificado; o cliente gera um segredo, cifra-o com a chave pública do servidor e manda um Finished com um MAC de todas as mensagens; o servidor manda o seu Finished; e os registros cifrados começam. Em detalhe (pág. 174–176 do PDF):

  • ClientHello: a versão (1.2 e 1.3 estão em uso; as anteriores, sendo abandonadas), 32 bytes aleatórios, a lista ordenada de suítes (ao contrário do ssh, o TLS negocia combinações prontas de algoritmos), a compressão (desligada na prática, por causa de ataques) e as extensões.
  • ServerHello: a versão e a suíte escolhidas, os 32 bytes do servidor e um Session Id, usado para retomar a sessão depois.
  • Certificate: a cadeia de certificados que liga o nome do domínio à chave pública do servidor, validada com as chaves das autoridades raiz que o cliente já tem (a infraestrutura de chave pública). Os certificados são codificados em ASN.1.
  • ServerKeyExchange, se a troca de chaves precisar, e ServerHelloDone.
Nota do livro
Server Name Indication (RFC 6066, pág. 174–175 do PDF). Na extensão SNI, o cliente diz no ClientHello o nome do servidor que quer. É o mesmo motivo do Host: do HTTP (Capítulo 10): um servidor TLS hospeda vários sites e precisa saber qual certificado apresentar. Sem o SNI, cada site com TLS precisaria de um endereço IP próprio.

O livro compara duas trocas de chaves (pág. 175 do PDF):

  • RSA: o cliente sorteia 48 bytes, cifra-os com a chave pública do certificado e os envia no ClientKeyExchange; o servidor decifra com a privada. Não há ServerKeyExchange.
  • DHE_RSA: Diffie-Hellman efêmero. O servidor manda os seus parâmetros no ServerKeyExchange, assinados com a chave privada RSA, e o cliente responde com a sua parte no ClientKeyExchange.

A diferença aparece contra Terrence, que gravou seis meses de tráfego do servidor de Bob e depois obtém a chave privada dele. Com RSA, ele decifra todas as sessões gravadas. Com DHE_RSA, ele consegue se passar pelo servidor nas sessões futuras, mas não decifra as passadas.

Nota do livro
Sigilo futuro (Perfect Forward Secrecy, pág. 175–176 do PDF). Um protocolo tem PFS se as chaves de sessões passadas continuam seguras mesmo que a chave privada do servidor vaze. DHE_RSA tem; RSA não. Como o DHE é caro, as implementações preferem ECDHE_RSA ou ECDHE_ECDSA, com curvas elípticas.

Para fechar, cada lado manda ChangeCipherSpec (a partir daqui, cifro) e Finished, a primeira mensagem cifrada, com um resumo de todo o handshake. É ele que confirma que ninguém alterou as mensagens anteriores (pág. 176 do PDF).

Nota do livro
Suítes (pág. 176 do PDF). O nome diz tudo: TLS_DHE_RSA_WITH_AES_128_GCM_SHA256 é troca DHE_RSA, AES de 128 bits no modo GCM para cifrar e SHA-256. NULL indica "nenhum algoritmo": TLS_ECDH_RSA_WITH_NULL_SHA não cifra nada. A lista oficial é mantida pela IANA.

Conceito 6

O protocolo de registro

1. Contextualização

Com as chaves combinadas, os dados viajam cifrados. Cifrar impede Eve de ler; mas e se Mallory repetir, apagar ou alterar um pedaço?

2. Explicação

Depois do handshake, os dados vão em registros, com chaves diferentes para cifrar e para autenticar, todas derivadas do segredo comum (RFC 5246). Cada registro tem quatro campos (pág. 176 do PDF):

  • Type: application data (dados cifrados, o mais comum), handshake, change_cipher_spec ou alert;
  • Protocol Version: versão maior e menor;
  • Length: no máximo 16 384 bytes;
  • os dados cifrados.

No método do exemplo do livro, o TLS primeiro calcula um HMAC sobre o número de sequência, o cabeçalho e o texto em claro: MAC(SeqNum, Header, PlainText). O número de sequência aumenta a cada registro e é contado nas duas pontas, sem ser transmitido. É ele que barra a repetição de registros (pág. 177 do PDF).

Nota do livro
MAC e depois cifra, ou cifra e depois MAC? (pág. 177 do PDF). Calcular o MAC e cifrar dados e MAC juntos obriga o receptor a decifrar dados possivelmente alterados antes de conferir a autenticidade. É melhor cifrar primeiro e calcular o MAC sobre o cifrado (encrypt-then-MAC, RFC 7366): o receptor confere o MAC antes de decifrar.

Nota
O livro diz que a versão atual do TLS usa "MAC e depois cifra" (pág. 177 do PDF). Isso vale para as suítes de bloco do TLS 1.2. O TLS 1.3, que o próprio livro descreve logo depois, só admite cifras AEAD (como AES-GCM e ChaCha20-Poly1305), que cifram e autenticam numa só operação (RFC 8446, seção 5.2). Na mesma página, "AEA" é um erro de digitação de AEAD.

3. Visualização

4. Prática

Como o receptor TLS percebe que Mallory repetiu um registro inteiro, com o MAC original?

5. Fixação

  • Registro: tipo, versão, tamanho (até 16 384 bytes) e dados.
  • MAC sobre número de sequência + cabeçalho + dados: barra alteração, repetição e remoção.
  • Encrypt-then-MAC é melhor; o TLS 1.3 usa AEAD.
Conceito 7

Melhorando o TLS: o TLS 1.3

1. Contextualização

No começo, só bancos e lojas usavam TLS. Com processadores mais rápidos, ele passou a proteger tudo. Pela telemetria do Firefox, 30% das páginas eram carregadas por HTTPS em 2013, e 80% em outubro de 2019 (pág. 177 do PDF).

2. Explicação

Medições mostram como o ecossistema mudou (pág. 177 do PDF): o RC4, usado em 60% das conexões em 2012, caiu a partir de 2015; as cifras AEAD passaram de 90%; o TLS 1.0 e 1.1 quase sumiram. Depois das revelações de Snowden, em 2013, a IETF declarou a vigilância em massa um ataque (RFC 7258) e passou a favorecer o sigilo futuro: desde 2014, o ECDHE supera o RSA, e em 2018 estava em mais de 90% das conexões. Iniciativas como o Let's Encrypt tornaram os certificados fáceis e gratuitos.

Os objetivos do TLS 1.3 eram simplificar, aumentar a segurança e a privacidade e reduzir a latência. Com TLS 1.2, baixar uma página custa no mínimo quatro RTTs: um para o TCP, um para ClientHello e ServerHello, um para a troca de chaves e um para o GET e a resposta (pág. 178 do PDF). O TLS 1.3:

  • tem só cinco suítes (RFC 8446), e todas as implementações devem aceitar TLS_AES_128_GCM_SHA256;
  • removeu todas as suítes sem sigilo futuro e a compressão;
  • exige Diffie-Hellman com poucos parâmetros possíveis. O cliente adivinha os parâmetros do servidor e já manda gc no ClientHello; o servidor responde com gs e, como já conhece a chave, manda cifrados o certificado, a assinatura do handshake e o Finished. O handshake leva um RTT; se o cliente adivinhou errado, o servidor indica os parâmetros certos e perde-se um RTT (pág. 178–179 do PDF);
  • permite o 0-RTT: se cliente e servidor já combinaram uma chave numa sessão anterior (uma chave pré-compartilhada, guardada em cache), o cliente manda dados cifrados junto com o ClientHello (pág. 179 do PDF).
Nota do livro
Empresas, privacidade e TLS (pág. 178 do PDF). Algumas empresas, sobretudo financeiras, queriam continuar decifrando o próprio tráfego TLS e pediram à IETF que mantivesse as suítes RSA, sem sigilo futuro. A IETF não aceitou; elas levaram a proposta ao ETSI, que adotou uma variante do TLS 1.3 sem sigilo futuro.

Na web, só o servidor apresenta certificado. Em redes corporativas, por exemplo em VPNs, o servidor pode pedir o do cliente com uma mensagem CertificateRequest; o cliente responde com o seu certificado e assina o handshake com a sua chave privada (pág. 180–181 do PDF).

Complemento
Os dados enviados em 0-RTT não têm proteção contra repetição: Mallory pode gravá-los e reenviá-los ao servidor. Por isso só devem ser usados para pedidos que possam ser repetidos sem dano, os idempotentes do Capítulo 10 (RFC 8446, seção 8). O TLS 1.0 e o 1.1 foram oficialmente abandonados em 2021 (RFC 8996).

3. Visualização

4. Prática

Por que o handshake do TLS 1.3 leva só um RTT?

O que o cliente precisa ter para enviar dados em 0-RTT?

5. Fixação

  • TLS 1.2: 4 RTTs até a resposta. TLS 1.3: 3. TLS 1.3 com 0-RTT: 2.
  • TLS 1.3: cinco suítes, todas com sigilo futuro e AEAD; sem compressão; certificado cifrado.
  • 0-RTT exige uma chave pré-compartilhada e só serve para pedidos idempotentes.
Conceito 8

Ataques ao DNS

1. Contextualização

As pessoas escolhem os servidores pelo nome. Se o DNS der uma resposta falsa, a conexão vai para o lugar errado, e isso já aconteceu várias vezes (pág. 181 do PDF).

2. Explicação

A RFC 3833 analisa as ameaças. O livro discute três (pág. 181–183 do PDF):

  1. Escuta: quem captura as consultas de Alice descobre os nomes que ela usa. O DNS original não se preocupava com isso.
  2. Homem no meio: Mallory, entre Alice e o resolvedor, troca as respostas. É difícil se o resolvedor está num datacenter protegido, mas fácil se Mallory controla o ponto de acesso Wi-Fi de Alice.
  3. Respostas forjadas, sem estar no caminho. Alice só aceita uma resposta cujo Identification, de 16 bits, case com uma consulta pendente. Mallory prevê um nome que Alice vai consultar e manda respostas falsas, cada uma com um ID, esperando que uma chegue antes da verdadeira. São só 65 536 IDs, e os enlaces rápidos de hoje dão conta. Ele também precisa forjar o endereço de origem, o que muitas redes ainda permitem. Se o alvo for o resolvedor de uma empresa ou provedor, com TTL longo, o estrago é grande.

Aumentar o campo de ID seria o ideal, mas a mensagem DNS não tem número de versão. A saída foi sortear também a porta UDP de origem de cada consulta: o atacante precisa acertar 16 bits de ID e 16 bits de porta, quase 232 combinações. A maioria das implementações faz isso (pág. 182 do PDF).

Há ainda o envenenamento pelos registros adicionais. Mallory controla mallory.net e atrai Alice a www.mallory.net, com spam ou um anúncio. Na resposta, o servidor dele inclui um AAAA para www.example.net apontando para um endereço dele. Se a biblioteca de Alice não conferir a resposta, o cache passa a mandar www.example.net para Mallory (pág. 182–183 do PDF).

Complemento
Hoje os resolvedores só aceitam registros adicionais do domínio pelo qual o servidor responde (a regra do bailiwick). Em 2008, Dan Kaminsky mostrou como forjar respostas em série para nomes inexistentes, o que tornou o sorteio da porta obrigatório (Wikipedia: DNS spoofing). Contra a escuta, o DNS sobre TLS (RFC 7858) e o DNS sobre HTTPS (RFC 8484), que o livro dizia ainda não estarem implantados, já vêm nos principais navegadores e sistemas.

3. Visualização

4. Prática

Por que não se aumentou simplesmente o campo Identification?

5. Fixação

  • Escuta, homem no meio e respostas forjadas.
  • Porta fixa: 216 combinações. Porta sorteada: cerca de 232.
  • Registros adicionais de outros domínios não devem ser aceitos.
Conceito 9

DNSSEC

1. Contextualização

Sortear portas dificulta o ataque, mas não prova que a resposta é verdadeira. Para isso é preciso assinar os registros.

2. Explicação

O DNSSEC (RFCs 4033, 4034 e 4035) usa chave pública para autenticar os registros. Cada zona tem um par de chaves, usado só para assinar. Os registros não são cifrados: o DNSSEC não dá confidencialidade. Ele cria quatro tipos de registro (pág. 183 do PDF):

  • DNSKEY: a chave pública da zona, com a identificação do algoritmo;
  • RRSIG: a assinatura de um conjunto de registros, com o algoritmo, a chave usada, o TTL original e o período de validade;
  • DS: um resumo da chave pública de uma zona filha, guardado na zona mãe;
  • NSEC: usado nas respostas negativas.

A confiança parte de uma âncora: a chave pública da raiz, obtida fora do DNS. Para validar www.example.org, a resolvedora confere a assinatura do DS de .org com a chave da raiz; confere que a DNSKEY de .org tem o resumo do DS; repete o processo para example.org; e, com a chave de example.org, valida a assinatura do AAAA. Basta haver uma cadeia DS → DNSKEY desde a âncora (pág. 183 do PDF).

As assinaturas podem ser feitas fora de linha, em outro computador. Isso evita que um atacante force o servidor a fazer muitas assinaturas (negação de serviço) e mantém a chave privada longe do servidor. Por isso o RRSIG guarda o TTL original, já que os caches diminuem o TTL, e um período de validade, que impede que assinaturas antigas fiquem para sempre nos caches quando a chave é trocada (pág. 183–184 do PDF).

E como provar que um nome não existe, sem assinar em tempo real? Respostas negativas são frequentes, e os resolvedores as guardam em cache (RFC 2308). O NSEC usa a ordem dos nomes: cada nome aponta para o seguinte, e o último volta ao primeiro. Na zona do livro, com alpha, beta e gamma, uma consulta por delta recebe "beta NSEC gamma", assinado: entre beta e gamma não há nada. Para pi, que viria depois de gamma, a prova é "gamma NSEC alpha" (pág. 184–185 do PDF).

Complemento
Na prática, cada zona costuma ter duas chaves: uma para assinar as próprias chaves (KSK), cujo resumo vai no DS, e outra para assinar os registros (ZSK). A âncora da raiz é publicada pela IANA. Seguindo os NSEC, qualquer um lista todos os nomes de uma zona; o NSEC3 (RFC 5155) usa resumos dos nomes para dificultar isso.

Pratique

Exercícios graduados

  1. Aquecimento: o cliente ssh envia, para MAC, [hmac-sha2-512, hmac-sha2-256, hmac-sha1]; o servidor aceita [hmac-sha1, hmac-sha2-256]. Qual é escolhido?
    Ver solução

    hmac-sha2-256: o primeiro da lista do cliente que o servidor aceita.

  2. Aquecimento: com RTT de 80 ms, quanto tempo leva até a resposta HTTP com TLS 1.2, com TLS 1.3 e com TLS 1.3 em 0-RTT?
    Ver solução

    4 × 80 = 320 ms; 3 × 80 = 240 ms; 2 × 80 = 160 ms.

  3. Intermediário: Mallory consegue enviar 4096 respostas falsas por consulta. Qual é a chance de sucesso numa consulta com porta fixa e com porta sorteada?
    Ver solução

    Porta fixa: 4096 / 65 536 = 1/16, cerca de 6%. Porta sorteada: 4096 / 232 ≈ 0,0001%.

  4. Intermediário: numa zona com os nomes ana, bia, caio e duda (todos em .example.org), qual NSEC prova que carla.example.org não existe? E zeca.example.org?
    Ver solução

    carla fica entre caio e duda: "caio NSEC duda". zeca vem depois de duda: "duda NSEC ana", o registro que dá a volta.

  5. Intermediário: por que o Finished do TLS precisa cobrir todas as mensagens do handshake, e não só as últimas?
    Ver solução

    Porque as primeiras mensagens, como o ClientHello com a lista de suítes, vão em claro e podem ser alteradas por Mallory para forçar uma suíte fraca (rebaixamento). Se o Finished resume tudo, qualquer alteração é detectada, como no hash assinado do ssh.

  6. Desafio: um servidor usa TLS 1.2 com troca RSA. A empresa grava todo o tráfego para auditoria e guarda a chave privada. Que propriedade de segurança está faltando, e o que mudaria com TLS 1.3?
    Ver solução

    Falta o sigilo futuro: quem tiver a chave privada (inclusive um invasor que a roube) decifra todo o tráfego gravado. O TLS 1.3 só tem trocas Diffie-Hellman efêmeras: a chave privada só assina, e o tráfego antigo não pode ser decifrado com ela. Foi por isso que algumas empresas pediram, sem sucesso, que a IETF mantivesse o RSA.

1. HMAC feito à mão

import hashlib, hmac

def hmac_a_mao(chave, dados, H=hashlib.sha256):
    B = H().block_size                                 # 64 bytes para SHA-1 e SHA-256
    if len(chave) > B:
        chave = H(chave).digest()
    chave = chave.ljust(B, b"\x00")                    # completa a chave até o tamanho do bloco
    ipad = bytes(b ^ 0x36 for b in chave)
    opad = bytes(b ^ 0x5C for b in chave)
    return H(opad + H(ipad + dados).digest()).hexdigest()

chave, msg = b"chave secreta", b"PAGUE 100 A BOB"
print("à mão:      ", hmac_a_mao(chave, msg))
print("módulo hmac:", hmac.new(chave, msg, hashlib.sha256).hexdigest())
print("SHA-1: bloco de", hashlib.sha1().block_size, "bytes, resumo de", hashlib.sha1().digest_size, "bytes")

# por que não basta H(chave + dados)? Um MAC ingênuo:
print("ingênuo:    ", hashlib.sha256(chave + msg).hexdigest())

2. Negociação do ssh e o rebaixamento

import hashlib

def negocia(cliente, servidor):
    """RFC 4253: vale o primeiro algoritmo da lista do cliente que o servidor também aceita."""
    for alg in cliente:
        if alg in servidor:
            return alg
    return None                                        # sem algoritmo em comum: a conexão falha

cliente = ["cifra-128", "cifra-48"]                    # o exemplo do livro: 128 bits preferida, 48 bits antiga
servidor = ["cifra-48", "cifra-128"]
print("negociado:", negocia(cliente, servidor))

# Mallory apaga a cifra forte da lista que o cliente enviou
recebida_pelo_servidor = ["cifra-48"]
print("com Mallory:", negocia(recebida_pelo_servidor, servidor))

# Defesa do ssh: o servidor assina um hash de TODAS as mensagens que viu, e o cliente compara com o que enviou
def resumo(*mensagens):
    return hashlib.sha256("|".join(",".join(m) for m in mensagens).encode()).hexdigest()[:16]

visto_pelo_servidor = resumo(recebida_pelo_servidor, servidor)
enviado_pelo_cliente = resumo(cliente, servidor)
print("hash do servidor:", visto_pelo_servidor)
print("hash do cliente: ", enviado_pelo_cliente)
print("ataque detectado:", visto_pelo_servidor != enviado_pelo_cliente)

3. Diffie-Hellman do ssh e as seis chaves

import hashlib, random

p, g = 4294967291, 5                                   # primo pequeno, só para o exemplo (o ssh usa 2048 bits ou curvas)
rnd = random.Random(7)
a = rnd.randrange(2, p - 1)                            # segredo do cliente
b = rnd.randrange(2, p - 1)                            # segredo do servidor
A = pow(g, a, p)                                       # o cliente envia A
B = pow(g, b, p)                                       # o servidor envia B
K_servidor = pow(A, b, p)                              # o servidor calcula com o SEU segredo b
K_cliente = pow(B, a, p)                               # o cliente calcula com o SEU segredo a
print("A =", A, " B =", B)
print("mesma chave K?", K_cliente == K_servidor)

# hash da troca: tudo o que foi negociado entra nele (versões, KEXINIT, chave do servidor, A, B, K)
H = hashlib.sha256(f"SSH-2.0-cliente|SSH-2.0-servidor|kexinit-c|kexinit-s|chave-pub-servidor|{A}|{B}|{K_cliente}".encode()).digest()
id_sessao = H

# RFC 4253, seção 7.2: seis chaves derivadas de K e H, uma para cada uso
usos = {"A": "IV cliente→servidor", "B": "IV servidor→cliente",
        "C": "cifra cliente→servidor", "D": "cifra servidor→cliente",
        "E": "MAC cliente→servidor", "F": "MAC servidor→cliente"}
for letra, uso in usos.items():
    chave = hashlib.sha256(str(K_cliente).encode() + H + letra.encode() + id_sessao).hexdigest()
    print(f"{letra} {uso:24} {chave[:16]}…")

4. A chance do envenenamento de cache

def chance_por_tentativa(respostas_falsas, porta_aleatoria):
    """Chance de uma das respostas falsas acertar o ID (e a porta) antes da resposta verdadeira."""
    espaco = 2**16 * (2**16 if porta_aleatoria else 1)
    return min(1.0, respostas_falsas / espaco)

def chance_em(tentativas, respostas_falsas, porta_aleatoria):
    p = chance_por_tentativa(respostas_falsas, porta_aleatoria)
    return 1 - (1 - p) ** tentativas                   # pelo menos um acerto em várias tentativas

for porta in (False, True):
    nome = "porta aleatória" if porta else "porta fixa     "
    for k in (100, 1000, 10000):
        print(f"{nome} k={k:5}: 1 tentativa {chance_por_tentativa(k, porta):.6f}  "
              f"100 tentativas {chance_em(100, k, porta):.6f}")

5. NSEC: provando que um nome não existe

def ordem_canonica(nome):
    """Ordem do DNSSEC (RFC 4034, seção 6.1): compara os rótulos da direita para a esquerda."""
    return list(reversed(nome.lower().rstrip(".").split(".")))

zona = ["alpha.example.org", "beta.example.org", "gamma.example.org"]   # o exemplo do livro
zona.sort(key=ordem_canonica)

# cada nome aponta para o seguinte; o último volta para o primeiro
nsec = {nome: zona[(i + 1) % len(zona)] for i, nome in enumerate(zona)}
for dono, proximo in nsec.items():
    print(f"{dono} NSEC {proximo}")

def prova_inexistencia(consulta):
    """Devolve o registro NSEC que cobre o nome consultado (ou None se o nome existe)."""
    if consulta in nsec:
        return None
    chave = ordem_canonica(consulta)
    for dono, proximo in nsec.items():
        depois_do_dono = ordem_canonica(dono) < chave
        antes_do_proximo = chave < ordem_canonica(proximo)
        ultimo = ordem_canonica(proximo) <= ordem_canonica(dono)        # o registro que dá a volta
        if (depois_do_dono and antes_do_proximo) or (ultimo and (depois_do_dono or antes_do_proximo)):
            return f"{dono} NSEC {proximo}"

for q in ["delta.example.org", "pi.example.org"]:
    print(q, "->", prova_inexistencia(q))

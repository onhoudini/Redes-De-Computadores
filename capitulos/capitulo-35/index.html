Prática: HTTP

Neste capítulo, você manda pedidos HTTP digitados à mão, descobre por que o cabeçalho Host é obrigatório, lê o que o curl troca com um servidor e calcula quanto cada versão do HTTP gasta em idas e voltas.

Exercícios sobre o HTTP

A seção 4.9 do livro tem exercícios com telnet e curl sobre o HTTP (pág. 314–315 do PDF). Os servidores desta página são simulados, com nomes de exemplo; os comandos para a rede real estão nas resoluções. O formato das atividades está explicado no Capítulo 27.

Objetivos de aprendizagem

  • Comparar o uso de conexões no HTTP/1.0, 1.1 e 2 e montar pedidos à mão, com e sem o cabeçalho Host.
  • Ler os cabeçalhos de um pedido e de uma resposta e explicar a negociação de conteúdo.

Antes de começar

Revise o HTTP do Capítulo 12 e o HTTP/2 e os caches do Capítulo 13. O capítulo cobre a seção 4.9 do livro (pág. 314–315 do PDF).

Cada atividade tem cinco etapas: Relembre, O que o livro pede, Experimente, Resolução comentada (fechada, para você tentar antes) e Fixação.

Cada pergunta vale 10 pontos se acertada na primeira tentativa (5 depois). Os desafios das simulações valem de 10 a 20 pontos. Ao concluir tudo de uma atividade, você ganha a medalha dela.

Atividade 1

HTTP/1.0, HTTP/1.1 e HTTP/2

1. Relembre

No HTTP/1.0, cada objeto usa uma conexão TCP nova. O HTTP/1.1 mantém a conexão aberta (persistente) e permite mandar vários pedidos sem esperar as respostas (pipelining). O HTTP/2 multiplexa vários pedidos e respostas numa só conexão. Veja as conexões persistentes no Capítulo 12 e o HTTP/2 no Capítulo 13.

2. O que o livro pede

A seção começa assim: uma diferença importante entre o HTTP/1.0, o HTTP/1.1 e o HTTP/2.0 é o uso que fazem das conexões de transporte; responda às três perguntas abaixo para confirmar que entendeu (pág. 314 do PDF).

Nota
As três perguntas não estão no PDF: eram exercícios interativos do INGInious. Esta atividade as substitui por uma conta de tempos de ida e volta, que não está no livro.

3. Experimente

4. Resolução comentada

Resolução (não está no livro) Abrir a resolução

Com n objetos: o HTTP/1.0, sem paralelismo, gasta 2 RTT por objeto (abertura da conexão e pedido), 2n ao todo. O HTTP/1.1 persistente abre uma vez e faz um pedido por RTT: 1 + n. Com pipelining ou HTTP/2, depois da página (1 + 1), os pedidos das imagens vão todos juntos: mais 1 RTT. Na prática, os navegadores também abrem várias conexões em paralelo no HTTP/1.x, e o TLS soma 1 ou 2 RTT por conexão (veja o Capítulo 16), o que torna ainda mais caro abrir uma conexão por objeto.

5. Fixação

Quantas conexões TCP o HTTP/2 usa para buscar uma página e as suas imagens num mesmo servidor?

Atividade 2

Testando um servidor web à mão

1. Relembre

Um pedido HTTP/1.x é texto: a linha de pedido (método, caminho e versão), os cabeçalhos e uma linha em branco. Vários sites podem dividir o mesmo endereço IP; o cabeçalho Host: diz qual deles o cliente quer. Veja o HTTP no Capítulo 12.

2. O que o livro pede

  1. Quem administra servidores web quer verificar se eles estão funcionando. Como o HTTP usa TCP na porta 80, o mais simples é abrir uma conexão nessa porta e ver se o servidor a aceita. Mas, como o HTTP/1.x é em ASCII, também é fácil baixar uma página e comparar com a esperada. Use telnet ou ncat para verificar se há um servidor web em www.computer-networking.info. (O pedido mínimo é GET / HTTP/1.0 seguido de CRLF e de uma linha em branco.)
  2. O HTTP/1.1, especificado na RFC 2616, obriga o cliente a incluir o cabeçalho Host: em todos os pedidos. O HTTP/1.0 não define esse cabeçalho, mas a maioria das implementações o aceita. Com telnet e curl, baixe a primeira página de https://www.computer-networking.info com e sem o cabeçalho Host:. Explique a diferença (pág. 314 do PDF).

Nota
O próprio livro avisa, em nota, que o site passou a usar HTTPS (porta 443). Um telnet comum não fala TLS: para a porta 443, use openssl s_client -connect www.computer-networking.info:443 ou o curl. A RFC 2616 foi substituída pela RFC 9110 e pela RFC 9112, que mantêm a regra do Host.

4. Resolução comentada

Resolução (não está no livro) Abrir a resolução
  • Q1: telnet www.computer-networking.info 80, depois GET / HTTP/1.0 e uma linha em branco. Hoje o servidor responde com um redirecionamento (301 ou 302) para o https, o que já prova que ele está no ar. Um script de monitoração faria o mesmo pedido e conferiria o código e parte do conteúdo.
  • Q3: com GET / HTTP/1.1 sem Host, um servidor conforme responde 400 Bad Request. Com HTTP/1.0 sem Host, ele responde com o site padrão daquele endereço, que pode não ser o pedido. Com o Host certo, vem a página do site. O motivo é a hospedagem virtual: vários sites no mesmo endereço IP, e só o Host os distingue.

Atividade 3

O que o curl manda e recebe

1. Relembre

Os cabeçalhos de um pedido dizem ao servidor quem pede e o que aceita; os da resposta descrevem o corpo (tipo, tamanho) e como guardá-lo em cache. Veja o HTTP no Capítulo 12 e os caches no Capítulo 13.

2. O que o livro pede

Em vez de telnet na porta 80, use uma ferramenta de linha de comando como o curl. Com a opção --trace-ascii arquivo, ele guarda tudo o que trocou com o servidor. Qual versão do HTTP o seu curl usa? Você consegue explicar os cabeçalhos que o curl põe no pedido? E os da resposta (pág. 314 do PDF)?

Nota
No PDF, as opções do curl aparecem com um traço só (-trace-ascii, -http2), efeito da tipografia, que junta os dois hífens. No terminal, elas têm dois: --trace-ascii, --http2.

3. Experimente

4. Resolução comentada

Resolução (não está no livro) Abrir a resolução

Rode curl --trace-ascii t.txt http://www.computer-networking.info/ e abra t.txt. Para http://, o curl usa HTTP/1.1; para https://, costuma negociar HTTP/2 durante o TLS. No pedido, ele põe Host, User-Agent e Accept. Na resposta, procure a linha de estado, Date, Server, Content-Type, Content-Length (ou Transfer-Encoding: chunked, quando o tamanho não é conhecido de antemão) e os cabeçalhos de cache. Os valores exatos dependem do servidor e do dia.

5. Fixação

Atividade 4

Pedindo a página noutro idioma

1. Relembre

Na negociação de conteúdo, o cliente diz o que prefere (idiomas, tipos, codificações), com pesos q de 0 a 1, e o servidor escolhe a melhor versão que tem. Veja o HTTP no Capítulo 12.

2. O que o livro pede

O cabeçalho Accept-Language permite indicar o idioma preferido. Por exemplo, curl -HAccept-Language:en http://www.google.be pede a página em inglês. O Google dá uma página diferente em francês (fr) e em valão (wa)? E www.uclouvain.be (como a página é grande, use diff para comparar as versões) (pág. 315 do PDF)?

3. Experimente

4. Resolução comentada

Resolução (não está no livro) Abrir a resolução

O servidor compara o pedido com as versões que tem, em ordem de peso, e devolve Content-Language e Vary: Accept-Language (o Vary avisa os caches de que a resposta depende desse cabeçalho). Sites grandes costumam ter francês; valão, quase nunca, e aí o servidor cai num padrão. Muitos sites hoje escolhem o idioma por cookie, pela URL ou pela localização, e ignoram o Accept-Language. Compare em casa com curl -s -H "Accept-Language: fr" URL > fr.html, o mesmo com wa e diff fr.html wa.html.

5. Fixação

Que cabeçalho da resposta avisa os caches de que a página muda conforme o idioma pedido?

Atividade 5

Tamanho, IPv6, HTTP/2 e páginas espalhadas

1. Relembre

Uma página web costuma juntar objetos de vários servidores: imagens num servidor estático, bibliotecas e fontes em CDNs, anúncios e contadores de terceiros. Cada nome precisa de uma consulta DNS e, em geral, de uma conexão. Veja os caches e CDNs no Capítulo 13.

2. O que o livro pede

  1. Compare o tamanho das páginas http://www.yahoo.com e http://www.google.com baixando-as com o curl.
  2. A extensão ipvfoo do Chrome mostra se um site usa IPv6 ou IPv4 e quais sites foram contatados para montar uma página. Alguns sites se espalham por dezenas de servidores. Você acha um?
  3. Alguns sites são alcançáveis por IPv4 e IPv6, outros só por IPv4. Com as opções -6 e -4 do curl, verifique se www.computer-networking.info é alcançável pelos dois e se o site da sua universidade já tem IPv6.
  4. O curl tem opções para forçar uma versão do HTTP: --http0.9, --http1.0, --http1.1 e --http2. Com a última, verifique se o seu site favorito aceita HTTP/2.0 (pág. 315 do PDF).

Nota
O livro termina a seção com capturas de pacotes de várias versões do HTTP para analisar no Wireshark; elas eram do INGInious e não fazem parte do PDF.

Resolução (não está no livro) Abrir a resolução
  • Q5: curl -sL URL | wc -c conta os bytes da página (o -L segue redirecionamentos). O HTML principal é só o começo: as imagens e os scripts vêm em pedidos separados.
  • Q6: no exemplo da simulação, a página fala com 6 servidores, 2 deles só por IPv4. Portais de notícias reais passam facilmente de dezenas, por causa de anúncios e rastreadores.
  • Q7: curl -6 -I URL e curl -4 -I URL: se o -6 falhar com "Could not resolve host" ou sem rota, o site (ou a sua rede) não tem IPv6. dig -t AAAA nome mostra se o nome tem endereço IPv6.
  • Q8: curl -sI --http2 https://site e veja a primeira linha: "HTTP/2 200" confirma o HTTP/2. Sem TLS, o curl tentaria o HTTP/2 em texto claro, que quase nenhum servidor aceita.

Pratique

Exercícios graduados

  1. Básico: Escreva o menor pedido HTTP/1.1 válido para a página inicial de www.example.com.
    Ver solução

    GET / HTTP/1.1, Host: www.example.com e uma linha em branco, cada linha terminada em CRLF.

  2. Intermediário: Uma página tem 10 objetos e o RTT é de 40 ms. Quanto tempo leva com HTTP/1.0 e com HTTP/1.1 persistente, contando só os RTTs?
    Ver solução

    HTTP/1.0: 2 × 10 = 20 RTT = 800 ms. HTTP/1.1 persistente: 1 + 10 = 11 RTT = 440 ms.

  3. Intermediário: Um pedido traz Accept-Language: de, fr;q=0.5. O servidor tem en e fr. Que versão ele devolve?
    Ver solução

    fr: não há alemão, e fr é a próxima preferência com peso maior que zero.

  4. Desafio: Por que o HTTP/2 com TLS 1.3 ainda gasta pelo menos 2 RTT antes da primeira resposta, e o que o TLS 1.3 com 0-RTT muda?
    Ver solução

    1 RTT para abrir o TCP e 1 para o handshake TLS 1.3, que já leva o pedido junto da sua conclusão: a resposta chega no fim do segundo RTT. Com 0-RTT, numa conexão retomada, o pedido vai no primeiro voo do TLS, e só sobra o RTT do TCP (veja o Capítulo 16).

Exemplos de código

Três trechos em Python que rodam no navegador, sem acessar a rede. Edite, execute e resolva os desafios de cada bloco.

1. Hospedagem virtual e o cabeçalho Host

# Um servidor HTTP com dois sites no mesmo endereço (hospedagem virtual).
SITES = {"www.example.com": "<html><title>Example Com</title></html>",
         "docs.example.org": "<html><title>Documentação</title></html>"}

def servidor(pedido):
    linhas = pedido.split("\r\n")
    metodo, caminho, versao = linhas[0].split()
    cabecalhos = {}
    for l in linhas[1:]:
        if not l:
            break                                    # linha em branco: fim dos cabeçalhos
        nome, valor = l.split(":", 1)
        cabecalhos[nome.strip().lower()] = valor.strip()
    host = cabecalhos.get("host")
    if versao == "HTTP/1.1" and host is None:
        return "HTTP/1.1 400 Bad Request\r\n\r\n"
    corpo = SITES.get(host, SITES["www.example.com"])   # sem Host conhecido: o site padrão
    return f"HTTP/1.1 200 OK\r\nContent-Length: {len(corpo.encode())}\r\n\r\n{corpo}"

for pedido in ["GET / HTTP/1.0\r\n\r\n",
               "GET / HTTP/1.1\r\n\r\n",
               "GET / HTTP/1.1\r\nHost: docs.example.org\r\n\r\n"]:
    resposta = servidor(pedido)
    print(repr(pedido.split("\r\n")[0]), "->", resposta.split("\r\n")[0], "|", resposta.split("\r\n\r\n")[1])

2. RTTs em cada versão

# Tempos de ida e volta para buscar uma página com n objetos (só RTTs, sem tempo de transmissão).
def rtts(versao, n, tls=0):
    """tls: RTTs a mais por conexão (1 no TLS 1.3, 2 no TLS 1.2)."""
    if versao == "HTTP/1.0":                  # uma conexão por objeto, uma de cada vez
        return n * (2 + tls)
    if versao == "HTTP/1.1":                  # conexão persistente, um pedido por vez
        return 1 + tls + n
    return 1 + tls + 1 + (1 if n > 1 else 0)  # HTTP/2: a página, depois todas as imagens juntas

RTT = 50
for n in (1, 5, 20):
    linha = ", ".join(f"{v}: {rtts(v, n) * RTT} ms" for v in ("HTTP/1.0", "HTTP/1.1", "HTTP/2"))
    print(f"{n:2} objetos -> {linha}")
print("com TLS 1.3, 5 objetos:", {v: rtts(v, 5, tls=1) * RTT for v in ("HTTP/1.0", "HTTP/1.1", "HTTP/2")})

3. Negociação de idioma

# Negociação de idioma: Accept-Language com pesos q (RFC 9110, seção 12.5.4).
def preferencias(cabecalho):
    prefs = []
    for item in cabecalho.split(","):
        partes = [p.strip() for p in item.split(";")]
        q = 1.0
        for p in partes[1:]:
            if p.startswith("q="):
                q = float(p[2:])
        if partes[0] and q > 0:
            prefs.append((q, partes[0].lower()))
    return [tag for q, tag in sorted(prefs, key=lambda x: -x[0])]

def escolhe(cabecalho, disponiveis, padrao):
    for tag in preferencias(cabecalho):
        for d in disponiveis:
            if tag in (d, "*") or d.split("-")[0] == tag:
                return d
    return padrao

DISP = ["en", "fr", "nl"]
for cab in ["fr", "wa", "wa, fr;q=0.8, en;q=0.9", "de;q=0.5, nl;q=0.4"]:
    print(f"{cab!r:28} -> {escolhe(cab, DISP, 'en')}")

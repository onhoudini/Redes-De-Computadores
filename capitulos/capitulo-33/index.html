Prática: a camada de aplicação

Neste capítulo, você usa um dig simulado para seguir uma resolução desde os servidores raiz, observa o TTL caindo no cache e calcula a chance de um atacante acertar o identificador de uma consulta.

Apresentação

Exercícios sobre o DNS

A seção 4.7 do livro tem exercícios com o dig sobre o DNS (pág. 312–313 do PDF). Como o navegador não manda consultas DNS de verdade, o dig desta página responde com os 13 servidores raiz reais e, abaixo deles, uma árvore de nomes ilustrativa; os comandos para rodar o dig real estão nas resoluções. O formato das atividades está explicado no Capítulo 27.

Objetivos de aprendizagem

  • Usar o dig para consultar resolvedores e servidores autoritativos e seguir a delegação desde a raiz.
  • Explicar o TTL, as preferências dos registros MX e a importância de um identificador aleatório.

Antes de começar

Revise o DNS do Capítulo 10, os registros MX do Capítulo 11 e os ataques ao DNS do Capítulo 17. O capítulo cobre a seção 4.7 do livro (pág. 312–313 do PDF).

Cada atividade tem cinco etapas: Relembre, O que o livro pede, Experimente, Resolução comentada (fechada, para você tentar antes) e Fixação.

Cada pergunta vale 10 pontos se acertada na primeira tentativa (5 depois). Os desafios das simulações valem de 10 a 20 pontos. Ao concluir tudo de uma atividade, você ganha a medalha dela.

Atividade 1

O dig e os resolvedores

1. Relembre

Uma mensagem DNS leva uma pergunta (nome e tipo) e volta com as seções de resposta, autoridade e informação adicional. Os tipos mais comuns são A (IPv4), AAAA (IPv6), NS (servidor de nomes) e MX (relay de e-mail). Quem pergunta em nome da aplicação é o resolvedor, que percorre a hierarquia e guarda as respostas. Veja a mensagem DNS e os registros no Capítulo 10.

2. O que o livro pede

O livro usa o dig, instalado na maioria dos sistemas Unix/Linux, na forma dig @servidor -t tipo nome: servidor é o endereço ou o nome de um servidor DNS ou resolvedor; tipo é o tipo de registro pedido; nome é o nome completo (FQDN). A opção +trace mostra todas as consultas de uma resolução recursiva (pág. 312 do PDF).

  1. Quais são os endereços IP dos resolvedores que o seu dig usa? (No Linux, a seção Description da página de manual do dig diz onde ele encontra essa lista.)
  2. Quais são os servidores de nomes responsáveis pelo domínio de topo info? Dá para consultá-los por IPv6?
  3. Qual é o endereço IPv6 de www.computer-networking.info? Que tipo de consulta o dig manda para obtê-lo (pág. 312 do PDF)?

3. Experimente

Dados ilustrativos: o TLD .example é reservado para exemplos (RFC 2606), e os endereços são de documentação. Os servidores raiz são os reais.

4. Resolução comentada

Resolução (não está no livro) Abrir a resolução
  • Q1: sem @servidor, o dig usa os resolvedores listados em /etc/resolv.conf, nas linhas nameserver. A linha ;; SERVER: no fim da saída mostra qual respondeu.
  • Q2: dig -t NS info lista os servidores do TLD. Se a seção adicional trouxer registros AAAA deles, dá para consultá-los por IPv6, com dig @endereço-IPv6 … ou dig -6. Na simulação, faça o mesmo com -t NS example.
  • Q3: o tipo AAAA: dig -t AAAA www.computer-networking.info. A resposta real muda com o tempo; rode em casa para ver a de hoje.

5. Fixação

O que indica a flag aa no cabeçalho da resposta?

Atividade 2

Seguindo a delegação desde a raiz

1. Relembre

Um servidor que não é autoritativo para um nome responde com uma referência: os registros NS da zona filha na seção de autoridade e, na adicional, os endereços desses servidores. Seguindo as referências desde a raiz, chega-se ao servidor autoritativo. Veja os registros de recurso no Capítulo 10.

2. O que o livro pede

  1. Sem parâmetros, o dig consulta um servidor raiz e obtém os nomes de todos eles. Por motivos técnicos, há só 13 servidores raiz, listados também no arquivo named.root da InterNIC. Quais são os endereços IPv6 deles?
  2. Suponha uma rede sem resolvedor, em que você precisa fazer a consulta à mão desde a raiz: pergunte a um servidor raiz pelos servidores (NS) do TLD org; depois, a um deles pelos de root-servers.org; continue até o servidor responsável por www.root-servers.org. Qual é o tempo de vida associado ao endereço IPv6 encontrado (pág. 312 do PDF)?

3. Experimente

Faça a Q5 com www.rede.example: comece por um servidor raiz, depois a.nic.example e, por fim, ns1.rede.example.

Atividade 3

O TTL e as respostas que mudam

1. Relembre

Cada registro tem um TTL: por quantos segundos um resolvedor pode guardá-lo antes de perguntar de novo. Enquanto guarda, o resolvedor responde do cache, com o TTL diminuindo. Veja os registros e o TTL no Capítulo 10.

2. O que o livro pede

Faça a mesma análise para um site popular, como www.google.com. Qual é o tempo de vida do endereço IPv6? Fazendo a mesma consulta várias vezes, você recebe sempre a mesma resposta? Por que um tempo de vida é associado às respostas DNS (pág. 313 do PDF)?

3. Experimente

4. Resolução comentada

Resolução (não está no livro) Abrir a resolução

Sites muito grandes usam TTLs curtos, de minutos, e respostas que variam: o endereço pode depender de onde está o resolvedor, e a ordem dos endereços gira para espalhar os clientes. Consultas repetidas ao mesmo resolvedor mostram o TTL caindo, porque a resposta vem do cache. O TTL existe para equilibrar duas coisas: um TTL longo poupa consultas e deixa as respostas rápidas; um curto permite trocar os endereços (por manutenção, falha ou distribuição de carga) sem esperar muito.

Atividade 4

Registros MX e preferências

1. Relembre

Um registro MX diz que servidor recebe o e-mail de um domínio, com uma preferência: o remetente tenta primeiro o de menor número e só passa ao seguinte se ele falhar. Veja os registros MX no Capítulo 11.

2. O que o livro pede

Use o dig para achar os relays de e-mail dos domínios uclouvain.be e student.uclouvain.be. Qual é o TTL desses registros? Explique as preferências dos registros MX. Há mais informação sobre eles na RFC 5321 (pág. 313 do PDF).

3. Experimente

rede.example e aluno.rede.example fazem o papel de uclouvain.be e student.uclouvain.be, com dados ilustrativos.

4. Resolução comentada

Resolução (não está no livro) Abrir a resolução

A RFC 5321 (seção 5.1) manda o remetente ordenar os MX pela preferência, do menor para o maior, e sortear a ordem entre os de mesma preferência. Dois MX com 10 dividem a carga; um com 20 é reserva. Um subdomínio pode ter MX próprios, como aluno.rede.example, que prefere o seu relay (5) e usa mx1.rede.example só como reserva (50). Os domínios reais do livro mudaram desde 2021; rode dig -t MX uclouvain.be para ver os de hoje.

Atividade 5

O identificador da consulta

1. Relembre

O cabeçalho DNS tem um identificador de 16 bits que o cliente escolhe e o servidor copia na resposta. Um atacante que forja respostas precisa acertar esse identificador antes de a resposta verdadeira chegar: é o envenenamento de cache. Veja os ataques ao DNS no Capítulo 17.

2. O que o livro pede

  1. Na saída do dig, a seção de cabeçalho mostra o identificador usado na consulta (no exemplo do livro, 25718). O seu dig gera identificadores aleatórios?
  2. Um dig, e principalmente um resolvedor como o bind ou o unbound, sempre confere se a resposta traz o mesmo identificador da consulta. Por que isso é tão importante? Imagine um atacante que forja respostas para associar www.bigbank.com ao seu próprio endereço. Como ele atacaria uma implementação que manda consultas com o mesmo identificador sempre, com o identificador somado de 1 a cada consulta, ou com identificadores aleatórios (pág. 313 do PDF)?

3. Experimente

4. Resolução comentada

Resolução (não está no livro) Abrir a resolução
  • Q8: rode o dig algumas vezes e compare os ids: implementações atuais sorteiam.
  • Q9: conferir o identificador descarta respostas que não correspondem a nenhuma consulta. Com id fixo, o atacante põe esse id em todas as respostas forjadas; com id incremental, basta ver (ou provocar) uma consulta para prever a próxima. Nos dois casos, ele só precisa chegar antes do servidor verdadeiro. Com id aleatório, cada resposta forjada acerta com chance 1/65 536; com 100 respostas antes da verdadeira, cerca de 0,15%. Como o atacante pode repetir o ataque muitas vezes, os resolvedores atuais também sorteiam a porta UDP de origem, o que multiplica as possibilidades (complemento).

Atividade 6

DNS sobre UDP e sobre TCP

1. Relembre

Com UDP, a consulta vai num datagrama e a resposta volta noutro. Com TCP, a abertura em três vias vem antes, e cada mensagem DNS leva na frente dois bytes de comprimento. Veja o DNS no Capítulo 10 e a abertura do TCP no Capítulo 20.

2. O que o livro pede

O DNS pode rodar sobre UDP e sobre TCP. A maioria dos servidores prefere UDP, que gasta menos recursos; o TCP é útil quando se espera uma resposta grande. Compare time dig +tcp e time dig consultando um servidor raiz. A resposta chega mais rápido por TCP ou por UDP (pág. 313 do PDF)?

Nota
O livro termina a seção mencionando três exercícios com capturas de pacotes das resoluções de www.example.com, www.google.com e www.computer-networking.info, para pôr em ordem. As capturas eram do INGInious e não fazem parte do PDF.

3. Experimente

4. Resolução comentada

Resolução (não está no livro) Abrir a resolução

Por UDP, a resposta chega em cerca de um RTT; por TCP, em cerca de dois, porque a conexão precisa ser aberta antes da consulta. Com o servidor raiz a 25 ms, algo como 25 ms contra 50 ms, mais o processamento. O TCP compensa quando a resposta não cabe num datagrama UDP (o servidor marca a resposta como truncada, com a flag TC, e o cliente repete por TCP) e nas transferências de zona.

Pratique

Exercícios graduados

  1. Básico: Que comando dig pergunta ao servidor raiz a.root-servers.net, por IPv6, quais são os servidores do TLD org?
    Ver solução

    dig @2001:503:ba3e::2:30 -t NS org. A resposta é uma referência: os NS de org na seção de autoridade e os endereços deles na adicional.

  2. Intermediário: Um registro tem TTL de 3600 s. Um resolvedor o guardou há 25 minutos. Que TTL ele mostra numa resposta do cache?
    Ver solução

    3600 − 25 × 60 = 2100 s.

  3. Intermediário: Um domínio tem os MX 30 a.exemplo, 10 b.exemplo e 20 c.exemplo. Em que ordem um servidor SMTP tenta entregar?
    Ver solução

    b.exemplo (10), depois c.exemplo (20) e, por fim, a.exemplo (30): a menor preferência primeiro.

  4. Desafio: Com identificadores aleatórios de 16 bits, quantas respostas forjadas um atacante precisa mandar para ter 50% de chance de acertar?
    Ver solução

    n tal que 1 − (1 − 1/65 536)n = 0,5: n ≈ 45 426. Se a porta de origem também for sorteada (mais 16 bits), seriam quase 3 bilhões.

Exemplos de código

Três trechos em Python que rodam no navegador, sem acessar a rede. Edite, execute e resolva os desafios de cada bloco.

1. Montando uma consulta DNS

import struct

# O cabeçalho DNS tem 12 bytes: id, flags e quatro contadores (pág. 134-135 do PDF, Capítulo 10).
def consulta(ident, nome, tipo, recursao=True):
    flags = 0x0100 if recursao else 0          # bit RD (recursion desired)
    cab = struct.pack("!HHHHHH", ident, flags, 1, 0, 0, 0)
    qname = b"".join(bytes([len(p)]) + p.encode("ascii") for p in nome.rstrip(".").split(".")) + b"\x00"
    TIPOS = {"A": 1, "NS": 2, "MX": 15, "AAAA": 28}
    return cab + qname + struct.pack("!HH", TIPOS[tipo], 1)   # classe IN = 1

def le_flags(flags):
    nomes = {15: "qr", 10: "aa", 9: "tc", 8: "rd", 7: "ra"}
    return [n for bit, n in nomes.items() if flags >> bit & 1]

msg = consulta(25718, "www.rede.example", "AAAA")       # o id do exemplo do livro (pág. 313)
print(len(msg), "bytes:", msg.hex(" "))
print("id em hexadecimal:", hex(25718))
print("flags 0x8180 =", le_flags(0x8180))                # uma resposta típica de resolvedor

2. Resolução iterativa e cache

# Resolução iterativa com dados ilustrativos (TLD .example, RFC 2606) e um cache com TTL.
ZONAS = {
    ".": {"filhos": {"example.": "a.nic.example."}},
    "example.": {"filhos": {"rede.example.": "ns1.rede.example.", "video.example.": "ns.video.example."}},
    "rede.example.": {"rr": {("www.rede.example.", "AAAA"): (3600, ["2001:db8:10::80"]),
                             ("rede.example.", "MX"): (3600, ["10 mx1.rede.example.", "10 mx2.rede.example.", "20 reserva.video.example."])}},
    "video.example.": {"rr": {("video.example.", "AAAA"): (300, ["2001:db8:a::1", "2001:db8:a::2", "2001:db8:a::3"])}},
}
cache, relogio = {}, 0

def resolve(nome, tipo):
    chave = (nome, tipo)
    if chave in cache and cache[chave][0] > relogio:
        expira, dados = cache[chave]
        return dados, expira - relogio, ["cache"]
    zona, caminho = ".", []
    while True:
        caminho.append(zona)
        z = ZONAS[zona]
        filho = next((f for f in z.get("filhos", {}) if nome == f or nome.endswith("." + f)), None)
        if filho:                               # referência: desce um nível
            zona = filho
            continue
        ttl, dados = z["rr"][chave]
        cache[chave] = (relogio + ttl, dados)
        return dados, ttl, caminho

print(resolve("www.rede.example.", "AAAA"))
relogio = 100
print(resolve("www.rede.example.", "AAAA"))
print(resolve("video.example.", "AAAA"))

3. A chance do envenenamento

import random

# Quantas respostas forjadas acertam o identificador de 16 bits? (4.7.1 Q9)
def chance(n, bits=16):
    return 1 - (1 - 2 ** -bits) ** n

for n in (1, 100, 1000, 10000):
    print(f"{n:6} respostas forjadas: {chance(n):.4%}")

# Experimento: 2000 consultas; contra cada uma, o atacante manda 100 respostas com ids sorteados
rng = random.Random(42)
envenenadas = 0
for _ in range(2000):
    verdadeiro = rng.randrange(65536)
    forjados = {rng.randrange(65536) for _ in range(100)}
    envenenadas += verdadeiro in forjados
print("consultas envenenadas:", envenenadas, "de 2000 (esperado: cerca de", round(2000 * chance(100), 1), ")")

# Complemento: sortear também a porta de origem soma cerca de 16 bits de incerteza
print(f"id + porta (32 bits), 1000 respostas: {chance(1000, 32):.8%}")

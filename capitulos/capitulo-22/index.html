A camada de rede: IPv6 e ICMPv6

No Capítulo 2 você viu como uma rede encaminha pacotes. Aqui está o protocolo de rede que o livro escolhe para a Internet: o IPv6, com endereços de 128 bits, um cabeçalho simples, fragmentação só na origem, mensagens de controle ICMPv6 e hosts que configuram o próprio endereço sem ajuda de ninguém.

Apresentação

De rede em rede, até o destino

O objetivo da camada de rede é permitir que hosts ligados a redes diferentes troquem informação passando por sistemas intermediários, os roteadores. A unidade de informação é o pacote (pág. 213 do PDF). O livro descreve o IPv6; o IPv4 aparece só nas comparações.

Objetivos de aprendizagem

  • Distinguir os tipos de enlace (ponto a ponto, LAN, NBMA) e o papel da MTU.
  • Ler a estrutura de um endereço IPv6 e aplicar a regra do maior prefixo.
  • Reconhecer os endereços especiais (link-local, loopback, ULA, multicast).
  • Ler o cabeçalho IPv6, seguir a cadeia de extensões e calcular a fragmentação.
  • Explicar o ICMPv6, o Path MTU Discovery, a descoberta de vizinhos e o SLAAC.

Antes de começar

Revise o encaminhamento, o TTL e a MTU do Capítulo 2 e a notação IPv6 do Capítulo 9. O capítulo cobre a seção 3.14 do livro (pág. 213–236 do PDF). Os exemplos usam os endereços do livro ou o bloco de documentação 2001:db8::/32.

Cada pergunta vale 10 pontos se acertada na primeira tentativa (5 depois). Os desafios das simulações valem de 10 a 15 pontos. Ao concluir tudo de um conceito, você ganha a medalha dele.

Conceito 1

A camada de rede e os tipos de enlace

1. Contextualização

Antes de olhar o IP, o livro olha para baixo: o que a camada de enlace oferece à camada de rede? A resposta muda de uma tecnologia para outra, e o IP precisa conviver com todas.

2. Explicação

O livro trata dos enlaces sem conexão, os mais usados, de três tipos (Figs. 38–40, pág. 214–215 do PDF):

  • Ponto a ponto: dois sistemas ligados diretamente, como no PPP (RFC 1661). O serviço pode ser não confiável, sobre fibras e pares trançados com poucos erros, ou confiável, com retransmissões, comum em redes sem fio.
  • LAN (rede local): qualquer par de dispositivos troca quadros diretamente. Cada dispositivo tem um endereço de enlace único, em geral um endereço MAC de 48 bits, e há endereços de broadcast (todos) e multicast (um grupo).
  • NBMA (Non-Broadcast Multi-Access): liga vários dispositivos como uma LAN, mas só oferece unicast, sem broadcast nem multicast.

Nenhum enlace manda quadros de tamanho ilimitado, e há mais de uma dúzia de tamanhos máximos diferentes. A camada de rede tem de lidar com essa heterogeneidade (pág. 215 do PDF).

3. Visualização

Baseado nas Figs. 39 e 40 e no texto das págs. 214–215 do PDF.

4. Prática

Uma rede liga vários dispositivos, cada um com seu endereço, mas não oferece broadcast. Que tipo é?

5. Fixação

  • Ponto a ponto, LAN (unicast, broadcast, multicast) e NBMA (só unicast).
  • Cada enlace tem um tamanho máximo de quadro.
Conceito 2

Endereçamento IPv6 e o maior prefixo

1. Contextualização

No fim dos anos 1980, os roteadores tinham uma CPU e até 1 MB de memória, e as tabelas cresciam depressa. Em 1990, previa-se o fim dos endereços classe B do IPv4 para 1994 (pág. 215 do PDF).

2. Explicação

As soluções de curto prazo foram o CIDR e o NAT (vários hosts dividindo um endereço IPv4 público). Em paralelo, a IETF pediu propostas para o IP da próxima geração (IPng) e escolheu a SIPP; como a versão 5 já era de um protocolo experimental, o sucessor do IPv4 virou o IPv6: endereços de 128 bits, cabeçalho simples para hardware, autoconfiguração e segurança (pág. 215 do PDF).

Nota do livro
O tamanho do endereço (pág. 216 do PDF). Todos concordavam que 32 bits eram pouco. A SIPP propunha 64 bits (4 bilhões de vezes o IPv4, cabendo nos registradores dos processadores de 64 bits); a TUBA reaproveitava os endereços de 20 bytes do ISO CLNP. 128 bits foi o meio-termo: cerca de 3,4 × 1038 endereços, ou 6,67 × 1023 por metro quadrado da Terra, contra 8 por quilômetro quadrado no IPv4.

Um endereço unicast identifica uma interface (um host com Ethernet e WiFi tem dois). Ele tem três partes (Fig. 41, pág. 217 do PDF):

  1. o prefixo global de roteamento, do provedor dono do bloco;
  2. o identificador de sub-rede, um cliente ou uma rede desse provedor;
  3. o identificador de interface, hoje sempre de 64 bits.

Os roteadores não podem guardar uma rota por host; os endereços são distribuídos em blocos, conforme a posição na rede, para que uma rota cubra muitos hosts. A IANA distribui blocos de 2000::/3 aos registros regionais (RIPE, ARIN, AfriNIC…), que os repassam aos provedores, que os repassam aos clientes. Tamanhos típicos: /32 para um provedor, /48 para uma empresa, /56 para sites pequenos, /64 para um usuário (pág. 218 do PDF). Endereços independentes do provedor (PI) acompanham a empresa se ela trocar de provedor; os agregáveis pelo provedor (PA) precisam ser trocados.

Com vários blocos aninhados, um roteador pode ter várias rotas para um destino. Desde a RFC 1519, vale a do maior prefixo. A Belnet anuncia 2001:6a8::/32, que inclui a UCLouvain (2001:6a8:3080::/48); se a UCLouvain contratar outro provedor, quem conhece as duas rotas usa a /48, mais específica. A rota ::/0 casa com tudo: é a rota padrão (pág. 218–219 do PDF).

4. Prática

Na tabela do livro, por onde sai um pacote para 2001:6a8:3080::1234?

Qual é o tamanho típico do bloco IPv6 de uma empresa?

5. Fixação

  • 128 bits: prefixo global, sub-rede e identificador de interface de 64 bits.
  • Distribuição hierárquica: IANA → RIR → provedor → cliente; PI e PA.
  • Maior prefixo vence; ::/0 é a rota padrão.
Conceito 3

Endereços especiais e multicast

1. Contextualização

Nem todo endereço IPv6 serve para atravessar a Internet. Alguns só valem dentro de um enlace, outros dentro de uma empresa, outros apontam para um grupo inteiro de receptores.

2. Explicação

  • ULA, Unique Local Unicast (fc00::/7, RFC 4193): para empresas que usam IPv6 sem se ligar à Internet, como os endereços privados do IPv4 (RFC 1918), mas com muito mais espaço.
  • ::1: o loopback, uma interface lógica sempre ativa. ::: o endereço não especificado, usado como origem por quem ainda não tem endereço.
  • Link-local (fe80::/10, Fig. 42): fe80::/64 seguido do identificador de interface. Serve para falar dentro do enlace, inclusive na autoconfiguração; nenhum roteador encaminha pacotes com esses endereços (pág. 219 do PDF).
Nota do livro
Todo host IPv6 tem vários endereços (pág. 220 do PDF): pelo menos o link-local e, em geral, um global por interface. Todas as pilhas IPv6 precisam lidar com isso.

Um endereço multicast identifica um grupo: a rede entrega cada pacote a todos os membros, e os roteadores replicam o pacote só onde há membros. O endereço começa com 8 bits 1 (ff), seguidos de 4 bits de flags (permanente ou temporário), 4 bits de escopo, que limita até onde o pacote vai, e 112 bits de grupo (Fig. 43). Todos os hosts estão no grupo ff02::1, e todos os roteadores no ff02::2 (pág. 220–221 do PDF).

Complemento
Os valores do escopo estão na RFC 4291, seção 2.7: 1 = interface, 2 = enlace, 4 = administração, 5 = site, 8 = organização e e = global. Por isso ff02::1 fica no enlace e ff0e::… é global. A arquitetura de endereços que o livro cita (RFC 3513) foi substituída pela RFC 4291.

Além de unicast e multicast, o IPv6 tem endereços anycast (pág. 216 do PDF). O glossário do livro define anycast como o modo em que a informação sai de uma origem e chega a um receptor de um grupo (pág. 393 do PDF): o mesmo endereço é configurado em vários lugares, e o pacote vai para um só deles.

Complemento
Pela RFC 4291, seção 2.6, um endereço anycast sai do espaço unicast e não tem formato próprio: é um endereço unicast atribuído a várias interfaces, e o roteamento entrega o pacote à mais próxima segundo as métricas. É assim que vários servidores raiz do DNS atendem, com o mesmo endereço, em dezenas de países.

3. Visualização

4. Prática

Um roteador encaminha para outra rede um pacote com destino fe80::1?

Um pacote enviado a um endereço anycast chega a quem?

5. Fixação

  • Unicast (uma interface), multicast (todos do grupo) e anycast (um do grupo).
  • ULA (fc00::/7), loopback (::1), não especificado (::) e link-local (fe80::/10).
  • Multicast: ff + flags + escopo + grupo; ff02::1 todos os hosts, ff02::2 todos os roteadores.
Conceito 4

O cabeçalho IPv6 e as extensões

1. Contextualização

Um roteador de alta capacidade processa milhões de pacotes por segundo. Cada campo a menos no cabeçalho é trabalho a menos em cada pacote.

2. Explicação

O cabeçalho IPv6 tem 40 bytes e, além dos endereços de origem e destino, seis campos (Fig. 44, pág. 221 do PDF):

  • Version (4 bits): 6;
  • Traffic Class (8 bits): o tipo de serviço, incluindo os bits ECT e CE do ECN (Capítulo 21);
  • Flow Label (20 bits): pensado para marcar pacotes de um mesmo fluxo; o uso ainda é incerto (RFC 6437);
  • Payload Length (16 bits): o tamanho do que vem depois do cabeçalho, até 65 535 bytes;
  • Next Header (8 bits): o que vem a seguir, por exemplo 6 (TCP), 17 (UDP), 58 (ICMPv6) ou uma extensão;
  • Hop Limit (8 bits): decrementado por roteador; evita que pacotes circulem para sempre.

Não há checksum: o enlace e o transporte já verificam erros, e recalcular um checksum em cada roteador custaria caro para pouco ganho (no IPv4, cada roteador atualiza o checksum ao decrementar o TTL). O Next Header permite uma cadeia de cabeçalhos: Hop-by-Hop Options (processado por roteadores e hosts), Destination Options, Routing, Fragment, e os do IPsec, AH e ESP (pág. 222–223 do PDF).

O Hop-by-Hop usa o formato tipo-tamanho-valor; os dois bits mais altos do tipo dizem o que faz um nó que não conhece a opção: 00 pula, 01 descarta, 10 e 11 descartam e avisam a origem por ICMP. Exemplos: o jumbograma, para pacotes de mais de 65 535 bytes (RFC 2675), e o router alert (RFC 2711). O Routing Header tipo 0, que indicava roteadores a visitar, foi retirado da especificação por problemas de segurança (RFC 5095, pág. 223 e 227 do PDF).

Nota
O livro diz que o campo Hdr Ext Len do Hop-by-Hop dá o tamanho do cabeçalho de opções em bytes (pág. 223 do PDF). Ele é medido em unidades de 8 bytes, sem contar os primeiros 8: Hdr Ext Len = 0 significa um cabeçalho de 8 bytes (RFC 8200, seção 4.3). A RFC 8200 substituiu a RFC 2460, citada pelo livro.

3. Visualização

4. Prática

Por que o cabeçalho IPv6 não tem checksum?

Um pacote IPv6 fragmentado tem qual valor no Next Header do cabeçalho principal?

5. Fixação

  • 40 bytes: versão, classe, rótulo de fluxo, tamanho da carga, próximo cabeçalho, limite de saltos e endereços.
  • Sem checksum; extensões encadeadas pelo Next Header.
Conceito 5

Fragmentação no IPv6

1. Contextualização

A MTU de uma interface é o maior pacote, com cabeçalho, que ela consegue mandar. O IPv6 permite pacotes de 64 KB, mas a Ethernet aceita 1500 bytes, e o caminho pode ter enlaces ainda menores (Fig. 47, pág. 224 do PDF).

2. Explicação

EnlaceMTU (pág. 224 do PDF)
Ethernet1500
WiFi2272
ATM (AAL5)9180
802.15.4102 ou 81
Token Ring4464
FDDI4352

No IPv4, hosts e roteadores fragmentavam; fragmentar nos roteadores se mostrou caro. No IPv6, só a origem fragmenta. Um roteador que recebe um pacote grande demais o descarta e avisa a origem por ICMPv6 (pág. 224 do PDF). Cada fragmento é um pacote IPv6 com um cabeçalho de fragmento de 8 bytes (Next Header 44, Fig. 48):

  • Next Header: o que vem depois (por exemplo, UDP);
  • Fragment Offset (13 bits): a posição dos dados no pacote original, em unidades de 8 bytes;
  • M (more): 1 em todos os fragmentos menos o último;
  • Identification (32 bits): a que pacote o fragmento pertence, sem repetir para o mesmo destino durante um MSL.

O destino junta os fragmentos com a mesma identificação, usa o offset para posicioná-los e o fragmento com M = 0 para saber o tamanho total. Se algum faltar quando um temporizador expirar, descarta todos (pág. 225–226 do PDF).

Nota
O pseudo-código de fragmentação do livro (pág. 225–226 do PDF) tem três erros: avança com payload[maxpayload+1:], o que pula um byte a cada fragmento (o certo é payload[maxpayload:]); põe plen=mtu, mas o Payload Length não conta o cabeçalho IPv6 de 40 bytes e precisa contar o de fragmento; e calcula os dados por fragmento como múltiplo de 8 de mtu − 40, esquecendo os 8 bytes do cabeçalho de fragmento. O exemplo de código 4 traz a versão corrigida.

Nota do livro
Compressão de cabeçalhos (pág. 226–227 do PDF). Em enlaces lentos, com pacotes pequenos como os de voz, os 40 bytes do IPv6 pesam. Há compressão genérica no enlace, compressão dos cabeçalhos IP e TCP aproveitando a repetição entre pacotes do mesmo fluxo (RFC 5795) e codificações compactas do IPv6 para redes como a 802.15.4 (RFC 4944).

3. Visualização

4. Prática

O que faz um roteador IPv6 que recebe um pacote maior que a MTU do enlace de saída?

5. Fixação

  • Só a origem fragmenta; cada fragmento leva um cabeçalho de 8 bytes (Next Header 44).
  • Offset em unidades de 8 bytes; M = 0 no último; Identification de 32 bits.
Conceito 6

ICMPv6

1. Contextualização

Quando um roteador descarta um pacote, a origem precisa saber por quê: não há rota? O pacote é grande demais? Os saltos acabaram?

2. Explicação

O ICMPv6 (RFC 4443) viaja dentro do IPv6 com Next Header 58. A mensagem tem um tipo de 8 bits, um código e um checksum de 16 bits, e o corpo traz uma cópia do pacote com problema (Fig. 51). As mensagens de erro (pág. 227–228 do PDF):

  • 1, Destination Unreachable, com os códigos 0 (sem rota), 1 (proibido por um firewall), 2 (fora do escopo da origem), 3 (endereço inalcançável) e 4 (porta inalcançável, enviado pelo destino);
  • 2, Packet Too Big, com a MTU do enlace de saída;
  • 3, Time Exceeded: código 0, o Hop Limit chegou a zero; código 1, o destino não conseguiu remontar os fragmentos;
  • 4, Parameter Problem: campo errado no cabeçalho (código 0) ou Next Header/opção desconhecidos (1 e 2).

Com o Packet Too Big, a origem descobre a maior MTU do caminho: é o Path MTU Discovery (RFC 1981). O TCP aproveita isso para ajustar o MSS e não depender de fragmentação: perder um fragmento obriga a retransmitir o segmento inteiro, e a remontagem traz problemas de desempenho e de segurança (pág. 228–229 do PDF).

As mensagens informativas são o Echo Request e o Echo Reply (RFC 4443), usados pelo ping6 para testar se um destino responde. Todo host deveria responder a um Echo Request, mas, depois dos problemas de segurança que afetaram as pilhas TCP/IP, muitas implementações permitem desligar essa resposta (pág. 229 do PDF). O exemplo do livro: 

#ping6 www.ietf.org
PING6(56=40+8+8 bytes) 2001:6a8:3080:2:3403:bbf4:edae:afc3 --> 2001:1890:123a::1:1e
16 bytes from 2001:1890:123a::1:1e, icmp_seq=0 hlim=49 time=156.905 ms
16 bytes from 2001:1890:123a::1:1e, icmp_seq=1 hlim=49 time=155.618 ms
…
16 bytes from 2001:1890:123a::1:1e, icmp_seq=7 hlim=49 time=155.869 ms
^C
--- www.ietf.org ping6 statistics ---
8 packets transmitted, 8 packets received, 0.0% packet loss
round-trip min/avg/max/std-dev = 155.325/155.810/156.905/0.447 ms

Cada linha é um Echo Reply: o icmp_seq é o número de sequência do pedido, o hlim é o Hop Limit com que a resposta chegou e o time é o RTT. Os 56 bytes são 40 de cabeçalho IPv6, 8 de cabeçalho ICMPv6 e 8 de dados.

O traceroute6 mostra o caminho até o destino. Ele usa as mensagens Time Exceeded: manda um pacote com Hop Limit 1, depois com 2, e assim por diante, e cada roteador que descarta um pacote por Hop Limit esgotado devolve um ICMPv6 com o cabeçalho e os primeiros bytes do pacote. Você já viu essa ideia no Capítulo 2. No exemplo do livro, são três medidas por salto (pág. 229–230 do PDF):

Complemento
Os nomes dos roteadores contam o caminho: a rede da UCLouvain (saltos 1 e 2), a Belnet (3 e 4), a rede acadêmica europeia GÉANT em Amsterdã e Copenhague (5 e 6), a Telia (7 a 9) e a rede do 2001:1890::/32, onde estava o servidor da IETF (10 a 12). Nota do livro
Limitação de taxa do ICMP (pág. 230 do PDF). Os chips que encaminham pacotes na velocidade da linha não geram ICMP: chamam a CPU do roteador, bem mais lenta. Para protegê-la, os roteadores limitam a taxa de mensagens ICMP, e nem todo pacote com erro gera uma. Pelo mesmo motivo, opções Hop-by-Hop são desaconselhadas.

Complemento
O exemplo do livro usa um enlace de 1200 bytes, e o próprio livro o chama de acadêmico: o IPv6 exige que todo enlace aceite pelo menos 1280 bytes (RFC 8200, seção 5). Se um firewall bloquear os Packet Too Big, o Path MTU Discovery falha em silêncio: pacotes grandes somem e os pequenos passam. Por isso não se deve filtrar todo o ICMPv6.

Conceito 7

A sub-rede IPv6: MAC, EUI-64 e descoberta de vizinhos

1. Contextualização

A maioria dos hosts está numa LAN, como uma Ethernet ou uma rede WiFi. Para mandar um pacote ao vizinho, o host precisa do endereço MAC dele. E, para começar, precisa do próprio endereço IPv6.

2. Explicação

Cada interface de LAN tem um endereço MAC único, gravado no hardware, e o quadro leva MAC de origem, MAC de destino e a indicação do protocolo de rede. O broadcast entrega a todos, inclusive a quem não fala IPv6; o multicast só a quem se inscreveu no grupo, e é o que o IPv6 usa (pág. 230–231 do PDF).

O EUI-64 transforma o MAC de 48 bits num identificador de interface de 64 bits: inverte o bit U/L (universal ou local) e insere ff:fe no meio (Figs. 52–53, RFC 4291, apêndice A). O host A do livro, de MAC 00:23:45:67:89:ab, ganha o link-local fe80::223:45ff:fe67:89ab (pág. 231–232 do PDF).

Nota
O livro diz que os endereços MAC são distribuídos em blocos de 220 (pág. 231 do PDF). O identificador da empresa (OUI) tem 24 bits, e cada bloco tem 224 endereços, cerca de 16 milhões, como o próprio livro diz na pág. 259 (Wikipedia: OUI).

Para achar o MAC de um vizinho, o IPv6 usa o Neighbor Discovery Protocol (RFC 4861), parte do ICMPv6: um Neighbor Solicitation (NS) multicast pergunta "quem tem este endereço?", e o dono responde com um Neighbor Advertisement (NA) unicast com o seu MAC, que vai para a tabela NDP. O NS também detecta endereços duplicados (DAD): antes de usar um endereço, o host pergunta por ele, com origem ::; se alguém responder, o endereço é recusado (pág. 232–233 do PDF).

Na autoconfiguração sem estado (SLAAC, RFC 4862), o host forma o link-local, confere com DAD e espera um Router Advertisement, que os roteadores mandam a ff02::1 cerca de cada 30 s, ou pede um com um Router Solicitation. O RA traz o hop limit padrão, os bits M e O (há informação no DHCPv6), o tempo de vida do roteador, a MTU e a opção de prefixo, com tempos de vida que ajudam a renumerar a rede. O host junta o prefixo ao seu identificador e confere o novo endereço com DAD (Figs. 55–56, pág. 233–234 do PDF).

Os tempos de vida da opção de prefixo, Valid Lifetime e Preferred Lifetime, servem para trocar o prefixo de uma sub-rede sem atrapalhar os hosts, o chamado problema da renumeração (RFC 7010). O cenário do livro (pág. 234 do PDF): uma pequena empresa com uma só sub-rede e SLAAC troca de provedor. O roteador passa a anunciar dois prefixos, o antigo com tempo de vida curto, para os hosts deixarem de usá-lo, e o novo com tempo de vida longo. Depois de algum tempo, o roteador para de anunciar o antigo, os hosts o abandonam e o prefixo volta ao primeiro provedor. Em redes grandes, renumerar continua difícil.

Uma pequena empresa com SLAAC troca de provedor. Como mudar o prefixo sem parar a rede?

Nota do livro
Router Advertisements e Hop Limit (pág. 234–235 do PDF). O RA não deve sair do enlace, mas vai com Hop Limit 255, e não 1. Assim, o host confere que o valor ainda é 255: um RA vindo de fora teria passado por um roteador e chegaria com 254 ou menos (RFC 5082).

Nota
O livro manda o Router Solicitation para FF01::2 (pág. 235 do PDF). O grupo de todos os roteadores do enlace é ff02::2, como o próprio livro escreve na pág. 221; ff01::2 tem escopo de interface e não sairia do host.

Com dois roteadores na sub-rede, o roteador padrão que recebe um pacote que deveria ter ido ao outro manda ao host um Redirect, e o host cria uma rota temporária (Fig. 57). A alternativa ao SLAAC é o DHCP, em que um servidor distribui endereços de um conjunto e os empresta por tempo limitado (pág. 235–236 do PDF).

Nota
Ao descrever o DHCP para IPv6, o livro mistura o DHCP do IPv4 (pág. 235–236 do PDF): diz que o servidor escuta na porta 67 e que a resposta traz a máscara de sub-rede e o roteador padrão. No DHCPv6 (RFC 8415, que substituiu a RFC 3315), os servidores escutam na porta UDP 547 (os clientes, na 546), e o prefixo da sub-rede e o roteador padrão vêm dos Router Advertisements, não do DHCPv6.

O SLAAC e o DHCPv6 podem levar mais do que o prefixo e o endereço. A RFC 6106 define opções do Neighbor Discovery que trazem o endereço do resolvedor DNS recursivo e a lista de sufixos de busca. Também dá para combinar os dois: o SLAAC distribui os prefixos, e uma variante sem estado do DHCPv6 (RFC 3736) distribui só as informações de DNS (pág. 236 do PDF).

O Hop Limit 255 impede uma família de ataques ao ICMPv6, mas não todos. O NDP pode ser protegido com endereços gerados criptograficamente (CGA, RFC 3972) e com o SEND, Secure Neighbor Discovery (RFC 3971); o livro deixa a segurança do IPv6 fora do escopo (pág. 235 do PDF).

Complemento
As opções de DNS da RFC 6106 estão hoje na RFC 8106, e o DHCPv6 sem estado da RFC 3736 foi incorporado à RFC 8415. O SEND (RFC 3971) quase não é implantado; nas LANs, a defesa comum contra RAs falsos é o switch filtrar anúncios nas portas de hosts, o RA Guard (RFC 6105).

Complemento
Um identificador fixo, derivado do MAC, permite rastrear um host por onde ele for. Por isso as extensões de privacidade, hoje na RFC 8981 (que substituiu a RFC 4941 citada pelo livro), geram identificadores aleatórios, e os sistemas atuais quase não usam mais o EUI-64 nos endereços globais.

Pratique

Exercícios graduados

  1. Aquecimento: escreva na forma compacta o prefixo 2001:0db8:0000:cd30:0000:0000:0000:0000/60.
    Ver solução

    2001:db8:0:cd30::/60, uma das três formas equivalentes do livro (pág. 216 do PDF).

  2. Aquecimento: na tabela do livro, por onde sai um pacote para 2001:6a8:3080:2::7? E para 2a02:2788:1::1?
    Ver solução

    O primeiro casa com ::/0, 2001:6a8::/32 e 2001:6a8:3080::/48: sai por fe80::bad:cafe. O segundo só casa com ::/0 (o /64 é 2a02:2788:2c4:16f::/64): sai por fe80::dead:beef.

  3. Intermediário: uma origem precisa mandar 3000 bytes de dados (depois do cabeçalho IPv6) por um enlace de MTU 1280. Quantos fragmentos, com que offsets e quantos dados no último?
    Ver solução

    Cada fragmento leva 8 × ⌊(1280 − 48) / 8⌋ = 1232 bytes. Três fragmentos: offsets 0, 154 e 308; o último leva 3000 − 2464 = 536 bytes, com M = 0.

  4. Intermediário: calcule o identificador EUI-64 e o endereço link-local do host B do livro, de MAC 00:34:56:78:9a:bc.
    Ver solução

    234:56ff:fe78:9abc; link-local fe80::234:56ff:fe78:9abc.

  5. Intermediário: para qual grupo multicast vai o Neighbor Solicitation que procura fe80::234:56ff:fe78:9abc?
    Ver solução

    ff02::1:ff78:9abc: ff02::1:ff seguido dos 24 bits finais (78:9a:bc).

  6. Desafio: um administrador bloqueia todo o ICMPv6 no firewall da empresa. Páginas pequenas abrem, mas downloads grandes travam. Explique.
    Ver solução

    Os roteadores IPv6 não fragmentam: descartam os pacotes grandes demais e avisam a origem com Packet Too Big. Sem esse aviso, a origem continua mandando segmentos do tamanho máximo, que somem num enlace de MTU menor (um "buraco negro" de MTU). As respostas pequenas cabem e passam. Bloquear também os NS, NA e RA quebraria a própria rede local.

1. O maior prefixo, com a tabela do livro

import ipaddress

# a tabela de rotas do livro (pág. 219)
tabela = [("::/0", "fe80::dead:beef"), ("::1/128", "::1"), ("2a02:2788:2c4:16f::/64", "eth0"),
          ("2001:6a8:3080::/48", "fe80::bad:cafe"), ("2001:6a8:2d80::/48", "fe80::bad:bad"),
          ("2001:6a8::/32", "fe80::aaaa:bbbb")]
rotas = [(ipaddress.ip_network(p), via) for p, via in tabela]

def encaminha(destino):
    d = ipaddress.ip_address(destino)
    casam = [(rede, via) for rede, via in rotas if d in rede]
    rede, via = max(casam, key=lambda r: r[0].prefixlen)     # o maior prefixo vence
    return [str(r) for r, _ in casam], rede, via

for destino in ["2a02:2788:2c4:16f::1", "2001:6a8:3080::1234", "2001:1890:123a::1:1e", "2001:6a8:3880:40::2"]:
    casam, rede, via = encaminha(destino)
    print(f"{destino:24} casa com {casam} -> {rede} via {via}")

2. Classificando endereços

import ipaddress

ESCOPOS = {1: "interface", 2: "enlace", 4: "administração", 5: "site", 8: "organização", 0xE: "global"}

def classifica(texto):
    a = ipaddress.IPv6Address(texto)
    if a == ipaddress.IPv6Address("::"):
        return "não especificado (::)"
    if a.is_loopback:
        return "loopback (::1)"
    if a.is_multicast:
        escopo = a.packed[1] & 0x0F                    # os 4 bits baixos do 2º byte
        return f"multicast, escopo {ESCOPOS.get(escopo, escopo)}"
    if a.is_link_local:
        return "unicast link-local (fe80::/10)"
    if a in ipaddress.IPv6Network("fc00::/7"):
        return "unicast local único, ULA (fc00::/7)"
    if a in ipaddress.IPv6Network("2000::/3"):
        return "unicast global (2000::/3)"
    return "outro"

for t in ["::", "::1", "fe80::219:e3ff:fed7:1204", "ff02::1", "ff02::2", "ff05::101", "ff0e::1",
          "fd12:3456:789a::1", "2001:6a8:3080::1234"]:
    print(f"{t:26} {classifica(t)}")

3. Montando e lendo o cabeçalho IPv6

import struct, ipaddress

def monta_ipv6(classe, fluxo, tam_carga, prox, saltos, origem, destino):
    primeira = (6 << 28) | (classe << 20) | fluxo       # versão (4 bits), classe (8), rótulo de fluxo (20)
    return (struct.pack("!IHBB", primeira, tam_carga, prox, saltos)
            + ipaddress.IPv6Address(origem).packed + ipaddress.IPv6Address(destino).packed)

def le_ipv6(dados):
    primeira, tam_carga, prox, saltos = struct.unpack("!IHBB", dados[:8])
    return {"versão": primeira >> 28, "classe": (primeira >> 20) & 0xFF, "fluxo": primeira & 0xFFFFF,
            "carga": tam_carga, "próximo": prox, "saltos": saltos,
            "origem": str(ipaddress.IPv6Address(dados[8:24])),
            "destino": str(ipaddress.IPv6Address(dados[24:40]))}

PROXIMO = {0: "Hop-by-Hop", 6: "TCP", 17: "UDP", 43: "Routing", 44: "Fragment", 58: "ICMPv6", 60: "Destination Options"}

cab = monta_ipv6(0, 0x12345, 20, 6, 64, "2001:db8::1", "2001:db8::2")
print(len(cab), "bytes:", cab.hex(" "))
campos = le_ipv6(cab)
print(campos, "->", PROXIMO[campos["próximo"]])

4. Fragmentação na origem (o pseudo-código do livro, corrigido)

def fragmenta(tam_carga, mtu, ident=7):
    """Fragmentação do IPv6 na origem (o pseudo-código da pág. 225, corrigido).
    tam_carga: bytes depois do cabeçalho IPv6 de 40 bytes. Devolve os fragmentos."""
    if 40 + tam_carga <= mtu:
        return [{"plen": tam_carga, "offset": 0, "M": 0, "dados": tam_carga}]   # cabe sem fragmentar
    max_dados = 8 * ((mtu - 40 - 8) // 8)           # múltiplo de 8, descontando o cabeçalho de fragmento
    fragmentos, pos = [], 0
    while pos < tam_carga:
        dados = min(max_dados, tam_carga - pos)
        ultimo = pos + dados >= tam_carga
        fragmentos.append({"id": ident, "offset": pos // 8, "M": 0 if ultimo else 1,
                           "dados": dados, "plen": 8 + dados})     # Payload Length conta o cabeçalho de fragmento
        pos += dados
    return fragmentos

for f in fragmenta(3000, 1280):
    print(f, "-> pacote de", 40 + f["plen"], "bytes")

5. EUI-64 e o grupo solicited-node

import ipaddress

def eui64(mac):
    """Identificador de 64 bits a partir do MAC (RFC 4291, apêndice A): inverte o bit U/L e insere ff:fe no meio."""
    b = bytes(int(x, 16) for x in mac.split(":"))
    b = bytes([b[0] ^ 0x02]) + b[1:3] + b"\xff\xfe" + b[3:]
    return b

def endereco(prefixo, mac):
    rede = ipaddress.IPv6Network(prefixo)
    return ipaddress.IPv6Address(rede.network_address.packed[:8] + eui64(mac))

def solicited_node(addr):
    """Grupo multicast usado pelo Neighbor Solicitation: ff02::1:ff + os 24 bits finais do endereço."""
    a = ipaddress.IPv6Address(addr).packed
    return ipaddress.IPv6Address(bytes.fromhex("ff0200000000000000000001ff") + a[13:])

for nome, mac in [("A", "00:23:45:67:89:ab"), ("B", "00:34:56:78:9a:bc")]:   # os hosts do livro (pág. 231–232)
    ll = endereco("fe80::/64", mac)
    glob = endereco("2001:db8:1234:5678::/64", mac)
    print(f"{nome}: link-local {ll}  global {glob}")
    print(f"   Neighbor Solicitation para {solicited_node(glob)}")

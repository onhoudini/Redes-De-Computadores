Capítulo 10 · Parte 2: Protocolos

A web e as chamadas remotas

A web nasceu para compartilhar documentos entre físicos e virou a aplicação mais usada da Internet. Este capítulo mostra as URIs, o protocolo HTTP e o que foi feito para torná-lo mais rápido. Depois, sai da conversa entre pessoas e documentos para a conversa entre programas: as chamadas de procedimento remoto.

Apresentação

Documentos e programas pela rede

O HTTP é um protocolo de texto, como o SMTP do capítulo anterior: o cliente pede, o servidor responde. A simplicidade ajudou a web a crescer, mas as páginas ficaram grandes, cheias de imagens e scripts, e os pedidos um por um passaram a custar caro. O livro acompanha essa evolução, do HTTP/1.0 ao HTTP/2.0, e termina com as chamadas de procedimento remoto, em que o "documento" trocado é o parâmetro de uma função.

Objetivos de aprendizagem

  • Identificar as três peças da web (URI, HTML, HTTP) e decompor uma URI em esquema, autoridade, caminho, consulta e fragmento.
  • Montar e ler pedidos e respostas HTTP: métodos, cabeçalhos e códigos de status.
  • Comparar uma conexão por objeto, conexões persistentes, pipelining e os quadros do HTTP/2.
  • Explicar como cookies, caches, proxies e CDNs funcionam e quais problemas de privacidade os cookies trazem.
  • Codificar parâmetros em XDR e JSON e explicar como um RPC alcança o procedimento e lida com pedidos repetidos.

Antes de começar

O capítulo usa o formato de mensagens e o MIME do Capítulo 9, o modelo cliente-servidor e a ordem dos bytes do Capítulo 3 e as conexões do Capítulo 4. Ele cobre as seções 3.4 a 3.6 do livro (pág. 148–169 do PDF).

Cada pergunta vale 10 pontos se acertada na primeira tentativa (5 depois). Os desafios das simulações valem de 10 a 20 pontos. Ao concluir tudo de um conceito, você ganha a medalha dele.

Conceito 1

A web, os padrões abertos e o HTML

1. Contextualização

No começo, a Internet servia para terminal remoto (telnet), e-mail e transferência de arquivos. O FTP (RFC 959) tinha um modo autenticado, com usuário e senha, e um modo anônimo, para arquivos públicos. Hoje o acesso autenticado é feito com ssh (scp, sftp), e o anônimo, pela web (pág. 148 do PDF).

2. Explicação

No fim dos anos 1980, os físicos do CERN precisavam trocar documentos. Tim Berners-Lee avaliou as soluções da época e, como nenhuma servia, criou um sistema novo, chamado primeiro de mesh e logo de world wide web. O hipertexto (documentos com links para outros documentos) já existia desde a proposta de 1945 e as experiências dos anos 1960; a novidade da web foi deixar um link apontar para um documento guardado em outra máquina (pág. 148 do PDF). Um sistema assim precisa de três peças:

  1. um esquema de endereços que identifique cada documento sem ambiguidade: as URIs;
  2. um formato de documento: o HTML;
  3. um protocolo para buscar os documentos: o HTTP.
Nota do livro
Padrões abertos e implementações abertas (pág. 149 do PDF). Sem padrões abertos, a web não teria chegado ao tamanho atual. Também ajudou o CERN ter publicado servidores e clientes de código aberto, que funcionavam como estavam e podiam ser estendidos. O NCSA, por exemplo, acrescentou imagens ao navegador Mosaic, que deu origem à Netscape e aos primeiros navegadores e servidores comerciais.

O HTML veio do SGML, padronizado pela ISO em 1986 para documentos que precisam continuar legíveis por décadas. Uma linguagem de marcação mistura o texto com anotações sobre ele. Um elemento HTML tem uma marca de abertura (com atributos opcionais), um conteúdo e uma marca de fechamento (pág. 150–151 do PDF): 

<tag atributo1="valor1" atributo2="valor2">texto a exibir</tag>

O documento tem um cabeçalho (<head>, com o título, por exemplo) e um corpo (<body>). No corpo, <h1> é um título, <ul> e <li> fazem uma lista, <img src="URI"> inclui uma imagem, que pode estar em qualquer servidor e é baixada automaticamente, e <a href="URI">texto</a> é um link. Folhas de estilo e JavaScript vieram depois, nas especificações mantidas pelo W3C.

4. Prática

Qual foi a principal inovação da web em relação ao hipertexto dos anos 1980?

O que acontece com <img src="http://outro.example/foto.png"> numa página?

5. Fixação

  • Web = URI (endereço) + HTML (formato) + HTTP (protocolo).
  • Padrões e implementações abertas explicam boa parte do sucesso da web.
  • HTML: elementos com marca de abertura, conteúdo e marca de fechamento.
Conceito 2

URIs

1. Contextualização

ftp://cnn.example.com&story=breaking_news@10.0.0.1/top_story.htm: a maioria das pessoas acha que esse endereço leva a um documento em cnn.example.com. Leva? Para responder, é preciso conhecer a gramática.

2. Explicação

Uma Uniform Resource Identifier (RFC 3986) é uma cadeia de caracteres que identifica um recurso sem ambiguidade. Parte da gramática (pág. 149 do PDF): 

URI         = scheme ":" "//" authority path [ "?" query ] [ "#" fragment ]
scheme      = ALPHA *( ALPHA / DIGIT / "+" / "-" / "." )
authority   = [ userinfo "@" ] host [ ":" port ]
query       = *( pchar / "/" / "?" )
fragment    = *( pchar / "/" / "?" )
pchar       = unreserved / pct-encoded / sub-delims / ":" / "@"
pct-encoded = "%" HEXDIG HEXDIG
unreserved  = ALPHA / DIGIT / "-" / "." / "_" / "~"
  • Esquema: um seletor que diz como ler o resto. Costuma indicar o protocolo (http, https), mas nem sempre: urn:isbn:0-380-81593-1 identifica um livro sem dizer como buscá-lo. Depois do esquema vêm : e //.
  • Autoridade: o nome DNS ou o endereço IP do servidor, opcionalmente precedido de informação sobre o usuário (antes de @) e seguido de : e uma porta. A porta só aparece quando não é a padrão do protocolo. Colocar uma senha na URI (permitido na antiga RFC 1738) é hoje obsoleto e inseguro.
  • Caminho: estruturado como nomes de arquivo no Unix, o que não quer dizer que o servidor guarde arquivos assim. Sem caminho, o servidor devolve um documento padrão.
  • Consulta (depois de ?) e fragmento (depois de #, um trecho do documento), ambos opcionais (pág. 150 do PDF).

Nota
O livro diz que o nome do host pode ser seguido de "semicolon" (ponto e vírgula) e da porta (pág. 150 do PDF). Pela gramática acima, o separador é o dois-pontos: host:porta, como em telnet://[2001:db8:3080:3::2]:2323/. Endereços IPv6 vão entre colchetes justamente porque contêm dois-pontos.

Agora a URI do começo. O @ separa o nome do usuário do host. Tudo o que vem antes dele, cnn.example.com&story=breaking_news, é o nome de usuário; o documento top_story.htm é buscado por FTP no host 10.0.0.1 (pág. 150 do PDF). Esse truque já foi usado em golpes de phishing.

Complemento
Caracteres fora do conjunto permitido são escritos com % e dois dígitos hexadecimais de cada byte (UTF-8): "café" vira caf%C3%A9, e um espaço, %20. A lista de esquemas registrados é mantida pela IANA.

3. Visualização

4. Prática

O fragmento (#…) de uma URI é enviado ao servidor no pedido HTTP?

5. Fixação

  • esquema://[usuário@]host[:porta]caminho[?consulta][#fragmento]
  • O host é o que vem depois do último @ da autoridade.
  • Porta separada por dois-pontos; IPv6 entre colchetes; senha na URI é obsoleta.
Conceito 3

Pedidos e respostas HTTP

1. Contextualização

Com a URI em mãos, o navegador abre uma conexão TCP com o servidor e conversa em linhas de texto, como no SMTP. Mas o que, exatamente, vai em cada linha?

2. Explicação

O HyperText Transfer Protocol roda sobre o fluxo de bytes, e os servidores escutam na porta 80. Ele foi muito inspirado no e-mail (Fig. 13, pág. 151–152 do PDF):

  • Pedido: uma linha com o método, a URI e a versão; um cabeçalho, que termina numa linha vazia; e, opcionalmente, um documento MIME.
  • Resposta: uma linha de status; um cabeçalho, que termina numa linha vazia; e um documento MIME.

Os três métodos mais importantes:

  • GET: busca um documento. Para http://www.w3.org/MarkUp/, o cliente abre uma conexão TCP com www.w3.org na porta 80 e envia GET /MarkUp/ HTTP/1.0.
  • HEAD: como GET, mas só devolve o cabeçalho, para saber se um documento existe, por exemplo.
  • POST: envia um documento ao servidor, anexado ao pedido como documento MIME.

Cabeçalhos comuns (pág. 152–153 do PDF):

  • nos dois sentidos: Content-Length: (tamanho em bytes), Content-Type: (text/html, por exemplo) e Content-Encoding: (x-gzip, por exemplo);
  • nas respostas: Server: (a versão do servidor, que alguns administradores escondem por segurança), Date: e Last-Modified:;
  • nos pedidos: User-Agent: (o cliente), If-Modified-Since: (só mande o documento se for mais novo que a minha cópia), Referer: (a página de onde veio o link) e Host: (o nome do servidor pedido).

Nota
O livro escreve o cabeçalho como "Referrer:" (pág. 153 do PDF). O nome padronizado é Referer:, com um r só, um erro de grafia que entrou na especificação original (RFC 1945) e ficou. Os próprios exemplos do livro usam Referer:.

Nota do livro
A importância do Host: (pág. 153 do PDF). A primeira versão do HTTP não tinha essa linha. Se uma empresa hospeda web.example.com e www.example.net no mesmo servidor, e os dois sites têm /index.html, o pedido GET /index.html HTTP/1.0 não diz qual dos dois o cliente quer. Com o Host:, um único servidor físico pode hospedar muitos sites independentes.

A linha de status tem a versão, um código de três dígitos e uma frase, com a mesma ideia do SMTP:

  • 2xx, sucesso: 200 OK.
  • 3xx: 301 Moved Permanently (o documento mudou de lugar; o novo endereço vem em Location:) e 304 Not Modified (resposta a um If-Modified-Since: a cópia do cliente ainda vale).
  • 4xx, erro no pedido: 400 Bad Request, 404 Not Found.
  • 5xx, erro no servidor: 500 Internal Server Error.

Nota
O livro diz que os códigos 3xx indicam que o documento "não está mais disponível no servidor" (pág. 153 do PDF). Isso vale para o 301, mas não para o 304, que diz o contrário: o documento continua lá e não mudou. A definição do padrão é mais geral: 3xx é redirecionamento, ou seja, o cliente precisa fazer mais alguma coisa para completar o pedido (RFC 9110, seção 15.4).

O exemplo do livro, um pedido HTTP/1.0 feito com a ferramenta curl (pág. 153–154 do PDF):

GET / HTTP/1.0
User-Agent: curl/7.19.4 (universal-apple-darwin10.0) libcurl/7.19.4 OpenSSL/0.9.8l zlib/1.2.3
Host: www.ietf.org

HTTP/1.1 200 OK
Date: Mon, 15 Mar 2010 13:40:38 GMT
Server: Apache/2.2.4 (Linux/SUSE) mod_ssl/2.2.4 OpenSSL/0.9.8e (truncated)
Last-Modified: Tue, 09 Mar 2010 21:26:53 GMT
Content-Length: 17019
Content-Type: text/html

<!DOCTYPE HTML PUBLIC .../HTML>

Complemento
As RFCs que o livro cita para o HTTP/1.1 (2616 e 7230) foram substituídas em 2022 pela RFC 9110 (semântica), pela RFC 9111 (caches) e pela RFC 9112 (o formato do HTTP/1.1). Hoje quase toda a web usa https, na porta 443: o mesmo HTTP dentro de uma conexão TLS, assunto do Capítulo 11.

4. Prática

Um programa quer saber se um arquivo de 2 GB mudou, sem baixá-lo. Qual método usa?

O que indica uma resposta 404?

5. Fixação

  • Pedido: método URI versão + cabeçalho + linha vazia + documento opcional.
  • Resposta: versão código frase + cabeçalho + linha vazia + documento.
  • Host: permite vários sites num servidor; If-Modified-Since: e 304 evitam baixar de novo.
Conceito 4

Conexões persistentes

1. Contextualização

Para facilitar a implementação, o HTTP abria uma conexão TCP para cada pedido. Para páginas só de texto, tudo bem: o usuário passa um tempo lendo. Mas e uma página com dezenas de imagens?

2. Explicação

Uma conexão por objeto tem dois custos (pág. 154 do PDF): os pacotes para abrir e fechar cada conexão TCP, que aumentam o tráfego e o tempo total da página; e o grande número de conexões abertas, que pode sobrecarregar o servidor. A solução do HTTP/1.1 foram as conexões persistentes: o cliente manda vários pedidos pela mesma conexão. Dois cabeçalhos controlam o uso:

  • Connection: Keep-Alive (o cliente quer manter a conexão) ou Close (quem enviou vai fechá-la ao fim da resposta);
  • Keep-Alive: o servidor diz quantos pedidos ainda aceita e depois de quantos segundos parado fecha a conexão: Keep-Alive: timeout=15, max=100.

No exemplo do livro (pág. 155–156 do PDF), o navegador busca a página de www.kame.net, a folha de estilo e o ícone pela mesma conexão; o servidor responde com max=100, max=99 e max=98. O ícone não existe (404), mas a conexão continua aberta.

Mesmo na mesma conexão, cada pedido é independente: o servidor não usa nada além do próprio pedido para respondê-lo. Por isso o navegador repete User-Agent: e Host: em todos os pedidos (pág. 156–157 do PDF).

3. Visualização

Modelo simplificado: abrir a conexão custa 1 RTT, cada pedido e resposta mais 1 RTT, e o tempo de transmissão é desprezado.

4. Prática

Por que o navegador repete o User-Agent: em todos os pedidos de uma mesma conexão persistente?

5. Fixação

  • HTTP/1.0: uma conexão TCP por objeto. HTTP/1.1: conexões persistentes.
  • Connection: Keep-Alive ou Close; Keep-Alive: timeout e max.
  • Cada pedido continua independente dos outros.
Conceito 5

Guardando estado: cookies

1. Contextualização

Se cada pedido é independente, como uma loja lembra o seu carrinho de uma página para a outra? Ou um site lembra o idioma que você escolheu?

2. Explicação

O livro discute três mecanismos (pág. 157 do PDF):

  1. Autenticação: o HTTP tem cabeçalhos para pedir usuário e senha (RFC 2617), mas ninguém aceita decorar uma senha para cada site visitado.
  2. Cabeçalhos Accept-*: Accept-Language: diz os idiomas preferidos, mas costuma vir da configuração do navegador, e é difícil escolher site a site.
  3. Cookies, a solução adotada. Criados pela Netscape e padronizados na RFC 6265: um cookie é uma cadeia curta escolhida pelo servidor para representar um cliente.

Quando chega um pedido sem Cookie:, o servidor gera um cookie e o manda no cabeçalho Set-Cookie: da resposta, com parâmetros como os domínios em que ele vale. O navegador guarda os cookies e, a cada pedido, anexa o cookie do domínio, se tiver um. A resposta passa a depender da URL e do cookie (pág. 157–158 do PDF).

Nota do livro
Cookies e privacidade (pág. 158 do PDF). Uma empresa de anúncios, ad.com, coloca imagens nas páginas de muitos sites. Cada vez que o navegador busca uma dessas imagens, manda o cookie de ad.com. Assim, ad.com pode acompanhar os interesses de quem visita todos esses sites e direcionar anúncios. Defensores da privacidade chegaram a processar empresas de anúncios.

Complemento
Um cookie mandado por um servidor diferente do site que você está visitando é um cookie de terceiro. Por causa do rastreamento, o Safari bloqueia e o Firefox isola por site esses cookies por padrão (Wikipedia: HTTP cookie). Mesmo sem cookies, o cabeçalho Referer: ainda conta ao anunciante de qual página veio o pedido.

3. Visualização

4. Prática

Em que ordem aparecem os cabeçalhos de cookie?

5. Fixação

  • Cookie: cadeia escolhida pelo servidor (Set-Cookie:) e devolvida pelo navegador (Cookie:).
  • Permite carrinhos, sessões e preferências sobre um HTTP sem estado.
  • Cookies de terceiros permitem rastrear pessoas entre sites.
Conceito 6

Caches, proxies e CDNs

1. Contextualização

A web passou a entregar música, vídeo, jogos e aplicações, que exigem mais desempenho do que documentos estáticos (pág. 158 do PDF). A forma mais simples de acelerar é não transmitir de novo o que já foi transmitido.

2. Explicação

Com o método HEAD e o If-Modified-Since:, o navegador confere se a cópia no seu cache ainda vale. Caches também podem ficar dentro da rede (Fig. 14, pág. 159 do PDF):

  • Proxy web: numa pequena empresa, ligada à Internet por um enlace lento, Alice e Bob leem o mesmo jornal, e a mesma informação passa duas vezes pelo enlace. Com um proxy, todos os navegadores mandam os pedidos a ele; se o conteúdo já está no cache do proxy, ele responde direto, senão busca no servidor e guarda uma cópia. Algumas empresas também usam o proxy para controlar e bloquear sites.
  • Proxy reverso: fica na frente dos servidores. Um servidor que monta páginas consultando bancos de dados e gasta 10 ms por pedido, em sequência, não atende mais de 100 pedidos por segundo. Um proxy reverso com cache responde os pedidos repetidos sem incomodar o servidor e pode dividir a carga entre vários servidores.
Nota do livro
Servindo conteúdo de vários servidores (pág. 159–160 do PDF). Quem acessa www.service.net tem a impressão de falar com um servidor só. Uma forma de distribuir a carga é guardar todos os arquivos em todos os servidores e deixar o DNS escolher: por rodízio (round-robin), pelo menos carregado ou pelo mais próximo do cliente. Outra é usar k proxies reversos perto dos clientes e N−k servidores com o conteúdo. As empresas que espalham proxies reversos pelo mundo são as redes de distribuição de conteúdo (CDNs).

As páginas cresceram muito. Quando o livro foi escrito, uma página média tinha quase 2 MB: 27 kB de HTML, 120 kB de fontes, 60 kB de CSS, quase 1 MB de imagens e mais de 400 kB de JavaScript, e exigia cerca de 70 pedidos HTTP (Fig. 15, pág. 160 do PDF). Os números atuais estão no HTTP Archive, a fonte do livro.

3. Visualização

4. Prática

Um servidor gasta 10 ms por pedido e atende um de cada vez. Quantos pedidos por segundo ele aguenta, no máximo?

Um site popular quer aliviar o servidor que monta as páginas a partir do banco de dados. O que ele instala?

5. Fixação

  • Cache no navegador (If-Modified-Since:), proxy na rede do cliente, proxy reverso na frente do servidor.
  • DNS e proxies reversos espalhados pelo mundo (CDNs) dividem a carga e aproximam o conteúdo.
Conceito 7

Pipelining e HTTP/2

1. Contextualização

Setenta pedidos por página, cada um esperando o anterior. Mesmo com a conexão persistente, o tempo de ida e volta se soma setenta vezes. Dá para pedir tudo de uma vez?

2. Explicação

Com o pipelining, o navegador manda vários pedidos sem esperar as respostas. No exemplo do livro, cinco objetos de 100 bytes, com 1 Gbit/s e 100 ms de atraso em cada sentido: um de cada vez, são 5 × 200 ms = 1 s; com pipelining, as cinco respostas chegam depois de cerca de 200 ms (pág. 161 do PDF). Mas o pipelining só serve para pedidos idempotentes, que não dependem dos anteriores. Foi difícil para os navegadores respeitar essa regra, e poucos o implementaram.

O HTTP/1.1 também tem outro problema: tudo é texto ASCII. Fica fácil escrever clientes e depurar, mas os servidores precisam de analisadores complexos, e essa flexibilidade abriu brechas para ataques. O HTTP/2.0 (RFC 7540) muda duas coisas: usa codificação binária e permite vários streams na mesma conexão. Ele também comprime os cabeçalhos (RFC 7541). A sessão é dividida em quadros, cada um com um cabeçalho de 9 bytes (Fig. 16, pág. 162 do PDF): 

+-----------------------------------------------+
|                 Length (24)                   |
+---------------+---------------+---------------+
|   Type (8)    |   Flags (8)   |
+-+-------------+---------------+-------------------------------+
|R|                 Stream Identifier (31)                      |
+-+-------------------------------------------------------------+
|                   Frame Payload (0...)                      ...
+---------------------------------------------------------------+
  • Length: 24 bits, então um quadro tem no máximo 224 − 1 bytes de dados; o padrão é 214 = 16 384 bytes, salvo se um quadro Settings negociar outro limite.
  • Type: Data (dados de um objeto), Headers (os cabeçalhos HTTP, comprimidos), Settings, Priority, Window_Update, Ping, GoAway…
  • Stream Identifier: o stream a que o quadro pertence. Os ímpares são do cliente, e os pares, do servidor. É isso que permite multiplexar vários objetos na mesma conexão.

A multiplexação ataca o bloqueio do primeiro da fila (Head of Line blocking). A 1 Mbit/s, um objeto de 12 500 bytes ocupa a conexão por 100 ms; se ele vem primeiro, um objeto de 125 bytes, talvez um script importante, espera esses 100 ms. Com quadros, o servidor manda 1 250 bytes do longo (10 ms), depois o curto inteiro (1 ms) e depois o resto do longo (pág. 163 do PDF). Quadros longos gastam pouco com cabeçalhos, mas bloqueiam os objetos curtos; quadros curtos fazem o contrário.

Nota
O livro diz que, assim, o cliente recebe o objeto curto depois de 10 ms (pág. 163 do PDF). Pela conta do próprio exemplo, são cerca de 11 ms: 10 ms do primeiro quadro do objeto longo mais 1 ms do objeto curto, sem contar os 9 bytes de cabeçalho de cada quadro.

Outros recursos (pág. 164–165 do PDF): o quadro Settings, o primeiro que o cliente envia, com SETTINGS_MAX_FRAME_SIZE (de 214 a 224 − 1) e SETTINGS_MAX_CONCURRENT_STREAMS (a RFC recomenda pelo menos 100); o push, em que o servidor manda um objeto antes de o cliente pedir, se o cliente permitir (poucos servidores o adotaram); prioridades entre streams; e controle de fluxo próprio, com janela inicial de 65 535 bytes, ampliada por quadros Window_Update. Para não confundir servidores antigos, uma sessão HTTP/2.0 na porta 80 começa como HTTP/1.1, com os cabeçalhos Connection: Upgrade, HTTP2-Settings e Upgrade: h2c, e o servidor responde 101 Switching Protocols.

Complemento
O nome oficial é HTTP/2, hoje na RFC 9113, que substituiu a 7540 em 2022 e deixou de recomendar o esquema de prioridades e o Upgrade h2c. Na prática, os navegadores só usam HTTP/2 sobre TLS, e o push foi abandonado por eles. O livro promete discutir mudanças na pilha inteira mais adiante: é o caminho do HTTP/3 (RFC 9114), que roda sobre o QUIC (RFC 9000) em vez do TCP, para que a perda de um pacote não bloqueie todos os streams.

3. Visualização

4. Prática

Para quais pedidos o pipelining pode ser usado?

Um navegador abre um stream novo no HTTP/2 para pedir uma imagem. O identificador do stream é…

5. Fixação

  • Pipelining: vários pedidos sem esperar; só para pedidos idempotentes.
  • HTTP/2: binário, quadros com cabeçalho de 9 bytes, streams multiplexados, cabeçalhos comprimidos.
  • Quadros menores reduzem o bloqueio do primeiro da fila, mas aumentam o custo dos cabeçalhos.
Conceito 8

Chamadas remotas: codificando os dados

1. Contextualização

Até aqui, pessoas trocavam mensagens e liam documentos. Mas muitas vezes é um programa que precisa de outro: um cálculo pesado feito em outra máquina, por exemplo. Muitos sistemas distribuídos usam a chamada de procedimento remoto (RPC) como peça básica (pág. 165 do PDF).

2. Explicação

Numa chamada local, a maioria das linguagens faz assim (pág. 166 do PDF):

  1. quem chama põe os parâmetros num lugar (registrador, pilha…) onde a função os encontra;
  2. transfere a execução para a função;
  3. a função lê os parâmetros e calcula;
  4. põe os valores de retorno num lugar acessível a quem chamou;
  5. devolve a execução.

Em máquinas diferentes, há dois problemas: elas não compartilham a memória, e podem representar números e caracteres de formas diferentes. Daí as duas perguntas: como codificar os parâmetros e como alcançar a função pela rede. Codificações populares: XDR, usada pelo ONC-RPC; XML, usada pelo XML-RPC; e JSON.

  • XDR (RFC 1832, pág. 166–167 do PDF): cada tipo vira uma sequência de bytes. Um inteiro de 32 bits vai com o byte mais significativo primeiro (big-endian, como você viu no Capítulo 3); há inteiros de 64 bits; booleanos viram inteiros 0 e 1; números de ponto flutuante seguem o padrão IEEE (no de 64 bits: 1 bit de sinal S, 11 de expoente E e 52 de fração F, valendo (−1)S × 2E−1023 × 1,F). Uma cadeia de bytes é o tamanho (um inteiro) seguido dos bytes, completados com zeros até um múltiplo de 4, para alinhar em 32 bits. Um vetor de tamanho variável começa pelo número de elementos.
  • JSON (RFC 4627, pág. 167–168 do PDF): texto. Inteiros são dígitos ASCII; cadeias vêm entre aspas, com escapes para " e \; booleanos são true e false; objetos são listas de pares entre chaves, e vetores, entre colchetes: {"Primes": [2, 3, 5, 7]}.

A vantagem do JSON é ser legível por uma pessoa; o custo é uma codificação menos compacta: os mesmos dados costumam ocupar mais espaço do que em XDR (pág. 168 do PDF).

Complemento
As versões atuais são a RFC 4506 (XDR) e a RFC 8259 (JSON). O "costumam" do livro é importante: um número pequeno ocupa um ou dois caracteres em JSON e sempre 4 bytes em XDR. A simulação mostra os dois casos.

Conceito 9

Chamadas remotas: alcançando a função

1. Contextualização

A função tem um nome, mas o transporte só conhece endereços e portas. E se o pedido, ou a resposta, se perder no caminho?

2. Explicação

A solução mais simples é a função ficar num processo que escuta numa porta conhecida. É o que faz o JSON-RPC, sobre datagramas ou sobre conexões. Um pedido é um objeto JSON com os campos jsonrpc (a versão), method, params e id, escolhido por quem chama (pág. 168 do PDF): 

{ "jsonrpc": "2.0", "method": "sum", "params": [1, 3], "id": 1 }
{ "jsonrpc": "2.0", "result": 4, "id": 1 }
{ "jsonrpc": "2.0", "error": {"code": -32601, "message": "Method not found"}, "id": 1 }

A resposta traz o mesmo id e um result ou um error, com código, mensagem e dados opcionais. Alguns códigos: −32700, erro ao analisar o pedido; −32602, parâmetros inválidos; −32601, método inexistente.

Nota
No exemplo de erro do livro, a resposta traz "id": "1", uma cadeia, enquanto o pedido usou o número 1 (pág. 168 do PDF). Pela especificação do JSON-RPC 2.0, a resposta deve repetir o id do pedido, com o mesmo valor, como no exemplo acima.

O id tem o mesmo papel do identificador da mensagem DNS: casar a resposta com o pedido. Ele é importante sobre datagramas, que não são confiáveis. No DNS, repetir uma consulta perdida não causa problema. Num RPC, pode causar: se a resposta de um depósito bancário se perde, o cliente reenvia o pedido, e o servidor deposita duas vezes. Ou as funções remotas podem ser chamadas várias vezes sem estragar nada (idempotentes), ou a aplicação precisa detectar pedidos repetidos. Na prática, os programadores preferem a primeira opção (pág. 168–169 do PDF).

O ONC-RPC (RFC 1831) resolve o endereçamento de outro jeito: como não há portas para todas as funções (são só 216 por host), cada servidor registra as suas funções num diretório local, o portmapper (RFC 1833), que escuta na porta 111. Quem chama pergunta primeiro ao portmapper em que porta está a função e depois fala direto com ela (pág. 169 do PDF).

Complemento
A versão atual do ONC-RPC é a RFC 5531. Muitas APIs atuais seguem a mesma ideia sobre HTTP, com JSON no corpo dos pedidos.

4. Prática

No ONC-RPC, a quem o cliente pergunta primeiro em que porta está uma função?

Qual destas funções remotas é idempotente, ou seja, pode ser repetida sem problema?

5. Fixação

  • JSON-RPC: jsonrpc, method, params e id; resposta com result ou error e o mesmo id.
  • Perda da resposta + reenvio = execução duplicada, a menos que a função seja idempotente ou o servidor detecte o id repetido.
  • ONC-RPC: o portmapper (porta 111) diz a porta de cada função.
Pratique

Exercícios graduados

  1. Aquecimento: decomponha https://alice@www.example.com:8443/docs/a.html?v=2#fim em esquema, usuário, host, porta, caminho, consulta e fragmento.
    Ver solução

    https; alice; www.example.com; 8443; /docs/a.html; v=2; fim.

  2. Aquecimento: escreva o pedido HTTP/1.1 que busca http://www.example.net/contato.html.
    Ver solução

    GET /contato.html HTTP/1.1, depois Host: www.example.net e uma linha vazia (o User-Agent: é opcional).

  3. Intermediário: uma página tem o HTML e 9 imagens, e o RTT é 80 ms. Pelo modelo do conceito 4, quanto tempo leva com HTTP/1.0 e com uma conexão persistente sem pipelining?
    Ver solução

    10 objetos. HTTP/1.0: 10 × 2 × 80 = 1600 ms. Persistente: 80 + 10 × 80 = 880 ms.

  4. Intermediário: codifique em XDR o inteiro 258 e a cadeia "Oi".
    Ver solução

    258 = 00 00 01 02. "Oi" = 00 00 00 02 4f 69 00 00 (tamanho, dois bytes de dados e dois de enchimento).

  5. Intermediário: a 1 Mbit/s, com quadros de no máximo 2500 bytes de dados, em quanto tempo chega o objeto de 125 bytes que vem atrás do de 12 500 bytes (ignore os cabeçalhos)?
    Ver solução

    O primeiro quadro do objeto longo leva 2500 × 8 / 106 = 20 ms, e o curto, 1 ms: 21 ms, contra 101 ms sem quadros.

  6. Desafio: um serviço de transferências bancárias por JSON-RPC sobre UDP não pode transferir duas vezes. Proponha duas soluções e diga onde cada uma guarda estado.
    Ver solução

    (1) O servidor guarda os ids já atendidos e as respostas, e repete a resposta se o id voltar: o estado fica no servidor. (2) A operação vira idempotente: o cliente gera um identificador único da transferência e o servidor só executa uma vez por identificador, ou a operação é escrita como "defina o estado" em vez de "some". Nas duas, o servidor precisa lembrar o que já fez por algum tempo.

def monta_requisicao(metodo, caminho, cabecalhos, versao="HTTP/1.1"):
    linhas = [f"{metodo} {caminho} {versao}"]
    linhas += [f"{nome}: {valor}" for nome, valor in cabecalhos.items()]
    return "\r\n".join(linhas) + "\r\n\r\n"          # a linha vazia fecha o cabeçalho

def le_resposta(texto):
    cabeca, _, corpo = texto.partition("\r\n\r\n")
    status, *linhas = cabeca.split("\r\n")
    versao, codigo, frase = status.split(" ", 2)
    cabecalhos = {}
    for linha in linhas:
        nome, _, valor = linha.partition(":")
        cabecalhos[nome.strip().lower()] = valor.strip()
    return versao, int(codigo), frase, cabecalhos, corpo

3. Quanto tempo leva uma página?

def transmissao(nbytes, banda_bps):
    return nbytes * 8 / banda_bps                     # segundos para pôr os bits no enlace

def http10(n, rtt, tam, banda):
    """Uma conexão TCP nova por objeto: 1 RTT para abrir + 1 RTT para pedir e receber."""
    return n * (2 * rtt + transmissao(tam, banda))

def sequencial(n, rtt, tam, banda):
    """Conexão persistente já aberta, um pedido de cada vez."""
    return n * (rtt + transmissao(tam, banda))

def pipelining(n, rtt, tam, banda):
    """Conexão persistente já aberta, todos os pedidos de uma vez."""
    return rtt + n * transmissao(tam, banda)

# o exemplo do livro: 5 objetos de 100 bytes, 1 Gbit/s, 100 ms em cada sentido (pág. 161 do PDF)
n, rtt, tam, banda = 5, 0.200, 100, 1e9
for nome, f in [("HTTP/1.0", http10), ("sequencial", sequencial), ("pipelining", pipelining)]:
    print(f"{nome:11} {f(n, rtt, tam, banda) * 1000:7.1f} ms")

# bloqueio do primeiro da fila e os quadros do HTTP/2 (pág. 163 do PDF): 1 Mbit/s
longo, curto, banda = 12500, 125, 1e6
print("objeto longo inteiro antes:", (transmissao(longo, banda) + transmissao(curto, banda)) * 1000, "ms")
print("quadro de 1250 bytes antes:", (transmissao(1250, banda) + transmissao(curto, banda)) * 1000, "ms")

4. XDR à mão e JSON

import struct, json

def xdr_int(n):
    return struct.pack(">i", n)                       # 4 bytes, o mais significativo primeiro

def xdr_string(texto):
    dados = texto.encode("utf-8")
    enchimento = (4 - len(dados) % 4) % 4             # alinha em 4 bytes
    return xdr_int(len(dados)) + dados + b"\x00" * enchimento

def xdr_array(numeros):
    return xdr_int(len(numeros)) + b"".join(xdr_int(n) for n in numeros)

print("int 1     :", xdr_int(1).hex(" "))
print("int -2    :", xdr_int(-2).hex(" "))
print("'rede'    :", xdr_string("rede").hex(" "))
print("'redes'   :", xdr_string("redes").hex(" "))
print("[2,3,5,7] :", xdr_array([2, 3, 5, 7]).hex(" "))

for lista in ([2, 3, 5, 7], [1000000000, 2000000000]):
    x, j = xdr_array(lista), json.dumps(lista).encode()
    print(f"{str(lista):26} XDR: {len(x):2} bytes   JSON: {len(j):2} bytes ({j.decode()})")

5. Um servidor JSON-RPC e o pedido repetido

import json

saldo = {"conta": 100}

def soma(a, b):
    return a + b

def deposita(valor):
    saldo["conta"] += valor
    return saldo["conta"]

METODOS = {"sum": soma, "deposit": deposita}
ja_vistos = {}                                         # id -> resposta (para pedidos repetidos)

def atende(texto, lembra_ids=False):
    try:
        pedido = json.loads(texto)
    except json.JSONDecodeError:
        return json.dumps({"jsonrpc": "2.0", "error": {"code": -32700, "message": "Parse error"}, "id": None})
    ident = pedido.get("id")
    if lembra_ids and ident in ja_vistos:
        return ja_vistos[ident]                        # repete a resposta sem executar de novo
    metodo = METODOS.get(pedido.get("method"))
    if metodo is None:
        resposta = {"jsonrpc": "2.0", "error": {"code": -32601, "message": "Method not found"}, "id": ident}
    else:
        try:
            resposta = {"jsonrpc": "2.0", "result": metodo(*pedido.get("params", [])), "id": ident}
        except TypeError:
            resposta = {"jsonrpc": "2.0", "error": {"code": -32602, "message": "Invalid params"}, "id": ident}
    ja_vistos[ident] = json.dumps(resposta)
    return ja_vistos[ident]

print(atende('{"jsonrpc": "2.0", "method": "sum", "params": [1, 3], "id": 1}'))   # o exemplo do livro
print(atende('{"jsonrpc": "2.0", "method": "mul", "params": [1, 3], "id": 2}'))
print(atende('{"jsonrpc": "2.0", "method": "sum", "params": [1], "id": 3}'))
print(atende('{"jsonrpc": "2.0", "method": "sum"'))

# a resposta de um depósito se perde, e o cliente repete o mesmo pedido
deposito = '{"jsonrpc": "2.0", "method": "deposit", "params": [50], "id": 7}'
atende(deposito)
atende(deposito)
print("saldo depois de repetir o pedido:", saldo["conta"])

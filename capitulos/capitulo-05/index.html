Capítulo 5

Nomes e endereços

As camadas de rede e de transporte trabalham com endereços: cadeias de bits de tamanho fixo. Pessoas, por outro lado, preferem nomes. Este capítulo mostra como a Internet passou de um único arquivo com todos os nomes para o DNS, uma base de dados distribuída em árvore, e por que as aplicações devem depender de nomes, e não de endereços.

Apresentação

De endereços a nomes

Nos capítulos anteriores, cada host tinha um endereço de rede, e cada aplicação, uma porta. Endereços são naturais para as entidades de rede e de transporte, mas não para pessoas: ninguém quer decorar a cadeia de bits de cada servidor. A solução é dar nomes aos hosts e usar um serviço de mapeamento que traduz cada nome no endereço correspondente.

Objetivos de aprendizagem

  • Explicar o papel dos endereços de rede, do campo de protocolo e das portas na multiplexação.
  • Justificar o uso de nomes como um nível de indireção sobre os endereços.
  • Descrever o hosts.txt e por que ele não escala.
  • Ler e montar nomes totalmente qualificados na árvore de nomes de domínio e validá-los pela gramática BNF.
  • Explicar os nomes internacionalizados (xn--) e o ataque homógrafo.
  • Seguir a resolução de um nome pelos servidores raiz, pela delegação e pelos resolvedores com cache.
  • Listar os benefícios dos nomes: mobilidade de servidores, distribuição de carga e vários serviços num só servidor.

Antes de começar

O capítulo usa a multiplexação por portas do Capítulo 4, o modelo cliente-servidor e as gramáticas BNF/ABNF do Capítulo 3. Ele cobre a seção 2.5 do livro (pág. 76–80 do PDF). O DNS em detalhe fica para a Parte 2 do livro.

Cada pergunta vale 10 pontos se acertada na primeira tentativa (5 depois). Os desafios das simulações valem de 10 a 20 pontos. Ao concluir tudo de um conceito, você ganha a medalha dele.

Conceito 1

Endereços nas camadas de rede e de transporte

1. Contextualização

Um mesmo host pode rodar, ao mesmo tempo, um protocolo de transporte confiável e um protocolo de transporte sem conexão. Quando chega um pacote, como a camada de rede sabe a qual deles entregar o segmento? E, quando o segmento chega à camada de transporte, a qual aplicação?

2. Explicação

As camadas de rede e de transporte usam endereços codificados como cadeias de bits de tamanho fixo. Um endereço de rede identifica um host de forma única. Para multiplexar os segmentos dos vários protocolos de transporte, o cabeçalho do pacote leva um campo que indica qual protocolo deve processar o segmento. Como existem poucos protocolos de transporte, esse campo não precisa ser longo. Os números de porta têm o papel equivalente na camada de transporte: permitem multiplexar os dados de vários processos de aplicação.

4. Prática

Por que o campo do pacote que indica o protocolo de transporte pode ser curto?

5. Fixação

  • Endereço de rede: identifica o host.
  • Campo de protocolo no pacote: escolhe o protocolo de transporte.
  • Porta no segmento: escolhe o processo de aplicação.
Conceito 2

Por que usar nomes

1. Contextualização

Nos primeiros anos da Internet, poucos hosts (principalmente minicomputadores) estavam ligados à rede, e as aplicações mais populares eram login remoto e transferência de arquivos. Em 1983 já havia cerca de quinhentos hosts, cada um com um endereço único. Obrigar as pessoas a decorar esses endereços não era nada prático.

2. Explicação

Pessoas preferem lembrar nomes. Um nome é uma cadeia de caracteres, e um serviço de mapeamento permite que as aplicações traduzam cada nome no endereço correspondente. Além de ser mais amigável, isso cria um nível de indireção, muito útil em várias situações.

Usar nomes como apelidos de endereços é uma técnica comum em computação. Quem programa numa linguagem de alto nível escreve com variáveis, sem saber se elas ficam na memória ou em registradores. Do mesmo jeito, como os nomes estão num nível acima dos endereços, os endereços viram meros identificadores técnicos, que podem mudar à vontade. Só os nomes são estáveis.

4. Prática

Com um serviço de nomes, o que deve permanecer estável para os usuários de um servidor?

5. Fixação

  • Endereços servem à rede; nomes servem às pessoas.
  • Um serviço de mapeamento traduz nome → endereço.
  • O nome é um nível de indireção: o endereço pode mudar, o nome fica.
Conceito 3

O arquivo hosts.txt

1. Contextualização

A primeira solução para usar nomes foi um simples arquivo de texto, parecido com a tabela de símbolos de um programa compilado: o hosts.txt, com o nome e o endereço de cada host da Internet.

2. Explicação

O arquivo era mantido pela SRI International, que coordenava o Network Information Center (NIC). Quando um novo host era ligado à rede, o administrador registrava o nome e o endereço no NIC, que atualizava o hosts.txt no seu servidor. Todos os hosts da Internet baixavam regularmente a versão atualizada e a guardavam num local conhecido (RFC 952), onde as aplicações a consultavam.

Isso funciona com algumas centenas de hosts, mas não com milhares ou milhões. Além disso, a ARPANet usava um espaço de nomes plano: cada host tinha um nome único na rede inteira. Para evitar colisões, os nomes costumavam juntar o nome da instituição a um sufixo para o host, uma espécie de hierarquia improvisada.

3. Visualização

Registre hosts no NIC e veja o que acontece com o arquivo. Depois, aumente o tamanho da rede.

4. Prática

Por que o hosts.txt não serve para uma rede com milhões de hosts?

5. Fixação

  • hosts.txt: um arquivo central com todos os pares nome–endereço, mantido pelo NIC.
  • Espaço de nomes plano: cada nome precisa ser único na rede inteira.
  • Não escala: o arquivo e o número de cópias crescem juntos.
Conceito 4

A árvore de nomes de domínio

1. Contextualização

As limitações do espaço plano ficaram claras antes do fim da ARPANet, e a RFC 819 propôs um esquema de nomes hierárquico. A RFC discutia organizar os nomes como um grafo dirigido, mas a Internet optou por uma árvore capaz de conter todos os nomes.

2. Explicação

  • Os domínios de topo (TLDs, top-level domains) estão ligados direto à raiz. O primeiro foi o .arpa, acrescentado como sufixo aos nomes do hosts.txt.
  • Em 1984 vieram os TLDs genéricos .gov, .edu, .com, .mil e .org.
  • A RFC 1032 propôs usar os códigos de país de duas letras da ISO-3166, como .be (Bélgica), .fr (França), .us (EUA) e .tv (Tuvalu). Assim, todo país ganhou automaticamente um TLD.
  • O conjunto de TLDs é gerido pela ICANN, que também cria TLDs genéricos sem ligação com países (por exemplo, .cat, para a língua catalã).
  • Cada TLD é gerido por uma organização que decide como registrar subdomínios. A maioria usa a regra "quem chegar primeiro leva", com exceções: .gov é do governo dos EUA, .int é de organizações internacionais e .ca é principalmente de quem tem presença no Canadá.

Complemento
O livro diz que havia "discussões em andamento" na ICANN para aumentar o número de TLDs. Isso já aconteceu: a lista oficial da IANA tem hoje mais de mil TLDs (lista da IANA).

3. Visualização

A árvore da Fig. 53 do livro. Clique num nó para montar o nome totalmente qualificado.

4. Prática

O que significa www.computer-networking.info?

5. Fixação

  • Os nomes formam uma árvore; os TLDs ficam logo abaixo da raiz.
  • TLDs genéricos (.com, .org…) e de país (.be, .fr…).
  • A ICANN gere os TLDs; cada TLD define as regras dos seus subdomínios.
Conceito 5

A sintaxe dos nomes totalmente qualificados

1. Contextualização

Para que todos os programas aceitem os mesmos nomes, a sintaxe precisa ser precisa. A RFC 1035 a define com uma gramática BNF. A ideia é a mesma da ABNF do Capítulo 3 (regras de produção), mas a escrita muda: aqui a regra é definida com ::=, as alternativas são separadas por | e as partes opcionais ficam entre [ ]; na ABNF são =, / e * (repetição).

2. Explicação

domain ::= subdomain | " "
subdomain ::= label | subdomain "." label
label ::= letter [ [ ldh-str ] let-dig ]
ldh-str ::= let-dig-hyp | let-dig-hyp ldh-str
let-dig-hyp ::= let-dig | "-"
let-dig ::= letter | digit
letter ::= qualquer uma das 52 letras de A a Z, maiúsculas ou minúsculas
digit ::= qualquer um dos dez dígitos de 0 a 9

BNF dos nomes totalmente qualificados (Listing 1 do livro, pág. 78 do PDF).

Um nome é uma lista ordenada de rótulos (labels) separados por ponto. Cada rótulo começa com letra, pode ter letras, dígitos e hífen, e termina com letra ou dígito. O nome é lido da esquerda para a direita: o primeiro rótulo é um host ou domínio, seguido da hierarquia de domínios, terminando na raiz, implícita à direita. O TLD precisa ser um dos TLDs registrados.

Complemento
Na BNF da RFC 1035, " " representa o nome vazio (a raiz). A regra de começar com letra foi relaxada pela RFC 1123, seção 2.1, que passou a aceitar rótulos começando com dígito (por isso existem nomes como 3com.com). A RFC 1035 também limita cada rótulo a 63 caracteres e o nome inteiro a 255 octetos. O validador abaixo segue a BNF do livro.

Conceito 6

Nomes internacionalizados e o ataque homógrafo

1. Contextualização

O DNS nasceu quando a Internet era usada principalmente na América do Norte, e o projeto inicial supunha nomes só com letras e dígitos (RFC 1035). Com o uso da Internet no mundo todo, passou a ser importante aceitar caracteres fora do ASCII, como em são-paulo ou bücher.

2. Explicação

Os nomes de domínio internacionalizados (RFC 3490) funcionam assim: quase todos os caracteres Unicode podem ser usados, com algumas exceções (o ponto, por exemplo, continua sendo o separador). Depois, o nome em Unicode é convertido numa cadeia ASCII com o prefixo xn--. Os detalhes do algoritmo estão nas RFC 3490 e 3492.

Complemento
A RFC 3490, citada pelo livro, foi substituída em 2010 pela versão conhecida como IDNA2008 (RFC 5890 a 5893), que muda as regras sobre quais caracteres são aceitos. A conversão para ASCII com xn-- continua a ser o Punycode da RFC 3492. O codec "idna" do Python, usado no exemplo de código desta página, ainda segue a versão antiga.

Essa liberdade abriu espaço para o ataque homógrafo: dois nomes visualmente parecidos que não correspondem ao mesmo servidor. O exemplo do livro é G00GLE.COM × GOOGLE.COM: o primeiro usa dois zeros no lugar das letras O. Com outros caracteres Unicode, dá para construir nomes visualmente idênticos a nomes existentes.

3. Visualização

Compare dois nomes caractere a caractere e veja a forma ASCII (xn--) que vai para o DNS.

4. Prática

Em que um nome como bücher.example é convertido para uso no DNS?

5. Fixação

  • IDN: nome em Unicode convertido para ASCII com xn--.
  • Homógrafo: nome que parece outro, mas tem caracteres diferentes.
  • O que vale é a sequência de códigos, não a aparência.
Conceito 7

A resolução de nomes pelo DNS

1. Contextualização

A árvore de nomes é a peça central do DNS (Domain Name System), uma base de dados distribuída com os mapeamentos entre nomes totalmente qualificados e endereços. Mas, se nenhum servidor tem a base inteira, como um cliente descobre o endereço de um nome qualquer?

2. Explicação

O DNS usa o modelo cliente-servidor. Cada servidor de nomes guarda uma parte da base e responde às consultas dos clientes; há pelo menos um servidor responsável por cada domínio. Na árvore da Fig. 54, o servidor responsável por dom responde diretamente:

  • o endereço de qualquer host que esteja diretamente em dom (por exemplo, h2.dom);
  • quais servidores respondem por cada subdomínio direto de dom (sdom1.dom e sdom2.dom, mas não z.sdom1.dom).

Para obter h3.a.sdom1.dom, o cliente pergunta ao servidor de dom, que indica o servidor de sdom1.dom, que indica o de a.sdom1.dom, que finalmente responde o endereço. Para que qualquer nome possa ser resolvido, existem os servidores raiz: cada um conhece os servidores de todos os TLDs, e todos dão as mesmas respostas.

Para falar com os servidores raiz, o cliente precisa saber os endereços deles, e manter essa lista atualizada em todos os hosts seria difícil. Por isso existem os resolvedores (DNS resolvers): servidores que fazem a resolução para um conjunto de clientes. Cada host manda suas consultas a um resolvedor local; são as consultas recursivas, porque o resolvedor percorre a hierarquia em nome do cliente. Vantagens:

  • os hosts não precisam manter a lista dos servidores raiz;
  • os hosts não mandam consultas a servidores no mundo inteiro;
  • o resolvedor atende muitos hosts e pode guardar as respostas em cache, respondendo rápido às consultas populares e aliviando todos os servidores de DNS.

Complemento
Só a consulta do host ao resolvedor é recursiva ("me traga a resposta final"). Para percorrer a hierarquia, o resolvedor faz consultas iterativas: cada servidor responde com o que sabe, em geral a indicação do próximo servidor a consultar (RFC 1034, seção 4.3.1). Cada resposta guardada em cache vale por um tempo limitado, o TTL, definido por quem administra o nome.

3. Visualização

Resolva nomes da Fig. 54 com e sem resolvedor. Depois, ligue o cache e resolva dois nomes do mesmo domínio.

Na simulação, a raiz conhece só dom, que faz o papel de domínio de topo. O cache guarda também as indicações de servidor recebidas no caminho, que também são respostas recebidas pelo resolvedor.

4. Prática

Perguntado sobre h3.a.sdom1.dom, o que o servidor de dom responde?

Qual é a vantagem de mandar as consultas a um resolvedor?

5. Fixação

  • Cada servidor de nomes responde pelo seu domínio e delega os subdomínios diretos.
  • Os servidores raiz conhecem os servidores de todos os TLDs.
  • O resolvedor faz a consulta recursiva pelo cliente e guarda as respostas em cache.
Conceito 8

Os benefícios dos nomes

1. Contextualização

Imagine uma aplicação em que clientes buscam informação em servidores. Numa primeira versão, ela usa só endereços: o servidor roda num host e os clientes se conectam ao endereço dele. Dois problemas:

  • se o servidor mudar de máquina, todos os clientes precisam saber o novo endereço;
  • se houver muitos clientes ao mesmo tempo, não dá para acrescentar outro servidor sem mudar os endereços que os clientes usam.

2. Explicação

Com nomes, os clientes consultam o serviço de nomes antes de contactar o servidor. Se o servidor mudar de máquina, basta atualizar o mapeamento nome → endereço. E um serviço muito popular pode crescer mapeando um nome num conjunto de endereços. Para escolher o endereço de cada resposta, o livro cita três estratégias:

  • um endereço aleatório do conjunto;
  • o endereço do servidor menos carregado, acompanhando a carga dos servidores;
  • o servidor mais próximo, deduzindo a localização do cliente pela consulta.

A lista de endereços não precisa ser fixa: dá para acrescentar e retirar servidores conforme a carga. O contrário também é útil: vários nomes num único endereço. Servidores de pessoas ou pequenas empresas recebem poucos clientes por dia, e dedicar uma máquina a cada um seria desperdício. Um único servidor físico atende vários serviços, cada um com seu nome; se um deles ficar popular, o nome dele passa a apontar para um conjunto de endereços.

Complemento
"Basta atualizar o mapeamento" tem um detalhe: os resolvedores que já guardaram o endereço antigo em cache continuam a usá-lo até o TTL da resposta expirar. Por isso, antes de mudar um servidor de máquina, os administradores costumam reduzir o TTL do nome.

3. Visualização

Três servidores atendem www.exemplo.org. Escolha a estratégia, mande clientes e mude um servidor de máquina.

4. Prática

O servidor de um serviço identificado por nome mudou de máquina. O que é preciso fazer?

Qual mapeamento evita desperdiçar uma máquina para cada serviço pouco acessado?

5. Fixação

  • Nomes deixam o servidor mudar de máquina sem afetar os clientes.
  • Um nome → vários endereços: distribui a carga (aleatório, menos carregado, mais próximo).
  • Vários nomes → um endereço: vários serviços num só servidor.
  • Como as variáveis num programa, as aplicações devem depender de nomes, e não de endereços.
Pratique

Exercícios graduados

  1. Aquecimento: separe blog.computer-networking.info em rótulos e diga o papel de cada um.
    Ver solução

    blog é o host, computer-networking é o domínio e info é o domínio de topo; a raiz fica implícita à direita.

  2. Aquecimento: quais destes nomes são válidos pela BNF do livro: ns-1.exemplo.org, -ns.exemplo.org, ns1.exemplo.org?
    Ver solução

    ns-1.exemplo.org e ns1.exemplo.org. O rótulo -ns começa com hífen, e a regra label exige letra no início.

  3. Intermediário: na Fig. 54, quantos servidores um resolvedor sem cache consulta para resolver h1.a.sdom1.dom, contando a raiz?
    Ver solução

    Quatro: a raiz, o servidor de dom, o de sdom1.dom e o de a.sdom1.dom.

  4. Intermediário: com o hosts.txt, cada um dos n hosts baixa um arquivo de n linhas a cada atualização. Quantas linhas circulam com 1000 hosts? E com 2000?
    Ver solução

    1 000 000 e 4 000 000: o tráfego cresce com n², então dobrar os hosts quadruplica as linhas transferidas.

  5. Desafio: um serviço popular usa a estratégia "mais próximo", e quase todos os clientes de hoje estão na mesma região. O que acontece com a carga? Que estratégia do livro corrigiria isso?
    Ver solução

    O servidor daquela região fica sobrecarregado e os outros ociosos. A estratégia "menos carregado" distribuiria melhor; também dá para acrescentar endereços ao conjunto da região.

1. Um hosts.txt em miniatura

HOSTS_TXT = """
# hosts.txt distribuído pelo NIC (formato simplificado)
10.0.0.73    sri-nic
10.1.0.51    mit-multics
10.3.0.11    ucla-ccn
10.2.0.5     utah-cs
"""

def carrega(texto):
    """Monta a tabela nome -> endereço, ignorando comentários e linhas vazias."""
    tabela = {}
    for linha in texto.splitlines():
        linha = linha.split("#", 1)[0].strip()
        if not linha:
            continue
        endereco, nome = linha.split()
        tabela[nome.lower()] = endereco
    return tabela

def resolve(tabela, nome):
    return tabela.get(nome.lower(), "nome desconhecido")

tabela = carrega(HOSTS_TXT)
for nome in ["sri-nic", "UCLA-CCN", "stanford-ai"]:
    print(f"{nome:12} -> {resolve(tabela, nome)}")

# Cada host baixa o arquivo inteiro do NIC a cada atualização.
for n in (500, 5_000, 50_000):
    tamanho = n * 30                      # ~30 bytes por linha
    print(f"{n:>6} hosts: arquivo de {tamanho/1e3:>7.0f} kB, {n * tamanho/1e9:>8.3f} GB transferidos por atualização")

2. Validando nomes pela BNF

import re

# Listing 1 do livro (RFC 1035): label ::= letter [ [ ldh-str ] let-dig ]
LABEL = re.compile(r"[A-Za-z]([A-Za-z0-9-]*[A-Za-z0-9])?")

def valida(nome):
    """Devolve (ok, motivo) segundo a BNF dos nomes totalmente qualificados."""
    if nome == "":
        return False, "nome vazio"
    for rotulo in nome.split("."):
        if rotulo == "":
            return False, "rótulo vazio (dois pontos seguidos ou ponto na ponta)"
        if not LABEL.fullmatch(rotulo):
            if not rotulo[0].isalpha():
                return False, f"'{rotulo}' não começa com letra"
            if rotulo.endswith("-"):
                return False, f"'{rotulo}' termina com hífen"
            return False, f"'{rotulo}' tem caractere fora de letra, dígito e hífen"
    return True, "ok"

for nome in ["www.computer-networking.info", "blog.uclouvain.be", "3com.com",
             "meu_site.org", "a..b", "servidor-.edu", "h3.a.sdom1.dom"]:
    ok, motivo = valida(nome)
    print(f"{nome:30} {'válido' if ok else 'inválido'}: {motivo}")

3. Nomes internacionalizados e homógrafos

import unicodedata

# 1. Nomes internacionalizados: Unicode -> ASCII com prefixo xn--
#    (o codec "idna" do Python segue a RFC 3490; a versão atual é a IDNA2008)
for nome in ["bücher.example", "são-paulo.example", "例え.jp"]:
    ascii_ = nome.encode("idna").decode("ascii")
    print(f"{nome:20} -> {ascii_}")

# 2. Ataque homógrafo: nomes parecidos, códigos diferentes
def compara(a, b):
    print(f"\n{a!r} x {b!r}: {'iguais' if a == b else 'DIFERENTES'}")
    for x, y in zip(a, b):
        if x != y:
            print(f"  {x!r} U+{ord(x):04X} {unicodedata.name(x)}")
            print(f"  {y!r} U+{ord(y):04X} {unicodedata.name(y)}")

compara("GOOGLE.COM", "G00GLE.COM")
compara("apple.com", "аpple.com")      # o primeiro 'а' é cirílico
print("\nVersão ASCII do falso apple:", "аpple.com".encode("idna").decode())

4. Um resolvedor iterativo com cache

# Árvore da Fig. 54. Cada servidor de nomes conhece os hosts do seu domínio
# e os servidores dos subdomínios diretos (delegações).
SERVIDORES = {
    ".":            {"delega": {"dom": "ns.dom"}},
    "dom":          {"hosts": {"h1": "10.0.0.1", "h2": "10.0.0.2", "h3": "10.0.0.3"},
                     "delega": {"sdom1": "ns.sdom1.dom", "sdom2": "ns.sdom2.dom"}},
    "sdom1.dom":    {"delega": {"a": "ns.a.sdom1.dom", "b": "ns.b.sdom1.dom", "z": "ns.z.sdom1.dom"}},
    "a.sdom1.dom":  {"hosts": {"h1": "10.1.1.1", "h2": "10.1.1.2", "h3": "10.1.1.3"}},
}

class Resolvedor:
    def __init__(self):
        self.cache = {}          # nome -> endereço
        self.consultas = 0

    def resolve(self, nome):
        if nome in self.cache:
            print(f"  {nome}: resposta do cache")
            return self.cache[nome]
        rotulos = nome.split(".")
        zona = "."                                  # começa pelos servidores raiz
        for i in range(len(rotulos) - 1, -1, -1):
            servidor = SERVIDORES.get(zona)
            if servidor is None:
                print(f"  o servidor de {zona!r} não está nesta simulação")
                return None
            self.consultas += 1
            proximo = rotulos[i]
            if i == 0 and proximo in servidor.get("hosts", {}):
                endereco = servidor["hosts"][proximo]
                print(f"  pergunta a {zona!r}: {nome} = {endereco}")
                self.cache[nome] = endereco
                return endereco
            if proximo in servidor.get("delega", {}):
                filho = ".".join(rotulos[i:])
                print(f"  pergunta a {zona!r}: quem responde por {filho!r}?")
                zona = filho
            else:
                print(f"  pergunta a {zona!r}: {nome} não existe")
                return None
        return None

r = Resolvedor()
for nome in ["h2.dom", "h3.a.sdom1.dom", "h3.a.sdom1.dom"]:
    print(nome)
    r.resolve(nome)
print("Consultas enviadas a servidores de nomes:", r.consultas)

Prática: TLS e ssh

Atividade 1

O que o telnet entrega a quem escuta

1. Relembre

O telnet manda cada caractere digitado, sem nenhuma proteção, por uma conexão TCP com a porta 23; o servidor ecoa o que deve aparecer na tela. O ssh substituiu o telnet cifrando e autenticando tudo. Veja o telnet no Capítulo 15.

2. O que o livro mostra

Uma das primeiras motivações para as redes de longa distância foi deixar os pesquisadores usarem servidores distantes. Por muitos anos, isso se fez com um protocolo simples como o telnet sobre TCP. Com o telnet, tudo o que o usuário digita vai em claro: quem captura os pacotes vê nomes de usuário e senhas. Hoje o telnet raramente é usado sem TLS, e os administradores preferem protocolos mais seguros, como o ssh. O TLS é usado por muitas aplicações, sendo o HTTPS a mais popular. Nos exercícios, você analisa algumas características do TLS olhando os pacotes trocados numa sessão (pág. 315 do PDF).

4. Resolução comentada

Resolução (não está no livro) Abrir a resolução

Depois de "Password: ", o cliente manda s, e, g, r, e, d, o, um caractere por segmento, e o servidor não ecoa nada (é por isso que a senha não aparece na tela). Quem captura o tráfego lê "segredo" sem esforço. Além disso, cada tecla custa um segmento inteiro: com cabeçalhos IPv4 e TCP de 20 bytes cada, são 41 bytes para levar 1, mais o eco do servidor. No ssh, o observador só veria pacotes cifrados.

5. Fixação

A senha não aparece na tela do telnet. Ela está protegida na rede?

Atividade 2

O que se vê de uma sessão TLS

1. Relembre

Tudo o que o TLS manda vai em registros: um cabeçalho de 5 bytes (tipo, versão e tamanho) e o conteúdo. Os tipos são 20 (change_cipher_spec), 21 (alert), 22 (handshake) e 23 (application_data). No TLS 1.2, o certificado do servidor passa em claro; no TLS 1.3, tudo depois do ServerHello vai cifrado. Veja o protocolo de registro e o TLS 1.3 no Capítulo 16.

2. O que o livro pede

Analisar algumas características do TLS olhando os pacotes de uma sessão (pág. 315 do PDF). Aqui, a pergunta é: o que um observador consegue ler num handshake TLS 1.2 e num TLS 1.3?

3. Experimente

Capturas ilustrativas: os tipos e as versões seguem as RFCs 5246 e 8446; os tamanhos são exemplos.

4. Resolução comentada

Resolução (não está no livro) Abrir a resolução
  • Cabeçalho: 17 03 03 00 45 é um registro de tipo 0x17 = 23 (application_data), versão 0x0303 e 0x45 = 69 bytes de conteúdo.
  • TLS 1.2: o observador lê ClientHello, ServerHello, Certificate (com o nome e a chave do servidor), ServerKeyExchange e ServerHelloDone. Depois do ChangeCipherSpec, os Finished e os dados vão cifrados.
  • TLS 1.3: só ClientHello e ServerHello passam em claro. O certificado, a assinatura e o Finished do servidor vão num registro que se disfarça de application_data. Os registros 14 03 03 00 01 01 existem só para que caixas intermediárias antigas não estranhem a conexão (RFC 8446, apêndice D.4). E todos os registros dizem 0x0303, a versão do TLS 1.2: a versão de verdade é negociada numa extensão.
  • Nas duas versões, o nome do servidor costuma passar em claro na extensão SNI do ClientHello, e o tamanho e o momento de cada registro continuam visíveis.

5. Fixação

No TLS 1.3, onde um observador ainda costuma ver o nome do site?

Atividade 3

O que o ssh deixa em claro

1. Relembre

O ssh começa com uma linha de identificação em texto e uma negociação de algoritmos (KEXINIT) em claro; depois, uma troca de chaves Diffie-Hellman e a mensagem NEWKEYS, a partir da qual tudo vai cifrado e autenticado. Veja a negociação do ssh e as chaves de sessão no Capítulo 15.

2. O que o livro pede

Para o ssh, a introdução da seção diz só que os administradores o preferem ao telnet (pág. 315 do PDF). Aqui, a pergunta é: o que um observador vê de uma conexão ssh, e que algoritmos os dois lados escolhem?

3. Experimente

Captura ilustrativa; os nomes dos algoritmos são os usados pelo OpenSSH.

4. Resolução comentada

Resolução (não está no livro) Abrir a resolução

A RFC 4253 (seção 7.1) manda escolher, em cada categoria, o primeiro algoritmo da lista do cliente que o servidor também aceita. Na troca de chaves, curve25519-sha256 (o primeiro do cliente, e o servidor o tem); na cifra, chacha20-poly1305 não está no servidor, então fica aes128-gcm@openssh.com. Um observador vê as versões dos programas, essas listas e as chaves públicas efêmeras; depois do NEWKEYS (mensagem 21), só tamanhos e horários de pacotes. Mesmo assim, o tamanho e o ritmo dos pacotes de uma sessão interativa revelam algo, como quando o usuário digita.

5. Fixação

Na negociação do ssh, a preferência de quem prevalece?

Pratique

Exercícios graduados

  1. Básico: Decodifique o cabeçalho de registro TLS 15 03 03 00 02.
    Ver solução

    Tipo 0x15 = 21 (alert), versão 0x0303 e 2 bytes de conteúdo: um alerta tem sempre 2 bytes, o nível e a descrição (quando não está cifrado).

  2. Intermediário: Uma sessão telnet manda 30 teclas, cada uma num segmento IPv6 com TCP sem opções. Quantos bytes passam pelo fio só no sentido do cliente?
    Ver solução

    Cada segmento leva 40 bytes de IPv6, 20 de TCP e 1 de dados: 30 × 61 = 1830 bytes, para 30 bytes úteis.

  3. Intermediário: No ssh, o cliente propõe as cifras aes256-ctr,aes128-gcm@openssh.com e o servidor aceita aes128-gcm@openssh.com,aes256-ctr. Qual é escolhida?
    Ver solução

    aes256-ctr: vale o primeiro da lista do cliente que o servidor também aceita, não importa a ordem do servidor.

  4. Desafio: Por que o TLS 1.3 manda registros de change_cipher_spec que não servem para nada?
    Ver solução

    Para parecer uma sessão TLS 1.2 retomada. Algumas caixas intermediárias antigas bloqueavam o que não reconheciam; com esse disfarce (o "modo de compatibilidade" da RFC 8446, apêndice D.4) e a versão 0x0303 nos registros, o TLS 1.3 passa por elas.

1. Percorrendo registros TLS

# Lendo cabeçalhos de registros TLS (RFC 8446, seção 5.1): tipo (1 byte), versão (2) e tamanho (2).
TIPOS = {20: "change_cipher_spec", 21: "alert", 22: "handshake", 23: "application_data"}
HANDSHAKE = {1: "ClientHello", 2: "ServerHello", 11: "Certificate", 12: "ServerKeyExchange",
             14: "ServerHelloDone", 16: "ClientKeyExchange", 20: "Finished"}

def registros(fluxo):
    """Percorre um fluxo de bytes com vários registros TLS seguidos."""
    i = 0
    while i + 5 <= len(fluxo):
        tipo, versao, tam = fluxo[i], int.from_bytes(fluxo[i + 1:i + 3], "big"), int.from_bytes(fluxo[i + 3:i + 5], "big")
        conteudo = fluxo[i + 5:i + 5 + tam]
        extra = f" ({HANDSHAKE.get(conteudo[0], '?')})" if tipo == 22 and conteudo else ""
        yield TIPOS.get(tipo, "?") + extra, hex(versao), tam
        i += 5 + tam

# um servidor TLS 1.2: ServerHello (4 bytes de conteúdo de mentira), Certificate e ServerHelloDone
fluxo = (bytes.fromhex("16 0303 0004") + bytes([2, 0, 0, 0]) +
         bytes.fromhex("16 0303 0006") + bytes([11, 0, 0, 2, 0, 0]) +
         bytes.fromhex("16 0303 0004") + bytes([14, 0, 0, 0]))
for r in registros(fluxo):
    print(r)

2. A negociação do ssh

import struct

# O começo de uma conexão ssh (RFC 4253): a identificação em texto e as listas do KEXINIT.
banner = b"SSH-2.0-OpenSSH_9.6\r\n"
protocolo, versao_sw = banner.decode().strip().split("-", 2)[1:]
print("protocolo", protocolo, "| programa", versao_sw)

def name_list(nomes):
    dados = ",".join(nomes).encode()
    return struct.pack("!I", len(dados)) + dados     # uint32 com o tamanho e os nomes separados por vírgula

def le_name_list(buf, i):
    n = struct.unpack("!I", buf[i:i + 4])[0]
    return buf[i + 4:i + 4 + n].decode().split(","), i + 4 + n

cliente = {"kex": ["curve25519-sha256", "ecdh-sha2-nistp256", "diffie-hellman-group14-sha256"],
           "cifra": ["chacha20-poly1305@openssh.com", "aes128-gcm@openssh.com", "aes256-ctr"]}
servidor = {"kex": ["sntrup761x25519-sha512@openssh.com", "curve25519-sha256", "diffie-hellman-group14-sha256"],
            "cifra": ["aes256-gcm@openssh.com", "aes128-gcm@openssh.com", "aes256-ctr"]}

# KEXINIT do servidor: tipo 20, 16 bytes aleatórios (cookie) e as listas
kexinit = bytes([20]) + bytes(16) + name_list(servidor["kex"]) + name_list(servidor["cifra"])
lista_kex, i = le_name_list(kexinit, 17)
lista_cifra, i = le_name_list(kexinit, i)

def negocia(do_cliente, do_servidor):
    return next((a for a in do_cliente if a in do_servidor), None)   # RFC 4253, seção 7.1

print("kex:", negocia(cliente["kex"], lista_kex))
print("cifra:", negocia(cliente["cifra"], lista_cifra))

3. A senha capturada

# Uma sessão telnet capturada (modo caractere): cada tecla num segmento.
captura = [("S", "login: ")] + [x for c in "aluno" for x in (("C", c), ("S", c))] + \
          [("C", "\r"), ("S", "\r\nPassword: ")] + [("C", c) for c in "segredo"] + [("C", "\r")]

senha, depois_do_prompt = "", False
for sentido, dados in captura:
    if sentido == "S" and "Password:" in dados:
        depois_do_prompt = True
    elif sentido == "C" and depois_do_prompt:
        if dados == "\r":
            break
        senha += dados
print("senha capturada:", senha)

# quanto custa mandar uma tecla por segmento (IPv4 + TCP sem opções = 40 bytes de cabeçalho)
teclas = sum(1 for s, d in captura if s == "C")
print(f"{teclas} teclas -> {teclas * 41} bytes no fio, dos quais {teclas} de dados ({teclas / (teclas * 41):.1%})")

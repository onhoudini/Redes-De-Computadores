Prática: o TCP de perto

Neste capítulo, você acompanha os scripts packetdrill do livro, que testam a pilha TCP do Linux, e resolve as questões abertas sobre controle de congestionamento com um simulador de diagramas de tempo.

Apresentação

Exercícios sobre o TCP de perto

A seção 4.13 do livro usa o packetdrill para injetar segmentos na pilha TCP do Linux e observar a reação dela, e termina com questões abertas sobre controle de congestionamento (pág. 319–336 do PDF). Os scripts e os valores impressos são os do livro. O formato das atividades está explicado no Capítulo 27.

Objetivos de aprendizagem

  • Ler scripts packetdrill e relacioná-los aos estados, ao rto e à janela de congestionamento do Linux.
  • Montar diagramas de tempo com slow start, ACK atrasado, ECN e perdas, e deduzir o tempo de uma transferência.

Antes de começar

Revise o TCP do Capítulo 20 e o controle de congestionamento do Capítulo 21. O capítulo cobre a seção 4.13 do livro (pág. 319–336 do PDF).

Cada atividade tem cinco etapas: Relembre, O que o livro pede, Experimente, Resolução comentada (fechada, para você tentar antes) e Fixação.

Cada pergunta vale 10 pontos se acertada na primeira tentativa (5 depois). Os desafios das simulações valem de 10 a 20 pontos. Ao concluir tudo de uma atividade, você ganha a medalha dela.

Atividade 1

Injetando segmentos com o packetdrill

1. Relembre

Uma conexão TCP abre em três vias, troca dados com números de sequência por byte e fecha com FINs; o kernel do sistema implementa tudo isso, e a aplicação só vê as chamadas de sistema. Veja o TCP no Capítulo 20.

2. O que o livro mostra

O packetdrill é um conjunto de testes para implementações TCP. Um script tem três tipos de linha: chamadas de sistema, cujo resultado é conferido; segmentos que ele injeta no kernel como se viessem da rede (<); e segmentos que ele espera que o kernel mande (>). Cada linha começa com o instante, absoluto ou relativo (+0,1), e os segmentos usam uma sintaxe próxima à do tcpdump, com números relativos. O primeiro script, connect.pkt, abre uma conexão com o kernel no papel de servidor, troca 10 bytes num sentido e 2 no outro e fecha (pág. 319–322 do PDF). Para o livro, a pilha do Linux foi configurada com MSS de 1000 bytes e sem extensões.

Nota
O packetdrill precisa de privilégios de administrador e de um kernel Linux; os scripts do livro estão no repositório público cnp3/ebook. Aqui, os scripts são percorridos linha a linha.

Atividade 2

Abrindo e fechando: os estados da conexão

1. Relembre

A máquina de estados do TCP passa por SYN_SENT, ESTABLISHED, FIN_WAIT, CLOSE_WAIT, LAST_ACK e TIME_WAIT, entre outros. A abertura e o encerramento podem ser simultâneos. Veja a abertura e a liberação no Capítulo 20.

2. O que o livro mostra

A opção TCP_INFO dá acesso a variáveis do bloco de controle da conexão; tcpi_state segue a máquina de estados do TCP. No client.pkt, o kernel é o cliente: depois de mandar o SYN, imprime 2 (SYN_SENT); depois do SYN+ACK e do ACK, 1 (ESTABLISHED). No dual.pkt, a abertura é simultânea: o kernel manda um SYN, recebe um SYN, responde com SYN+ACK e só fica ESTABLISHED depois do quarto segmento; no meio, imprime 3 (SYN_RECV). Outros três scripts mostram o encerramento: quando o host local fecha primeiro, quando o remoto manda o seu FIN junto com o ACK e quando o remoto fecha primeiro (pág. 322–324 do PDF).

3. Experimente

Os números dos estados são os do Linux (include/net/tcp_states.h). Os estados das linhas marcadas como complemento seguem a máquina de estados da RFC 9293; o livro não os imprime.

4. Resolução comentada

Resolução (não está no livro) Abrir a resolução
  • Abertura simultânea: ao receber um SYN em SYN_SENT, o kernel vai para SYN_RECV (3) e manda SYN+ACK; com o ACK do outro lado, ESTABLISHED (1).
  • Fechamento local: close leva a FIN_WAIT1 (4); o ACK do FIN, a FIN_WAIT2 (5); o FIN do remoto, a TIME_WAIT (6), onde a conexão espera um tempo antes de sumir. Se o FIN do remoto vem junto com o ACK (local-close2), o kernel vai direto de FIN_WAIT1 para TIME_WAIT.
  • Fechamento remoto: o FIN do outro lado leva a CLOSE_WAIT (8), onde a conexão fica até a aplicação chamar close; aí vem LAST_ACK (9) e, com o ACK final, CLOSE (7). Quem fecha primeiro é quem passa por TIME_WAIT.

5. Fixação

Atividade 3

O temporizador e a retransmissão rápida

1. Relembre

O temporizador de retransmissão (rto) vem do RTT medido e da sua variação; quando expira, o TCP retransmite e dobra o rto. Três ACKs duplicados disparam a retransmissão rápida, sem esperar o temporizador. Veja o rto e a retransmissão no Capítulo 20.

2. O que o livro mostra

Com uma janela inicial grande (16 KB), para não haver slow start, o rto.pkt manda 8000 bytes e só o primeiro segmento é confirmado: tcpi_rto vale 204 000 µs antes, 216 000 depois de medir o RTT e dobra a cada retransmissão (432 000, 864 000, 1 728 000). O frr.pkt mostra a retransmissão rápida depois de três ACKs duplicados (tcpi_bytes_retrans passa de 0 a 1000). No frr-rto.pkt, dois segmentos seguidos se perdem: o primeiro volta pela retransmissão rápida e o segundo, 24 ms depois do ACK seguinte; no frr-rto2.pkt, três segmentos se perdem, e tcpi_bytes_retrans chega a 3000 (pág. 324–326 do PDF).

3. Experimente

4. Resolução comentada

Resolução (não está no livro) Abrir a resolução

O rto dobra a cada expiração: o próximo seria 3 456 000 µs (3,456 s). Esse recuo exponencial segura o emissor quando a rede está muito congestionada. O mínimo de cerca de 200 ms que se vê no Linux vem de um piso de implementação, maior que o RTT do teste (0,1 s). No frr-rto2.pkt, os três segmentos perdidos são retransmitidos, um por vez, e tcpi_bytes_retrans soma 1000, 2000 e 3000. Os 24 ms entre o ACK e a retransmissão vêm de uma heurística do Linux para a recuperação.

Atividade 4

A janela de congestionamento no Linux

1. Relembre

No slow start, a janela de congestionamento cresce rápido, até o limiar ssthresh; depois de uma perda, ela cai, e o TCP recupera. Veja a slow start e as reações a perdas no Capítulo 21.

2. O que o livro mostra

Com janela inicial de dois segmentos, os scripts imprimem tcpi_snd_cwnd e tcpi_snd_ssthresh. Sem perdas, a janela vai de 2 a 9 e salta para 18 com um ACK que confirma tudo; com ACK atrasado, vai de 2 a 4, 6, 8, 10 e 18. Quando o penúltimo segmento se perde, não chegam ACKs duplicados suficientes, e o TCP espera o temporizador: a janela cai para 1. Quando o segundo ou o primeiro segmento se perdem, a regra da RFC 3042 manda segmentos novos a cada ACK duplicado, e a retransmissão rápida acontece (pág. 326–330 do PDF).

3. Experimente

4. Resolução comentada

Resolução (não está no livro) Abrir a resolução
  • No slow start, a janela cresce o número de segmentos que cada ACK confirma (contagem de bytes, RFC 3465): um por ACK quando cada ACK confirma um segmento; dois, com ACK atrasado. O salto final soma de uma vez os 9 (ou 8) segmentos confirmados: 9 + 9 = 18 e 10 + 8 = 18.
  • Depois do rto, a janela cai a 1 e o slow start recomeça: o ACK que confirma dois segmentos a leva a 3.
  • Na retransmissão rápida, o Linux reduz a janela aos poucos durante a recuperação (o algoritmo PRR, RFC 6937), por isso os valores 2, 2, 2, 4 e 5 no frr2 não seguem a regra simples de dividir por dois. Os números do livro são o que conta aqui.

5. Fixação

Atividade 5

Diagramas de tempo com controle de congestionamento

1. Relembre

A janela efetiva é o menor entre a janela de congestionamento e a de recepção. No slow start, a cwnd cresce um MSS por ACK; acima do ssthresh, cresce cerca de um MSS por RTT. Uma marca ECN ou uma perda reduzem a janela. Veja o Capítulo 21.

2. O que o livro pede

Hipóteses das questões (pág. 326–327 do PDF): o emissor faz um único send de x bytes; o RTT é fixo, de 100 ms, e o temporizador, de 200 ms; transmitir um segmento de MSS bytes leva 1 ms, seja qual for o MSS; o ACK não tem tempo de transmissão; a janela inicial é de um segmento; o limiar de ACKs duplicados é 3; e o TCP confirma cada segmento recebido.

  1. Com cwnd de 1000 bytes, rwin de 2000 (constante) e ssthresh de 64 000, o emissor manda 3 KB. (a) Por que manda primeiro um segmento e depois dois? (b) Por que a janela cresce ao chegar o primeiro ACK? (c) Quanto tempo leva para entregar os 3 KB?
  2. A mesma coisa, com a janela inicial de 10 000 bytes, como nas implementações recentes.
  3. A mesma coisa, com MSS de 500 bytes. Como isso afeta o atraso total?
  4. Sem perdas nem congestionamento, deduza uma fórmula para o tempo mínimo de entregar x bytes numa conexão nova, com x múltiplo do MSS e rwin e ssthresh maiores que x.
  5. Com ACK atrasado (temporizador de 50 ms), refaça o diagrama da Q1. O atraso aumenta ou diminui?
  6. Com cwnd de 4000 bytes e rwin de 64 000, o emissor manda 10 KB. Refaça o diagrama supondo que (a) o segundo segmento passou por congestionamento e veio marcado (ECN), com a marca devolvida no ACK; (b) o quarto segmento foi marcado, sem ser descartado.
  7. Uma conexão chegou a cwnd de 4000 bytes (com ssthresh de 4000). Quatro segmentos são enviados, e o segundo chega corrompido. Complete o diagrama (pág. 327–336 do PDF).

3. Experimente

Hipóteses do simulador além das do livro: na ECN, o emissor divide a janela por dois uma vez por RTT; na retransmissão rápida e no rto, o ssthresh vira metade dos bytes em voo; a retransmissão reinicia o temporizador (RFC 6298).

4. Resolução comentada

Resolução (não está no livro) Abrir a resolução
  • Q1: (a) a janela inicial é de um segmento; (b) no slow start, cada ACK soma um MSS à cwnd, que vai a 2000 e libera dois segmentos; (c) o primeiro segmento sai em 0–1 ms e o ACK volta em 101 ms; os outros dois saem em 101–103 ms, e o último chega ao receptor em 153 ms (o emissor recebe o último ACK em 203 ms).
  • Q2: a cwnd de 10 000 não ajuda muito, porque a rwin de 2000 limita a dois segmentos em voo: o terceiro só sai com o primeiro ACK. Os dados chegam em 152 ms.
  • Q3: com MSS de 500, a janela inicial tem 500 bytes e são precisos 6 segmentos: três rodadas de slow start em vez de duas. A entrega passa para 255 ms, um RTT a mais.
  • Q4: com n = x/MSS segmentos, a rodada k manda 2k−1 segmentos; são r = ⌈log2(n + 1)⌉ rodadas, a última com nr = n − (2r−1 − 1) segmentos. Com d = 1 ms por segmento: T = (r − 1)(RTT + d) + nr · d + RTT/2. Para 3 KB: r = 2, nr = 2, T = 101 + 2 + 50 = 153 ms. O bloco 3 confere a fórmula com o simulador.
  • Q5: o primeiro segmento chega sozinho, e o receptor espera 50 ms antes de confirmar: tudo atrasa 50 ms, e a entrega passa para 203 ms. O ACK atrasado aumenta o atraso no começo da conexão.
  • Q6: sem marcas, os 10 segmentos chegam em 157 ms. (a) Com o segundo marcado, o ACK com a marca chega quando a cwnd vale 5000: ela cai para 2500, e o resto da transferência segue em prevenção de congestionamento; a entrega vai para 256 ms. (b) Com o quarto marcado, quando a marca chega, os 10 segmentos já foram enviados: a entrega continua em 157 ms, e só a janela das próximas transmissões fica menor.
  • Q7: o receptor confirma o primeiro (ack 1000) e manda dois ACKs duplicados pelo terceiro e pelo quarto. Dois não bastam, mas o ACK novo levou a cwnd a 4250 e liberou mais um segmento, cuja chegada produz o terceiro duplicado: retransmissão rápida aos 202 ms, cwnd de 2000, e a entrega termina em 457 ms. Sem esse segmento extra, o TCP teria esperado o temporizador de 200 ms.

5. Fixação

Quantos bytes o emissor pode ter em voo?

Pratique

Exercícios graduados

  1. Básico: Num script packetdrill, o kernel manda > P. 1:1001(1000) ack 1. Que ack o packetdrill deve injetar para confirmar esse segmento?
    Ver solução

    ack 1001: o segmento leva os bytes 1 a 1000, e o próximo esperado é o 1001.

  2. Intermediário: Se o rto começa em 216 ms e a perda continua, em quanto tempo, a partir da primeira retransmissão, sai a quarta?
    Ver solução

    As esperas são 432, 864 e 1728 ms depois da primeira: 432 + 864 + 1728 = 3024 ms, cerca de 3 s.

  3. Intermediário: Com as hipóteses da seção 4.13.2 e rwin grande, quanto tempo leva para entregar 7 KB (sete segmentos de 1000 bytes)?
    Ver solução

    Três rodadas (1, 2 e 4 segmentos): T = 2 × 101 + 4 + 50 = 256 ms.

  4. Desafio: Com janela inicial de 10 segmentos (RFC 6928) e as mesmas hipóteses, quanto tempo leva para entregar 31 segmentos? E com janela inicial 1?
    Ver solução

    Rodadas de 10, 20 e 1 segmento: o último sai em 202 ms e chega em 202 + 1 + 50 = 253 ms. Com janela inicial 1, são cinco rodadas (1, 2, 4, 8 e 16): 4 × 101 + 16 + 50 = 470 ms.

1. Lendo o connect.pkt

import re

# As linhas de segmento do connect.pkt (pág. 321-322). "<" o packetdrill injeta; ">" o kernel deve mandar.
# As chamadas de sistema ficaram de fora; por isso, os instantes não contam o +.2 do read.
SCRIPT = """\
+0 < S 0:0(0) win 1000 <mss 1000>
+0 > S. 0:0(0) ack 1 <...>
+.1 < . 1:1(0) ack 1 win 1000
+0 > P. 1:11(10) ack 1
+.1 < . 1:1(0) ack 11 win 1000
+.1 < P. 1:3(2) ack 11 win 4000
+0 > . 11:11(0) ack 3
+0 < F. 3:3(0) ack 11 win 4000
+0 > . 11:11(0) ack 4
+0 > F. 11:11(0) ack 4
+0 < . 4:4(0) ack 12 win 4000"""

PADRAO = re.compile(r"^\+?([\d.]+) ([<>]) (\S+) (\d+):(\d+)\((\d+)\)(?: ack (\d+))?")
t = 0.0
for linha in SCRIPT.splitlines():
    dt, sentido, flags, ini, fim, tam, ack = PADRAO.match(linha).groups()
    t += float(dt)
    quem = "packetdrill -> kernel" if sentido == "<" else "kernel -> packetdrill"
    consome = int(tam) + ("S" in flags) + ("F" in flags)        # SYN e FIN consomem um número
    faixa = f"seq {ini}" if consome == 0 else f"seq {ini}..{int(ini) + consome - 1}"
    print(f"{t:4.1f} s  {quem:22} [{flags:2}] {faixa}{'' if ack is None else ', ack ' + ack}")

2. O slow start do Linux

# O slow start do Linux nos scripts da pág. 326-328: a cwnd cresce os segmentos que cada ACK confirma.
def slow_start(acks, cwnd=2, mss=1000):
    confirmado, saida = 1, [cwnd]
    for ack in acks:
        segmentos = (ack - confirmado) // mss
        cwnd += segmentos                      # contagem de bytes (RFC 3465), sem limite por ACK
        confirmado = ack
        saida.append(cwnd)
    return saida

um_por_segmento = [1001, 2001, 3001, 4001, 5001, 6001, 7001, 16001]
atrasado = [2001, 4001, 6001, 8001, 16001]
print("slow-start.pkt:        ", slow_start(um_por_segmento), "(o livro imprime 2, 3, 4, 5, 6, 7, 8, 9, 18)")
print("slow-start-delayed.pkt:", slow_start(atrasado), "(o livro imprime 2, 4, 6, 8, 10, 18)")

3. A fórmula da Q4

import math

# Q4 (pág. 329): tempo mínimo para entregar x bytes com slow start, sem perdas, rwin e ssthresh grandes.
RTT, D = 100, 1            # ms; D = tempo de transmitir um segmento

def formula(x, mss=1000):
    n = math.ceil(x / mss)
    r = math.ceil(math.log2(n + 1))          # rodadas: 1, 2, 4, ... segmentos
    ultima = n - (2 ** (r - 1) - 1)          # segmentos na última rodada
    return (r - 1) * (RTT + D) + ultima * D + RTT / 2

def simula(x, mss=1000):
    """Cada ACK soma um MSS à cwnd; o enlace do emissor manda um segmento por ms."""
    n = math.ceil(x / mss)
    chegada_ack = []                          # quando cada ACK volta ao emissor
    livre, cwnd, enviados, t = 0.0, 1, 0, 0.0
    entrega = 0.0
    while enviados < n:
        while enviados < n and enviados - len([a for a in chegada_ack if a <= t]) < cwnd:
            ini = max(t, livre); livre = ini + D
            entrega = livre + RTT / 2         # o segmento chega ao receptor
            chegada_ack.append(livre + RTT)
            enviados += 1
        proximos = sorted(a for a in chegada_ack if a > t)
        if not proximos:
            break
        t = proximos[0]
        cwnd = 1 + len([a for a in chegada_ack if a <= t])   # slow start: +1 por ACK recebido
    return entrega

for x in (1000, 3000, 7000, 10000, 15000):
    print(f"x = {x:5} bytes: fórmula {formula(x):6.1f} ms, simulação {simula(x):6.1f} ms")

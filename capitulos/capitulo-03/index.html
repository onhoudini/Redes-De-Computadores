Capítulo 3

Aplicações

Os capítulos anteriores levaram bits de um host a outro, primeiro por um único enlace e depois através de roteadores. Mas ninguém liga um computador para trocar bits: queremos abrir páginas, mandar e-mails, imprimir documentos. Este capítulo olha para o topo da pilha, ou seja, como as aplicações se organizam e como combinam o formato e a ordem das mensagens que trocam.

Apresentação

Do bit à conversa entre programas

Quando você abre um site, seu navegador e um programa em outro continente trocam mensagens. Para que isso funcione, os dois precisam concordar sobre quem fala primeiro, o que cada mensagem significa e como ela é escrita em bits. Essas regras formam um protocolo de aplicação.

Objetivos de aprendizagem

  • Distinguir os modelos cliente-servidor e peer-to-peer.
  • Explicar as duas partes de um protocolo de aplicação: sintaxe e organização do fluxo.
  • Codificar texto em ASCII, incluindo os caracteres de controle CR e LF.
  • Ler e aplicar uma gramática ABNF.
  • Explicar a ordem de rede (big-endian) e por que ela existe.
  • Interpretar o diagrama de 32 bits usado para descrever mensagens binárias.

Como funciona a pontuação

Cada conceito tem perguntas e desafios interativos. Acertos somam pontos, e completar tudo de um conceito rende uma medalha. O progresso fica salvo neste navegador.

Conceito 1

O modelo cliente-servidor

1. Contextualização

Até os anos 1980, os únicos computadores em rede eram mainframes e minicomputadores, máquinas multiusuário usadas por dezenas de pessoas ao mesmo tempo. Cada pessoa usava um terminal: uma tela e um teclado ligados por cabo ao computador central. Um lado só pedia; o outro fazia todo o trabalho. Esse arranjo inspirou o primeiro modelo de aplicação em rede.

2. Explicação

No modelo cliente-servidor, um servidor oferece um serviço e clientes trocam informação com ele. O modelo é fortemente assimétrico: clientes enviam requisições, e servidores executam ações e devolvem respostas.

  • Um servidor web devolve informação em resposta à requisição do cliente.
  • Um servidor de impressão imprime os documentos enviados pelos clientes.
  • Um servidor de e-mail encaminha as mensagens recebidas até o destinatário.
  • Um servidor de música entrega a música pedida.

Do ponto de vista de quem programa a aplicação, cliente e servidor trocam mensagens diretamente (setas horizontais). Na prática, essas mensagens descem pelas camadas inferiores, atravessam a rede e sobem do outro lado (setas verticais). Neste capítulo o foco está nas trocas horizontais; a camada de transporte, que torna isso possível, é o tema do Capítulo 4.

3. Visualização

Escolha um servidor e envie uma requisição. Depois ligue as camadas inferiores para ver o caminho real.

4. Prática

Qual frase descreve o modelo cliente-servidor?

5. Fixação

  • Cliente pede, servidor responde: um modelo assimétrico.
  • A aplicação enxerga uma troca horizontal; as camadas de baixo fazem a entrega de verdade.
Conceito 2

Protocolos de aplicação: sintaxe e fluxo

1. Contextualização

Alice quer saber as horas, mas está sem relógio. Bob passa perto e a conversa acontece assim:

Alice: Olá
Bob: Olá
Alice: Que horas são?
Bob: 11:55
Alice: Obrigada
Bob: De nada

A conversa funciona porque os dois falam a mesma língua. Se Alice encontrasse Tchang, que só fala chinês, não conseguiria perguntar as horas. E Alice não pergunta as horas antes de cumprimentar: há uma ordem esperada.

Agora imagine Bob como segurança de uma sala restrita: ele pergunta a senha; Trudy responde "1234" e entra; Alice responde "3.1415" e é barrada.

2. Explicação

Computadores se parecem mais com soldados do que com amigos conversando: precisam de regras bem definidas. Um protocolo de aplicação é o conjunto de regras sintáticas e semânticas que cliente e servidor seguem. Ele define dois tipos de regra:

  1. Regras sintáticas: o formato exato das mensagens. Como computadores só processam bits, a sintaxe especifica como a informação vira cadeias de bits.
  2. Organização do fluxo de informação: a ordem das mensagens e as relações de precedência entre elas. Por exemplo, um servidor só aceita comandos mais complexos depois de receber um nome de usuário e uma senha válida.

3. Visualização

Você é o cliente. Envie mensagens em qualquer ordem e veja como o outro lado reage.

4. Prática

O cliente envia LIST antes de USER e PASS e recebe “Autentique-se primeiro”. Que tipo de regra foi violada?

5. Fixação

  • Protocolo de aplicação = sintaxe (formato) + fluxo (ordem).
  • Sem sintaxe comum, não há conversa; sem ordem combinada, o servidor rejeita a mensagem.
Conceito 3

Mensagens de texto: ASCII, CR e LF

1. Contextualização

Protocolos como os de correio eletrônico trocam linhas de texto. A camada de transporte só entrega bytes. Então os dois lados precisam concordar sobre qual byte representa cada caractere e como uma linha termina.

2. Explicação

O método mais simples e antigo é a tabela ASCII, publicada para a Internet na RFC 20. Alguns exemplos:

Caractere7 bitsTipo
A1000001imprimível
00110000imprimível
z1111010imprimível
@1000000imprimível
espaço0100000imprimível
CR (carriage return)0001101controle
LF (line feed)0001010controle
Bell0000111controle

Nota
A edição do livro lista A : 1000011b, mas 1000011 é o código de C. O código correto de A (65) é 1000001, como na tabela acima.

Além dos imprimíveis, a tabela define caracteres de controle, criados para comandar impressoras e terminais. CR e LF terminam uma linha; Bell faz o terminal apitar. Cada caractere ASCII é um campo de 7 bits, transmitido como um byte de 8 bits com o bit mais alto normalmente em 0. Nos diagramas e nas RFCs, os bits de cada byte são escritos e numerados a partir do mais significativo.

Nota
O livro diz que os bytes são "sempre" transmitidos a partir do bit mais significativo (pág. 56 do PDF). Isso vale para a notação usada nos protocolos de aplicação, que só veem bytes. No fio, a ordem dos bits é escolha da camada física: a Ethernet, por exemplo, envia cada byte começando pelo bit menos significativo.

3. Visualização

Digite um comando e veja os bytes que vão para a rede. O Capítulo 1 mostra a codificação UTF-8, usada para caracteres fora do ASCII.

4. Prática

Quantos bytes ocupa a linha “USER alice” terminada com CR LF?

5. Fixação

  • ASCII: 7 bits por caractere, enviados em um byte com o bit mais alto em 0.
  • CR LF marca o fim de linha nos protocolos de texto da Internet.
  • Na notação dos protocolos, os bits de um byte são escritos do mais significativo para o menos significativo.
Conceito 4

Descrevendo mensagens com gramáticas ABNF

1. Contextualização

Como dizer, sem ambiguidade, quais linhas de texto um servidor aceita? "O nome de usuário é curto" não basta: quantas letras? Pode ter dígitos? Maiúsculas importam?

2. Explicação

A solução comum é escrever uma gramática na forma de Backus-Naur (BNF), como a Augmented BNF da RFC 5234. Uma gramática é um conjunto de regras de produção que geram todas as cadeias válidas. O livro usa um exemplo com dois comandos, um para o nome de usuário e outro para a senha:

  • %x41 é o código ASCII 41 em hexadecimal, isto é, a letra A maiúscula.
  • Texto entre aspas, como "user", não diferencia maiúsculas: user, USER e uSeR servem.
  • 1*8ALPHA significa de 1 a 8 letras, maiúsculas ou minúsculas: ALPHA inclui as duas faixas (%x41-5A e %x61-7A). O que diferencia maiúsculas em ABNF são os valores numéricos como %x41, que casam com um único código.
  • ALPHA *(ALPHA / DIGIT): a senha começa com letra e segue com quantas letras ou dígitos quiser. Espaços e caracteres de controle não são permitidos.

Nota
O livro diz que os nomes de usuário diferenciam maiúsculas "porque não estão entre aspas" (pág. 57 do PDF). A gramática não afirma isso: alice e Alice são ambos username válidos. Se eles identificam o mesmo usuário ou não, é uma regra do servidor, que a ABNF não descreve (RFC 5234, seção 2.3).

3. Visualização

Digite uma linha e veja, regra por regra, onde ela é aceita ou recusada.

4. Prática

Qual destas linhas é um passwordcommand válido?

5. Fixação

  • Uma gramática ABNF diz exatamente quais cadeias são válidas.
  • Literais entre aspas não diferenciam maiúsculas; valores como %x41, sim. ALPHA aceita as duas formas.
  • n*m limita repetições; / indica alternativas.
Conceito 5

Inteiros na rede: big-endian e ordem de rede

1. Contextualização

Nem tudo é texto: muitas aplicações trocam inteiros de 16 ou 32 bits. A ideia ingênua é enviar o número exatamente como ele está na memória. O problema é que processadores diferentes guardam o mesmo número de formas diferentes.

2. Explicação

Alguns processadores guardam o byte mais significativo no primeiro endereço; outros guardam ali o menos significativo. Ao transferir um campo de 16 bits, há então duas opções: enviar primeiro o byte mais significativo (big-endian) ou o menos significativo (little-endian). Os nomes vêm de uma nota de Cohen (1980), e a discussão entre fabricantes virou quase uma questão religiosa.

A Internet escolheu big-endian: campos de vários bytes são sempre transmitidos com o byte mais significativo primeiro. A RFC 791 chama isso de ordem de rede (network byte order). Bibliotecas oferecem funções de conversão, como htonl(3) (host → rede) e ntohl(3) (rede → host) da biblioteca C.

3. Visualização

Desligue a conversão e veja o que o receptor entende.

4. Prática

Em ordem de rede, quais bytes são transmitidos, e em que ordem, para o valor de 16 bits 0x1234?

5. Fixação

  • Ordem de rede = big-endian = byte mais significativo primeiro.
  • Converta sempre com htons/htonl ao enviar e ntohs/ntohl ao receber.
Conceito 6

Formatos de mensagem binária

1. Contextualização

Algumas mensagens misturam campos de tamanhos variados: um campo de 16 bits, oito flags de 1 bit, um campo de 24 bits e dois bytes. Como especificar isso de forma que dois programadores, em empresas diferentes, produzam exatamente os mesmos bits?

2. Explicação

As especificações da Internet usam um desenho em ASCII: cada linha tem 32 bits, barras verticais delimitam os campos e os números no topo indicam a posição de cada bit, com o bit mais alto na posição 0. A mensagem é transmitida a partir da linha de cima, em ordem de rede.

3. Visualização

Altere os campos e veja cada bit na grade de 32 colunas e a sequência de bytes transmitida.

4. Prática

Em que posição de bit fica a flag A?

5. Fixação

  • Linhas de 32 bits, bit 0 à esquerda (o mais significativo).
  • Campos podem atravessar linhas; a transmissão segue linha a linha, em ordem de rede.
Conceito 7

O modelo peer-to-peer

1. Contextualização

No cliente-servidor, um único servidor atende muitos clientes. O que acontece quando milhares de pessoas querem o mesmo arquivo ao mesmo tempo?

2. Explicação

No modelo peer-to-peer (P2P), todos os hosts atuam ao mesmo tempo como clientes e como servidores. O modelo foi usado em telefonia pela Internet, compartilhamento de arquivos e sistemas de arquivos distribuídos pela Internet.

3. Visualização

4. Prática

Em uma aplicação peer-to-peer, qual é o papel de cada host?

5. Fixação

  • Cliente-servidor: papéis fixos e assimétricos.
  • Peer-to-peer: cada host é cliente e servidor, o que distribui a carga.
Pratique

Exercícios graduados

  1. Aquecimento: escreva em binário os bytes da linha “QUIT” terminada com CRLF.
    Ver solução

    01010001 01010101 01001001 01010100 00001101 00001010 (Q, U, I, T, CR, LF).

  2. Intermediário: estenda a gramática ABNF com um comando quit sem argumentos.
    Ver solução

    quitcommand = "quit" CRLF

  3. Intermediário: um host little-endian envia o inteiro de 32 bits 1 sem converter. Que valor um receptor que segue a ordem de rede lê?
    Ver solução

    Os bytes saem como 01 00 00 00; em big-endian isso vale 0x01000000 = 16 777 216.

  4. Desafio: desenhe, no formato de 32 bits por linha, uma mensagem com um campo de 8 bits “versão”, um campo de 8 bits “tipo”, um campo de 16 bits “comprimento” e um campo de 32 bits “identificador”.
    Ver solução

    Linha 1: versão (bits 0–7), tipo (8–15), comprimento (16–31). Linha 2: identificador ocupando os 32 bits. Total: 8 bytes, enviados em ordem de rede.

Exemplos de código

Os três trechos em Python abaixo rodam no navegador. Edite, execute e resolva os desafios de cada bloco.

1. Validando comandos com a gramática ABNF

import re

# Gramática da Fig. 37 traduzida para expressões regulares.
# (?i:user) aceita user, USER, uSeR...; [A-Za-z] aceita letras maiúsculas e minúsculas.
USERCOMMAND = re.compile(r"(?i:user) ([A-Za-z]{1,8})\r\n")
PASSWORDCOMMAND = re.compile(r"(?i:pass) ([A-Za-z][A-Za-z0-9]*)\r\n")

def classifica(linha: str) -> str:
    if m := USERCOMMAND.fullmatch(linha):
        return f"usercommand (username={m.group(1)!r})"
    if m := PASSWORDCOMMAND.fullmatch(linha):
        return f"passwordcommand (password={m.group(1)!r})"
    return "inválida"

linhas = ["user alice\r\n", "USER Bob\r\n", "user alexandre\r\n",
          "pass s3gr3d0\r\n", "pass 3.1415\r\n", "user bob"]
for linha in linhas:
    print(f"{linha!r:20} -> {classifica(linha)}")

2. Ordem dos bytes com struct

import struct, sys

valor = 0x12345678
print("Ordem nativa desta máquina:", sys.byteorder)

big = struct.pack(">I", valor)     # ordem de rede (big-endian)
little = struct.pack("<I", valor)  # little-endian
print("big-endian:   ", big.hex(" "))
print("little-endian:", little.hex(" "))

# O receptor sempre interpreta em ordem de rede ("!" = network = big-endian).
print("Lido corretamente: ", hex(struct.unpack("!I", big)[0]))
print("Lido sem conversão:", hex(struct.unpack("!I", little)[0]))

def htonl(x: int) -> int:
    """Converte da ordem do host para a ordem de rede, como htonl(3) em C."""
    return int.from_bytes(x.to_bytes(4, sys.byteorder), "big")

print("htonl(0x12345678) =", hex(htonl(valor)))

3. Empacotando a mensagem da Fig. 38

LETRAS = "ABCDEFGH"

def empacota(f16: int, flags: str, f24: int, b1: int, b2: int) -> bytes:
    """Monta a mensagem da Fig. 38. flags: letras ligadas, ex. "AH"."""
    bits_flags = 0
    for i, letra in enumerate(LETRAS):
        if letra in flags:
            bits_flags |= 1 << (7 - i)      # A é o bit mais alto
    return (f16.to_bytes(2, "big") + bytes([bits_flags])
            + f24.to_bytes(3, "big") + bytes([b1, b2]))

def desempacota(msg: bytes):
    f16 = int.from_bytes(msg[0:2], "big")
    flags = "".join(l for i, l in enumerate(LETRAS) if msg[2] & (1 << (7 - i)))
    f24 = int.from_bytes(msg[3:6], "big")
    return f16, flags, f24, msg[6], msg[7]

msg = empacota(1500, "AH", 70000, 7, 255)
print("Bytes:", msg.hex(" "))
for linha in range(2):
    palavra = msg[linha * 4:(linha + 1) * 4]
    print(f"palavra {linha + 1}:", " ".join(f"{b:08b}" for b in palavra))
print("Desempacotado:", desempacota(msg))
